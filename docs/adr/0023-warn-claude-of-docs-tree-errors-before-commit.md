# 0023. git commit の前に文書の木を検査し、見つけた誤りを Claude に伝えるフックを足す

## コンテキストと問題

spec 071（PR #134）は、sync-docs に文書の木を加えた。文書の木は、リポジトリ、プロダクト、機能フォルダの README を、親から子へ、子から親へリンクでつなぐ構造である。`check_tree.py` は、`.living-documentation.json` に `tree` を宣言したプロジェクトで、README がないフォルダと親子のリンクの欠けを誤りとして報告する。CI のひな形もこの検査を走らせる。

ただし、作業の途中でこの検査が走る仕組みはない。sync-docs を使うかどうかは、モデルが skill の説明文を見て選ぶ。モデルが実際に選ぶかは測っていない（spec 071 の `residual-risks.md`）。新しい機能フォルダの README を作り忘れても、push した後の CI で初めて分かる。

2026-11-14 に、利用者は `check_tree.py` を走らせるフックを求めた。その前の回答で、私（Claude）は作業の終わりに走らせる Stop フックを勧めていた。ところが、`docs/harness-zero-base.md` §6.7 は「Stop フックを足さない」と決めている。理由は2つある。spec 042 が、応答のたびにモデルを呼ぶ Stop フックを費用を理由に外したこと。`maintaining-living-documentation` の Stop フックが誤って作業を止め、2026-10-18 に外されたこと。

公式の文書（<https://code.claude.com/docs/en/hooks.md>、<https://code.claude.com/docs/en/hooks-guide.md>）で確かめたこと:

- Stop フックの `systemMessage` は利用者に表示される。Claude がそれを読むかは書かれていない。Claude に直させるには、`block` か `additionalContext` で応答を続けさせるしかない。
- PreToolUse フックの `if` は、フックの定義に置き、権限の規則と同じ書き方で、実行するコマンドを絞る。`npm test && git push` のような複合コマンドは、コマンドごとに照合される。先頭の変数の代入は外して照合する。絞り込みは最善の努力で、判定できないときはフックを走らせる。
- PreToolUse フックの `additionalContext` は、system reminder として Claude に渡る。
- 終了コード 2 は、道具の呼び出しを止める。それ以外の失敗、無効な JSON の出力、時間切れは、呼び出しを止めない。

`permissionDecision` を返さなければ通常の許可の流れのまま進む、という点は、文書の記述（終了コード 0 は承認ではない）からの推論である。

利用者は同じ日に、次のように答えた。走らせるときは「git commit の直前」。誤りを見つけたときは「警告だけ」。この決定は「ADR に書く」。

## 決定

- `harness/settings.json` に、PreToolUse のフックを1つ足す。設定は次のとおり。
  - `matcher` は `Bash`、`if` は `Bash(git *)`、`timeout` は 15 秒。
  - `Bash(git commit*)` にしない理由: これは `git commit` で始まるコマンドにしか当たらず、`git -C <path> commit` や `git -c user.name=x commit` を取りこぼす。どれがコミットかはスクリプトが判定する。
  - `settings.json` に書くのは1行のコマンドである。そのコマンドが、sync-docs に同梱した `~/.claude/skills/sync-docs/scripts/check_tree.py --hook` を走らせる。
  - スクリプトか `python3` がなければ、何もしない。標準エラーは捨て、終了コードは常に 0 にする。
- `check_tree.py --hook` は、フックの入力を標準入力から読み、次のように動く。
  - コマンドを、シェルの引用符を守って単純なコマンドに分ける。コミットのメッセージの中の `;` や `(` は区切りにならない。ヒアドキュメントの本文は読まない。
  - そのうちの1つが、git の大域オプションを挟んでもよい `git commit` のときだけ動く。
  - コミットが走るディレクトリを求める。入力の `cwd` から始め、コミットの前の `cd` と git の `-C` で移す。変数や置き換えを含むパスは展開しない。そのため、書いたとおりのパスが存在しなければ何もしない。
  - そのディレクトリから Git の作業ツリーの根まで上り、最も近い `.living-documentation.json` を持つフォルダをプロジェクトとする。
  - その設定が `tree` を持つときだけ検査する。`tree` のない設定は、壊れていても何も言わない。
  - 誤りがあれば、`additionalContext` として Claude に渡す。渡すのは最大 20 件で、残りは件数だけにする。`tree` を持つ設定自体の誤りも同じように渡す。
  - リポジトリから来る文字列（フォルダの名前、設定の誤りの文）は、制御文字を空白にし、1行 200 字で切る。
  - 文面は、コミットはすでに済んでいるかもしれないこと、この変更が生んだ誤りは次のコミットで直し、前からある誤りは人に伝えることを書く。
  - `permissionDecision` は返さない。どんな失敗でも、何も出さずに終了コード 0 で終わる。
  - `TODO(unfilled)` の警告は渡さない。宣言したプロジェクトでは、ほぼ毎回のコミットに出るためである。
- Stop フックは足さない。`docs/harness-zero-base.md` §6.7 の決定は、そのまま変えない。
- 形は ADR-0008 にならい、`settings.json` に書いた1行のコマンドだけにする。フックのディレクトリもラッパーのスクリプトも作らない（ADR-0005）。検査の本体は、sync-docs に同梱した `check_tree.py` である。

## 検討した選択肢

- **応答のたびに走らせる Stop フック（警告だけ）**: §6.7 と食い違う。利用者には見えるが、Claude に届くかは文書に書かれていない。利用者は選ばなかった。
- **Claude に応答を続けさせる Stop フック**: 前に外したフックと同じ壊れ方をする。誤りが前からあるリポジトリでは、関係のない応答のたびに作業が続く。
- **誤りがあればコミットを止める（`deny`）**: README の抜けは必ず直される。ただし、誤りが前からあるリポジトリでは、関係のないコミットも止まる。利用者は警告だけを選んだ。
- **CI だけにする**: 今の状態である。抜けは push の後に分かる。
- **各プロジェクトの Git の pre-commit フック**: 人のコミットも検査できる。ただし、プロジェクトごとに入れる必要があり、ハーネスの外にある。ハーネスはすべてのプロジェクトに設定なしで効く形を選んだ。人のコミットまで検査したいプロジェクトは、自分で足せる。

## 確認方法

- `bash tests/run-commit-tree-hook.sh` は、`settings.json` のフックを sh、bash、zsh（入っていれば）で、作業用の HOME を使って走らせる。確かめることは次のとおり。
  - フックは1つだけで、`timeout` は 30 秒以下である。
  - `if` の接頭辞が、`git commit`、`git -C <path> commit`、`git -c <name=value> commit`、`git --no-pager commit` のどれも覆う。
  - 誤りは `additionalContext` として出る。許可の判定は出さず、終了コードは 0 である。
  - `git status` では何も出さない。sync-docs も `python3` もなければ、何もしない。
  - 検査のスクリプトが終了コード 2 で落ちても、止めない。
  - `jq` か `python3` がなければ、このテストは失敗する。
- 2026-11-14 に、このテストが落ちることも確かめた。
  - `main` の `settings.json` では、6件が落ちる。
  - 終了コードを 0 にする部分を外したコマンドでは、TREE-07 が3件落ちる。
  - `if` を `Bash(git commit*)` に戻すと、TREE-01 が落ち、覆わない3つの形を示す。
- sync-docs のテストの `CheckTreeHookTests`（16件）は、`--hook` の振る舞いを確かめる。同じ日に、次の11の部分をわざと壊し、どれもいずれかのテストが落ちることを確かめた。
  - コミットかどうかの判定
  - 道具の名前の判定
  - 宣言の有無の判定
  - 誤りがないときに何も出さないこと
  - 許可の判定を返さないこと
  - 件数の上限
  - `cd` による移動
  - `-C` による移動
  - 作業ツリーの根まで上る探索
  - `tree` のない壊れた設定に何も言わないこと
  - リポジトリの文字列を1行に切ること
- 独立したレビュー（読み取り専用のレビュー役）が、最初の版に7件の指摘をした。上の、`if` の範囲、ディレクトリの決め方、`tree` のない設定、文面、文字列の切り詰め、テストの前提は、その答えである。
- 確かめていないこと: Claude Code が `if` に従い、`additionalContext` を Claude に渡すこと。`install.sh` の後、新しいセッションで確かめる。

## 影響

- かかる時間（2026-11-14、macOS、このリポジトリで宣言なし）は次のとおり。
  - コミットでない git のコマンド1回あたり、約 0.16 秒。
  - コミット1回あたり、約 0.22 秒。
  - 宣言を一時的に加えて検査まで走ると、コミット1回あたり約 0.4 秒。
- Claude が警告を読むのは、コミットが済んだ後である。直しは次のコミットに入る。これは文書の記述（コミットは止めず、文脈は system reminder として渡る）からの推論である。
- 検査は作業ツリーのファイルを読み、ステージした内容は見ない。README を作ってもステージし忘れれば、このフックは通す。CI がそれを捕まえる。
- 対象は、Claude が Bash で行うコミットだけである。人のコミットは CI が受け持つ。
- 取りこぼす形がある。`bash -c "git commit"`、git の絶対パス、`--git-dir <path>` のように値を別の語で取るオプション、`then` や `{` の後の `git commit` である。警告だけのフックなので、取りこぼしても CI が受け持つ。
