# 0016. MCP サーバーと MCP 同梱プラグインをユーザー設定に取り込まない

## コンテキストと問題

`install.sh` は `~/.claude` を同期するとき、`.mcp.json` に載っている MCP サーバー（7件）もユーザースコープに登録し直していた。MCP サーバーを同梱するプラグイン（`github` / `deploy-on-aws` / `microsoft-docs`）もインストールしていた。`deploy-on-aws` を入れる判断は [ADR-0009](0009-adopt-deploy-on-aws-plugin.md) で決めたものである。

この構成には次の問題がある。

- インストーラーを実行したすべてのユーザーに、使わないサーバーの接続とツールが入る。`deploy-on-aws` の場合は、AWS へのデプロイ能力も入る。
- `uvx` と、任意の `GOOGLE_DEV_KNOWLEDGE_API_KEY` がインストールの前提になる。
- 再実行するたびに登録を削除して入れ直すので、ユーザーが自分で変えた同名サーバーの設定を上書きしてしまう。
- `.claude/skills/cloud-platform-research/SKILL.md` がサーバー名の表を持っていたため、スキルが特定のサーバーを前提にしていた。

## 決定

`install.sh` は MCP サーバーの登録・更新・削除を一切行わない。MCP サーバーを同梱するプラグインもインストールしない。どちらも必要なユーザーが自分で追加する。プラグインは `frontend-design` / `code-review` / `skill-creator` だけをインストールする。`.claude/` 配下のルールとスキルには MCP サーバー名を書かない。

ユーザーが自分で必要なものを選べ、インストールの影響範囲が同期対象のファイルとサーバーを含まないプラグインに限られるためである。これにより ADR-0009 を置き換える。

登録済みの MCP サーバーとインストール済みのプラグインは、削除しないで残す。以前のインストーラーが入れたものと、ユーザーが自分で入れた同名のものを区別できず、消すとユーザーの設定を壊すおそれがあるためである。

`.mcp.json` はリポジトリに残す。このリポジトリ内で作業するときのプロジェクトスコープ定義であり、ユーザーが自分で登録するときの参照カタログでもある。

### 結果

- 良い点: インストールに `uvx` と API キーが要らなくなり、前提は `claude` と `jq` だけになる。
- 良い点: デプロイ能力やサードパーティの接続が、ユーザーの選択なしに入らなくなる。
- 良い点: ユーザーが自分で調整した MCP の登録を、再インストールで上書きしなくなる。
- 悪い点: ドキュメント調査や AWS の構成図作成を使いたいユーザーは、README の手順に沿って自分でサーバーやプラグインを追加する手間が増える。
- 悪い点: 以前のバージョンで入った MCP サーバーとプラグインは、不要でもユーザーが自分で削除しない限り残り続ける。
- 悪い点: `cloud-platform-research` は、サーバーが入っていない環境ではライブのドキュメントを参照できない。その場合、未確認であることを明示して答える（スキル既存の手順）。

## 検討した選択肢

- **取り込まない（採用）**: 上記のとおり。
- **従来どおり全部取り込む**: 新規ユーザーは設定の手間がないが、使わない能力と前提コマンドを全員に課し、ユーザーの設定を上書きする問題が残る。
- **取り込まず、以前登録した分を再実行時に削除する**: 環境はきれいになるが、ユーザーが自分で入れた同名の設定まで消すおそれがある。
- **MCP サーバーだけ外し、MCP 同梱プラグインは残す**: `.mcp.json` の分は解決するが、プラグイン経由で同じ種類の接続とデプロイ能力が全員に入り続ける。

## 確認方法

`tests/run-install.sh` が次を検証する。

- 初回・2回目のどちらの実行でも `claude mcp` コマンドを実行しない。
- `github` / `deploy-on-aws` / `microsoft-docs` をインストールも有効化もしない。
- `uvx` がなくても前提チェックを通る。

`.claude/` 配下にサーバー名を書かないことは、自動チェックがなくレビューで確認する。
