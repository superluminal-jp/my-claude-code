# 0015. 設定階層を名前参照ではなく意味で結合する

## コンテキストと問題

Claude Code のプロジェクト設定には、常時読み込まれる頂点指示とルール、必要時だけ読み込まれるスキル、外部機能の接続定義がある。従来構成はこれらを一つの三層ツリーとして扱い、頂点がルール名を、ルールがスキル名を、中央ルーティング表が複数スキルの組合せを列挙していた。

この構成には三つの問題があった。

1. 頂点の直下に価値、作業時点、条件付きワークフロー、動的な外部機能台帳が混在し、同一の分類原理がなかった。
2. 親子や兄弟の設定ファイルが相互の名前と配置に依存し、改名・分割・削除の影響が別ノードへ波及した。
3. 常時ルールに Git 手順、外部ツール台帳、スキル組合せ表が入り、全セッションのコンテキストを消費しながら実態と重複・ドリフトした。

一方で、Git運用、クラウド公式資料の調査、複合スキルの適用順は失ってはならない。大きなスキルが所有する参考資料やスクリプトまで禁止すると、必要時ロードができず、単一ファイルへの重複と肥大化を招く。

## 判断の要因

- 頂点から具体手順まで、各階層が上位命題を論理的に支持すること。
- 同じ階層の要素が一つの分類原理で整理され、重複と欠落を説明できること。
- 各設定ノードを単独で理解、変更、移動、削除できること。
- 常時ロード量を減らし、条件付き手順を必要時だけ読み込むこと。
- 既存の安全、Git、クラウド調査、複合適用、文書同期の振る舞いを維持すること。
- 構文検索で検証できる独立性と、人が判断すべき意味的MECEを区別すること。

## 検討した選択肢

1. 現在の三層構造を保ち、兄弟参照だけを除去する。
2. 親から子への名前付き参照と中央ルーティング表を許可する。
3. すべてのリンクを禁止し、参考資料も各エントリーポイントへ埋め込む。
4. 条件付きのGit/MCPルールを単純に削除する。
5. 設定ノード間の名前参照をなくし、常時制約と条件付き手順を分離する。

## 決定

選択肢5を採用する。

### 頂点

頂点は「ユーザーの意図を、その統制下で前進させ、理解・検証・維持に十分な証拠を残す、信頼できる成果を届ける」という一つの命題を持つ。直下は同じライフサイクル基準で次の三つに分ける。

1. 正しい作業を定義する。
2. 統制下で実行する。
3. 検証可能で持続可能な成果として引き渡す。

### 常時ルール

常時ルールは、すべての関連作業に適用される品質条件だけを持つ。所有範囲は、要件確度、内部推論、権限と安全、外部表現、文書整合性の五つとする。各ルールは頂点の一つの枝だけを直接支持し、別ルールの判断や条件付きツール手順を所有しない。

Git協働とクラウド公式資料調査は条件付き手順として必要時ロードへ移す。中央ルーティング表は削除する。

### 条件付きスキル

スキルは二つの独立した選択軸で扱う。

- ライフサイクル操作: 要件化、実装、意思決定記録、文書の共同構築・診断・最終変換、Git協働、クラウド調査。
- ドメインoverlay: Scrum、デジタル庁React/Tailwindフロントエンド。

操作とドメインは意図的に交差する。各スキルの標準descriptionが自分の適用条件、除外境界、複合適用を自己完結して述べる。利用可能な全descriptionを評価し、独立に適合するものをすべて選び、依存順に適用する。

### 参照境界

独立した実行時設定ノードは、上位、下位、横の別ノードを名前またはパスで参照しない。親子関係はファイル参照ではなく、命題の抽象・具体関係で成立させる。

次は設定ノード間依存ではないため許可する。

- スキル自身が所有する参考資料、スクリプト、テンプレートへの相対参照。
- 一次資料、規格、公式文書への出典。
- 公開契約や意思決定記録を説明する成果物間の安定したリンク。

## 却下した代替案

- **兄弟参照だけを禁止する**案は、親から子への名前付き依存と異種ノード混在を残し、親を単独で理解できないため却下した。
- **下向き参照と中央ルーターを許可する**案は、発見情報を二重管理し、スキル追加や改名のたびに常時設定を変更するため却下した。
- **すべてのリンクを禁止する**案は、一次資料とpackage-owned resourceまで複製させ、必要時ロードと出典追跡を損なうため却下した。
- **条件付きルールを削除するだけ**の案は、既存のGit安全性と公式クラウド資料優先の振る舞いを失うため却下した。
- **全スキルを一つのMECEな兄弟群にする**案は、実装操作とドメイン制約が正当に重なる複合依頼を表現できないため却下した。

## 結果

- Positive: 頂点と各ルールは、別設定ファイルを開かずに理解・適用できる。
- Positive: 常時ロード対象は8ルールから5ルールへ減り、頂点を含む文量も20,126 bytesから14,317 bytesへ減る。
- Positive: 条件付き手順はdescriptionで発見され、本文とowned resourceは必要時だけ読み込まれる。
- Positive: Git、クラウド調査、複合適用、安全、文書同期の振る舞いを削除せず、適切な抽象度へ移す。
- Positive: 構造テストが名前付き依存、トポロジー、portable path、代表的な複合適用、常時ロード量を継続検証する。
- Negative: 同じ概念が複数ファイルで必要な場合、別ファイルへ委譲せず各ノードの責務内で短く自己完結して表現する必要がある。
- Negative: 二つのスキル軸の意味的な重複・欠落は検索だけでは証明できず、関係表とレビューが必要である。
- Negative: 外部機能の利用可否と認証状態は実行時に確認するため、静的文書だけでは利用可能性を断定できない。

## 確認方法

1. 頂点から設定パス、スキル名、コマンド名、外部サーバー台帳を検索し、0件であることを確認する。
2. ルールが5件だけで、設定参照と兄弟ファイル参照が0件であることを確認する。
3. authored skill のentry pointに上位設定パスがなく、package間の名前付き参照が0件であることを確認する。
4. package-owned link がpackage内で解決し、ハードコードされたインストール位置がないことを確認する。
5. ライフサイクル操作とドメインoverlayの関係表を人が確認し、代表的な単独・複合・非該当ケースを自動テストする。
6. 常時ロード量、既存テスト、installer同期、MCP起動、差分品質を確認する。
