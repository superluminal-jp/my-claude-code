# 常時ロード設定の設計方針

`.claude/CLAUDE.md` と `.claude/rules/` は、セッション開始時に無条件で読み込まれる。全プロジェクト・全セッションに課金される固定費であり、書けば書くほど良くなるものではない。本書は、それらのファイルが**なぜ今の形なのか**を記録する。

設定ファイル自体には、この種の説明を置かない。Claude の判断を変えない文はコンテキストを消費するだけだからである。本書は `.claude/rules/` の外にあり自動ロードされない。

## 1. 設定は強制しない。設定 *ファイル* が強制する

Claude Code は `CLAUDE.md` と `.claude/rules/` を **advisory（助言）** として扱い、`.claude/settings.json`（permissions、hooks）だけを**強制**する [1]。この区別は程度差ではなく種類の差である。

帰結として、原則をどれだけ巧く書いても保証にはならない。だから `CLAUDE.md` の各原則は「徳目」ではなく**観測可能な義務**として書かれている — transcript や diff で第三者が確認できる形。「正確であれ」は検証不能だが、「実行したコマンドと出力を示せ」は検証できる。検証できないものは当てにできない。

強制が必要な項目は設定側へ移してある。実例は3つある。ファイルツールに対する資格情報の読み取り拒否(経緯と受け入れた副作用は [ADR-0014](adr/0014-restore-credential-deny-rules.md))、Bash のコマンドを OS の制限で閉じ込めるサンドボックス、使わない MCP サーバーの拒否である([ADR-0020](adr/0020-enable-sandbox-by-default.md)、[ADR-0021](adr/0021-block-mcp-servers-by-settings.md))。hooks とガードレールスクリプトを全廃した経緯は [ADR-0005](adr/0005-remove-claude-hooks.md) と [ADR-0007](adr/0007-remove-scripts.md)。

例外として、`settings.json` の `SessionStart` フックが、条件に当たるセッションにだけ短い注意を文脈に足す(Bash ツールが zsh のとき、macOS のとき、aws CLI があるとき)。中身は §2 の問い「これが無いと Claude は間違えるか」を、会話記録とこのマシンでの観察で通したものに限る(zsh の3種類の誤り、サンドボックスの中の Chromium、サンドボックスの外に出る aws の書き方)。条件に当たらない環境では何も足さないので、ルールとして全セッションに課金しない。経緯は ADR-0020。

## 2. 常時ロードに残す判断基準

一文ごとに問う — **これが無いと Claude は間違えるか。**

間違えないなら消す。具体的には、次のいずれかに当たる記述は常時ロードに置かない:

| 分類 | 意味 | 例 |
|---|---|---|
| ネイティブ | モデルが既に知っている、またはクライアント自身の挙動 | Conventional Commits の文法、命令形、50/72 規則、権限の評価順 |
| ハーネス注入済み | セッション開始時に自動で文脈に入る | 全スキルの名称・説明・トリガー語句、MCP サーバーの `instructions` |
| 参照資料 | 判断ではなく裏取りに使う | 準拠規格の一覧、参考文献、ベンダー公式 URL |
| 設計説明 | なぜその形なのか | 本書の内容そのもの |

この基準は公式ベストプラクティスの「Claude が指示なしで既に正しくできることは削除するか hook に変換せよ」「self-evident な徳目は除外せよ」に対応する [2]。

## 3. ファイル別 — 何を意図的に置いていないか

### 3.1 常時ロードに残る4つのルール

各ルールは apex の3分岐（定義・実行・引き渡し）のうち正確に1つだけを支え、他のルールが既に持つ関心事は持たない。

| ファイル | 置いていないもの | 所在 |
|---|---|---|
| `CLAUDE.md` | スキル一覧 | ハーネスが全スキルの説明を注入する。手書きの列挙は重複であり、以前はスキル数が増えるたびにドリフトしていた |
| `CLAUDE.md` | `@.claude/rules/...` の import | `paths:` を持たないルールは無条件ロードされるため冗長 [1] |
| `CLAUDE.md` | ルール・スキル・コマンド・サーバーいずれの個別名 | apex は意味で子を支えるのであり、名指しで委譲しない。名指しすると、子の改名・分割・削除のたびに apex 自体が壊れる |
| `permissions.md` | 資格情報パスの列挙 | `settings.json` の `permissions.deny` が正本 |
| `permissions.md` | 部分一致をグロブ化しない理由 | [ADR-0014](adr/0014-restore-credential-deny-rules.md) |
| `clarifier.md` | 意図の共通認識を形成する手順、判断基準の接地先となる枠組みの在庫、曖昧性パターン目録、品質ゲート、出典 | `.claude/skills/clarifier/SKILL.md` と同パッケージの `references/` |
| `pyramid-principle.md` | Minto の4条件の詳述そのもの、構成の機械検査、および成果物を会話を見ていないサブエージェントに読ませる手順（spec 057） | `pyramid-structure` スキルが全タスク向けに持つ（spec 055 で取り込みプラグイン `minto-pyramid` を置き換えて `archive/minto-pyramid/` へ退避。従来の対話・診断・書き直し向け Minto スキル3件は `archive/minto-suite/` へ退避済み） |
| `thinking-lenses.md` | 4つのセルフチェック（依存と並行・条件と分岐・反復・推論）を出力へ強制する書式 | 自然な置き場がある成果物（`clarifier`/`coder` の Given/When/Then、Spec Kit の依存順タスクリストなど）にだけ表出させる |

残っているのは、いずれの分類にも当たらないもの — **非自明で、判断を変え、他のどこにも存在しない**記述だけである。

#### 補足 — `clarifier.md` とスキル `clarifier` は名前を共有するが責務が異なる

ルール `clarifier.md`（Requirements Certainty）が定めるのは、**いつコミットしてよいか**の判定基準である
——重大な結果ギャップが残るなら着手前に解消せよ、という常時適用の不変条件。一方スキル `clarifier` が持つのは、
**その解消をどう実行するか**の手順である——AIが理解を言語化して突き合わせ、名前のある枠組みから判断基準を引き、
合意を共通認識メモに残し、その後で形式的要件へ変換する二段構成。

名前が同じままこの乖離が生じたのは、[ADR-0015](adr/0015-rule-layer-independence.md) のルール層独立原則により、
ルールがスキルを名指しできず、スキル側の拡張に追随して改名する経路も持たないためである。乖離は受容するが、
読み手が「同名だから同じもの」と読まないよう、ここに明示する。ルールは判定、スキルは手順である。

### 3.2 常時ロードから条件付きスキルへ移した3ファイル

以前はルールが8ファイルあった。次の3件は全セッション共通のユニバーサルな判断基準ではなく、特定の作業が発生したときだけ必要な条件付き手順だったため、常時ロードの対象から外した。

| 旧ファイル | 移動先・置き換え先 | 理由 |
|---|---|---|
| `rules/git-workflow.md` | `.claude/skills/git-workflow/SKILL.md` | ブランチ・コミット・push・PR の作業は Git 協業が発生するときだけの条件付き手順で、全セッションに課金する理由がない |
| `rules/mcp.md` | `.claude/skills/aws-research/SKILL.md` | サーバー選択と AWS スキルレジストリ手順も、クラウド提供元の現行ドキュメントが要る条件付き調査であり、同様の理由で移した |
| `rules/skill-routing.md` | 削除（復元先なし） | 中央ルーティング表はスキルの `description`/`when_to_use` と重複する第二の状態で、スキル境界が変わるたびにドリフトしていた。apex 内の汎用マルチマッチ不変条件と、各スキル自身の記述に置き換えた |

移動した2件は、移動先スキル自身が「いつ呼ぶか」を `description`/`when_to_use` で自己記述する。削除した1件は、その自己記述の仕組みそのものに置き換わっている。経緯と却下した代替案は [ADR-0015](adr/0015-rule-layer-independence.md) にある。

### 3.3 廃止したルール

`rules/model-routing.md`（作業の単位ごとに、モデルの能力層と推論の労力を選ぶルール）は、利用者が不要と判断し、[spec 058](../specs/058-parent-skill-references/spec.md) で削除した。移動先はなく、戻すときは Git の履歴から復元する。

2026-11-07、利用者がトークン使用料の節約と処理の高速化を求めたため、サブエージェント（メインの会話から起動され、別の文脈で作業して結果だけを返す Claude）への委任の指示を、ルールのファイルではなく `.claude/CLAUDE.md` の「Execute under control」の1項目として加えた。削除した `rules/model-routing.md` は作業の種類ごとのモデルの選び方を広く並べていたが、新しい項目は委任してよい作業の条件と報告の形に絞り、次の3点を決めている。

- 委任する作業と渡す先を、種類で決める。出力の長い確認（テスト、ビルド、lint）、読み取り専用の検索、仕様の確定した同じ変更を多数のファイルに繰り返す作業の3種は `haiku`（小型で安価なモデルの別名）に、判断を要する独立した作業は `sonnet`（中位のモデルの別名）に渡す。ただし、指示文（サブエージェントに渡す作業の指示）を書くトークンが、メインの会話が自分で作業するトークンと同じくらいになるとき、例えば小さな変更1件や出力の短い確認は、メインの会話が自分で行う。委任には、指示文を書くトークンと、サブエージェントが空の文脈から始めてファイルを読み直すトークンがかかるためである。
- 判断、設計、コードレビュー、作業が完了したかの判定はメインの会話のモデルに残す。サブエージェントが確認のコマンドを実行してもよいが、実行した各コマンドとその終了コードを報告させ、失敗した出力は原文のまま引用させる。完了は、メインの会話のモデルがその報告から判定する。`haiku` が出力を誤って要約しても、メインの会話のモデルがその要約を根拠に完了と判定しないようにするためである。
- 利用者に求められるのを待たずに委任するよう、この項目で指示する。Claude Code の既定のシステムプロンプトは、利用者が求めない限りサブエージェントを起動しないよう指示している（2.1.319 で確認）。`.claude/CLAUDE.md` の指示はこの既定より優先されるため、この項目が既定を上書きする。`rules/model-routing.md` は委任するときのモデルの選び方を書いていたが、この既定を上書きする指示を持たなかった。

モデルは、エージェントの定義ファイル（`install.sh` が `~/.claude/agents/` へ同期する `.claude/agents/`）でなく、Claude が Agent ツールを呼ぶときに渡す `model` と `effort` の指定で選ぶ。定義を置けばモデルを確実に固定でき、確認だけをするエージェントから編集の道具を外せる。しかし利用者は、新しいファイルを置かない指示文だけの方式を選んだ。会話の記録に、`model` の指定なしに起動されてメインの会話と同じモデルで動いたサブエージェントが見つかったら、定義を置く方式に移る。

メインの会話の effort（推論の深さとトークンの消費量を決める段階。low, medium, high, xhigh, max がある）は、`.claude/settings.json` の `effortLevel` で `xhigh` に固定した。effort を課題ごとに自動で切り替える設定はなく、何も設定しないとモデルの既定値で動く（Opus 5.5 は `medium`）[4]。`effortLevel` は、利用者が `/effort` などでモデルごとに保存した段階（`modelSettings`）がないモデルにだけ効き、環境変数 `CLAUDE_CODE_EFFORT_LEVEL` やセッション中の指定はさらに優先される [4]。

サブエージェントのモデルは、呼び出しのときに渡す `model` の指定、エージェントの定義の `model` 欄、環境変数 `CLAUDE_CODE_SUBAGENT_MODEL`、呼び出し元の会話のモデルの順で決まり、先に挙げたものほど優先される [3]。

## 4. 番号ではなく名前で参照する

`CLAUDE.md` の原則は「Core Principle #3」のような番号ではなく **Traceability のように名前で** 参照する。原則を 1 つ足せば番号参照は全て壊れるためで、実際に Traceability は #3 から #4 へ動いた。`specs/` 配下の過去の記録は当時の番号のまま残してある（当時の事実の記録であり、遡及修正の対象ではない）。

## 5. 変更するとき

構成は `CLAUDE.md` を唯一の頂点とする独立ピラミッドとして保つ。各層は**意味**でのみ親の主張を支え、名前やパスで他ノードを名指ししない（唯一の例外は下の親スキル）。第2層は4個のユニバーサルルール（品質の関心事1つにつき1ファイル）、第3層は2つの独立した軸で自己記述するスキルである — ライフサイクル操作（意図の共通認識と要件化、問題定義、プロダクト戦略、実装、Git 協業、AWS 調査）と、ドメインオーバーレイ（Scrum、Digital Agency フロントエンド、Digital Agency スライド、セキュアロギング）。macOS アプリ連携の2件（`apple-notes`、`apple-reminders`）はどちらの軸にも分類していない。ドメインオーバーレイは一致するライフサイクル操作に**追加で**適用されるものであり、置き換えではない。第3層の分類がなぜルールへの1対1対応ではなく2軸なのかは [ADR-0015](adr/0015-rule-layer-independence.md) にある。

| 層 | 依存できる上位層 | 分類原理 | 許可する参照 | 禁止する参照 |
|---|---|---|---|---|
| `CLAUDE.md`（1件） | なし | ライフサイクル段階（定義→実行→引き渡し） | なし | ルール・スキル・コマンド・サーバーいずれの個別名も不可 |
| `.claude/rules/*.md`（4件） | `CLAUDE.md` | 品質の関心事1つにつき1ファイル | 外部一次情報源への引用 | 他のルールのファイル名・パス・それと分かる言及、スキルへの名指し |
| `.claude/skills/*/SKILL.md` | `CLAUDE.md` と、自身が支える品質の関心事 | ライフサイクル操作軸／ドメインオーバーレイ軸 | 自身のパッケージ内リソース（`references/`、スクリプト等）、外部一次情報源。親スキルに限り、自身の `SKILL.md` で宣言した子スキルの名前 | 他スキルへの名指し（親スキルが宣言した子を除く）・パス参照（親スキルから子へも不可）、`.claude/` 配下の絶対パスのハードコード、このリポジトリの `specs/` と `archive/` の参照(インストール先にないため。検査 SKILL-09) |

対象スキルは `tests/run-config-pyramid.sh` の `authored_skills` に列挙した12件で、この一覧が正本である — `clarifier`、`aws-research`、`verified-delivery`、`coder`、`digital-agency-frontend`、`git-workflow`、`requirements-decomposition`、`problem-definition`、`product-strategy`、`pyramid-structure`、`scrum-master`、`secure-logging`。このうち `git-workflow` と `aws-research` は §3.2 で常時ロードから移した先である。spec 036 の改訂時点の対象には `adr` と Minto スイート3件（`minto-builder`、`minto-reviewer`、`minto-rewriter`）も含まれていたが、いずれも `archive/` へ退避した（`adr` の規則は `maintaining-living-documentation` へ統合）。`meta-spec` も、利用者が不要と判断し、spec 058 で `archive/` へ退避した。自作スキルのうち `digital-agency-slides`、`apple-notes`、`apple-reminders` は現在この一覧に入っておらず、入れていない理由は記録されていない。ルール名とスキル名が同じ場合でも、子スキルを指す下向き参照は許可する。禁止するのは、同じ層にある別ファイルを指す横向き参照である。バンドルされたサードパーティ資料（DADS 参考資料一式など）、上流から取り込んだプラグイン（`hooks/hooks.json` を削除するローカル変更を加えた `maintaining-living-documentation`。`minto-pyramid` は spec 055 で退避）、Spec Kit の生成物はこの対象スキル一覧に含めない。

**親スキルは、宣言した子スキルを名前で参照できる**（[spec 058](../specs/058-parent-skill-references/spec.md)）。親スキルは、複数のスキルを決まった順序で適用する取りまとめ役のスキルである。`SKILL.md` に `## Child skills` 節を置き、子を1行に1つ「- `名前`」の形で宣言する。検査 SKILL-05 は、パッケージ内の Markdown が宣言した子以外の自作スキルを名指しすると失敗する。検査は次も確かめる: 子は `authored_skills` にあり、`SKILL.md` が存在する。子は自分の子を宣言しない（階層は1段）。親は自分を子として宣言しない。親も子をパスでは参照しない。親子の規則は、実在の親スキルがまだなくても働くよう、検査 PARENT-01〜10 が一時ディレクトリに作る架空のスキルに対しても確かめる。PARENT-09 と PARENT-10 は、コードブロックの中の例を宣言と読まないことを確かめる。親スキルとその子は `authored_skills` に入れる。入れないと検査されない。

この例外は、[ADR-0015](adr/0015-rule-layer-independence.md) が却下した「下向き参照と中央ルーターを許可する案」とは別物である。ADR-0015 の却下理由は2つあった。発見の情報（どのスキルをいつ使うか）を二重に管理すること、スキルの追加や改名のたびに常時ロードの設定を変えることである。親スキルはどちらにも当たらない。親スキルは常時ロードではなく、条件付きで読み込まれる。子がいつ呼ばれるかは、引き続き子自身の `description` が決め、親が持つのは自分の手順の中で子を使う順序だけである。子を改名して壊れるのは、その子を宣言した親だけで、検査 SKILL-05 がそれを見つける。ただし ADR-0015 の「参照境界」節（設定ノードは上位・下位・横の別ノードを名前やパスで参照しない）は、スキル層ではもう成り立たない。ADR-0015 の本文は変えていない。

同一階層にしかない情報が必要になったら、参照を足すのではなく、次のどちらかを行う。

1. そのファイル自身の判断基準として短く言い直す。
2. 複数の子が共有すべき内容なら、共通の親へ引き上げる。

設定ファイルに文を足す前に §2 の問いを通す。説明を書きたくなったら、それは本書か、対応する `docs/` の解説か、ADR に属する。新しいルールを作って設計理由を常時ロードさせない。

サイズの目安は公式指針の 1 ファイル 200 行未満 [2]。ルール群の合計はコミット履歴で追える。

この依存方向、対象範囲、却下した代替案は [ADR-0015](adr/0015-rule-layer-independence.md) に記録する。
