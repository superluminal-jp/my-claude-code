# ハーネスのゼロベース再構成案

状態: 実施済み（このブランチのプルリクエストとして提出、未インストール）。作成日 2026-11-10。ブランチ `refactor/harness-zero-base`（`main` の c272c2f から分岐）。§1〜§5 と §7 は、何も変更していない時点の検討結果である。§6 は提案で、そのうち §6.6 と §6.8 は実際に作ったものを記す。§8 は、利用者の決定と、それを実施した結果と、残っている作業を記す。

## 1. 要約: 作り直す対象は部品そのものではなく、部品の置き場所と大きさを決める規則である

現行のハーネスは、強制する設定・常時読み込む指示・必要時に読み込むスキルの3層と、「層どうしは名前ではなく意味でつなぐ」原則を保ったまま、次の5つの規則で組み直すのがよい。ここでハーネスは、`install.sh` が `~/.claude/` に入れる設定一式（`CLAUDE.md`、`rules/`、`skills/`、`agents/`、`settings.json`）を指す。

1. **指示の置き場所は、強制できるかどうかと、いつ必要かで決める。** 常時読み込む文は 18,073 字あり、その 17% は、現行の設計文書（`docs/claude-config-design.md`）が常時読み込みに置かないと定めた参考文献である。
2. **スキルの単位を「発動条件1つ・成果物1つ・完了確認1つ」と定義し、型ごとに既定の動かし方を決める。** 現行のスキルは大きさが不揃いで、たとえば `git-workflow` の本文は 463 語、`verified-delivery` の本文は 2,065 語あり、後者はそのうち 1,723 語が1つの段落に入っている。
3. **どの段階を踏むかは、変更のリスク区分（変更を high・medium・low に分ける分類）で決める。** 現行は「手順と検証を、複雑さ・可逆性・影響に比例させる」と1文で述べるだけで、文書構成のスキル `pyramid-structure` は「実質的な作業のすべて」で読み込まれる。
4. **サブエージェントは3つの条件（§6.4）に当たるときだけ使い、モデルと道具は定義ファイルで固定する。** サブエージェントは文脈を分ける代わりに多くのトークンを使う。この検討で使った調査用の5件は、合計 1,338,728 トークンを使って、合わせて約2万トークン（報告の語数からの概算）の報告を返した。
5. **費用と振る舞いの計測を、次の作業へ進む条件にし、スキルが参照する標準（ISO、OWASP などの規格や指針）を台帳（版と適用の仕方を記した一覧）で管理する。** 変更前の振る舞いの基準値（同じシナリオ集を3回実行した結果）はまだ取られていない。参照する標準は各スキルの本文と参照ファイルに散らばっていて、版を確かめる手順がない。

この案を示した後、利用者は次のとおり決めた: サンドボックスの中でも動くことを前提にする。スキルは破棄して、分割と統合を含めて作り直す。残りの決定は推奨どおりにする。Apple のアプリを操作する2つのスキルは削除する。これを受けて、配布元を `harness/` へ移し、スキルを 17 件から 16 件に作り直し、サブエージェントの定義を4件にし、テストと評価と README を付け替えた（§6.6、§8）。利用者の操作が要る作業が2つ残っている（§8.3）。

## 2. 前提: この案が使う用語と、成り立つ範囲

利用者の依頼は、現行のハーネスを分解して組み直し、次の4つを実現することである: 単位のそろったスキルとその組み合わせ、サブエージェントを使ったコンテキストとトークンの消費と応答の速さの最適化、成果物の品質と速さの両立、標準やベストプラクティスの参照と適用。

この案は、Claude Code 2.1.322 と、2026-11-10 時点の公式文書の記述を前提にする。対象は、このリポジトリが管理する個人のユーザースコープ設定（`~/.claude/` に置かれ、すべてのプロジェクトに効く設定）だけである。

| 用語 | この文書での意味 |

| 頂点の方針 | `.claude/CLAUDE.md`。常時ロードの最上位にある1ファイル |
| ルール | `.claude/rules/` の4ファイル。この案が定める5つの「規則」とは別のものである |

| プロンプトキャッシュ | 直前の要求と同じ先頭部分を再利用して、入力の費用と待ち時間を減らす仕組み |

## 3. 方法: 現物の計測、経緯の読解、公式文書と外部資料の調査を組み合わせた

結論は4種類の根拠に基づく。本文では根拠の種類を次の印で区別する。「私」は、この検討を行った Claude を指す。

- **[観測]** 私がこの作業ツリーで読んだ、数えた、実行した結果。
- **[出典]** サブエージェントが取得した資料の記述、またはサブエージェントの報告。番号つきの出典と報告の名前は付録C にまとめた。
- **[推論]** 上の2つから私が導いた判断。
- **[未検証]** 確かめていない点。

手順は次のとおりである。

1. 設定、インストーラ、設計文書、評価の仕組みと、17 スキルのうち 15 の `SKILL.md` を読み、字数と語数を数えた。読んでいないのは `apple-reminders` と `digital-agency-slides` である。
2. サブエージェント5件に、スキル同梱物の棚卸し、ADR 22 件と spec 約 70 件の経緯、Claude Code の拡張仕様、Anthropic の公開指針と Agent Skills 標準（スキルの形式を定める公開の仕様）、外部の実践・研究・標準を調べさせた。
3. 設計判断の根拠にする公式仕様8点を、別のサブエージェントに、公式文書を取得して再確認させた（本文で V1〜V8 の番号を付けた箇所）。
4. 変更前の記録として、オフラインで動くテスト 12 本を実行させた（付録B）。

限界は3つある。外部資料の大半はサブエージェントの要約であり、私自身は原文を開いていない。資料の多くは 2026 年に公開されたもので、私の学習時点より新しい。削減や分割の効果は、§6.5 の計測を行うまで仮説である。

## 4. 現状: 構造は健全で、弱点は費用と単位の不揃いにある

現行のハーネスは、強制と助言を分ける層の設計と、プログラムによる検査を既に持っている。弱点は7つあり、常時読み込む量、description、スキルの単位、手順の重さの決め方、サブエージェントの使い方、ハーネス自身の計測、effort の設定に分かれる（§4.3）。

### 4.1 現行の構成は、3つの層、サブエージェント1件、ハーネス自身の検証からなる

| 層 | 中身 | 量 [観測] |
|---|---|---|
| 強制（`settings.json`） | 資格情報の読み取り拒否 11 件、Bash の OS サンドボックス、使わない MCP サーバー（外部の道具を Claude につなぐ仕組み）の拒否、フック 4 件。フックはどれも、スクリプトのファイルを置かずに `settings.json` の中に直接書いたコマンドである | 122 行 |
| 常時ロード | 頂点の方針と 4 ルール（`clarifier.md`、`permissions.md`、`pyramid-principle.md`、`thinking-lenses.md`） | 5 ファイル、18,073 字（18,168 バイト） |
| スキル | 自作 17 件。ほかに Spec Kit が生成した 15 件と、公式プラグインのスキルがスキルの一覧に並ぶ | description 合計 12,150 字。同梱の実行ファイル（検査スクリプトとそのテストを含む）38 本・約 13,700 行 |
| サブエージェント | `read-only-reviewer`（読み取り専用、sonnet、xhigh） | 定義ファイル 1 件 |
| ハーネス自身の検証 | インストーラなどの契約のテスト、層の独立の検査、評価（26 シナリオ） | 47 ファイル、8,012 行 |

### 4.2 保つべき設計は4つある

- **強制と助言の区別。** `settings.json` だけが強制し、頂点の方針とルールは助言である、という区別（設計文書 §1）は、公式文書の説明と一致する。[出典 S10]
- **常時ロードの判断基準。** 「これが無いと Claude は間違えるか」（設計文書 §2）は、Agent Skills の作成指針の問いと同じである。[出典 S4]
- **意味でつなぐ層。** スキルは他のスキルを名指ししない。例外は、子を宣言した親スキルだけである（ADR-0015、spec 058）。
- **決定的な検査。** 要件グラフ、検証マニフェスト、文書構成、構成図の検査はプログラムが行い、モデルの自己申告を証拠にしない。

### 4.3 弱点は7つあり、いずれも数値か記録で確かめられる

**a. 常時ロードが、自分の判断基準を超えている。**

- 18,073 字のうち 3,058 字（17%）は、ルールの `## References` 節である。設計文書 §2 は、参考文献を「判断ではなく裏取りに使う」資料として常時ロードに置かないと定めている。[観測]
- `pyramid-principle.md` が 6,711 字で、全体の 37% を占める。[観測]
- 常時ロードの大きさの検査（層の独立の検査の項目 BUDGET-01）の上限は 20,126 バイトである。これは、ルールが8ファイルあった 2026-08-30 より前の大きさである。ADR-0015 は、同日の整理の後の大きさを 14,317 バイトと記録している。そこから現在の 18,168 バイトへの増加は上限の内側にあるので、この検査では検出されない。[出典: 経緯の調査、観測]
- このリポジトリの中で Claude Code を使うと、同じ5ファイルが2回文脈に入る。`~/.claude/` の写しはユーザースコープの設定として、リポジトリの `.claude/` はこのリポジトリのプロジェクトの設定として、それぞれ読み込まれるためである。この検討のセッションの文脈で確かめた。[観測]

**b. description が、Agent Skills 標準の上限と、発動条件という役割を超えている。**

- Agent Skills 標準は description を 1,024 字以下と定める。`clarifier` は 1,290 字で超えている。`secure-logging`（1,017 字）、`system-diagrams`（994 字）、`product-strategy`（965 字）は上限に近い。[観測、出典 S1]
- description の多くは、発動条件と除外のほかに、手順の要約と、他の部品との併用の指示を含む。手順の要約を含む description では、モデルが要約に従って本文を読まないことがあると報告されている。[出典 B1-4]
- スキルの一覧の予算はモデルのコンテキストの 1% で、超えると、使用の少ないスキルから description が落ちる。[出典 V2] この検討のセッションでは、スキルの一覧に description なしで並ぶスキルが 10 件あった。[観測] その原因が予算の超過かどうかは確かめていない。[未検証]

**c. スキルの単位が不揃いである。**

- `verified-delivery` の本文には 1,723 語の段落が、`requirements-decomposition` には 882 語の段落がある。[観測]
- `coder` は、テスト駆動開発、仕様駆動開発、変更の手順、文書同期、型安全、コード品質、セキュリティ、スタックの慣習の8つを1つの本文に持つ。文書同期は `maintaining-living-documentation` と、ログの扱いは `secure-logging` と重なる。[観測]
- 受け入れ基準を書く場所が4つある: `clarifier` の後半（合意を要件に変換する部分）、`requirements-decomposition` の要件グラフ、`coder` の仕様駆動開発の節、Spec Kit の `spec.md`。[観測]

**d. 手順の重さを決める定めが1文しかなく、重い手順が小さな作業にもかかる。**

- 頂点の方針は「手順と検証を複雑さ・可逆性・影響に比例させる」と述べるが、何をどの重さで行うかは定めていない。[観測]
- `pyramid-structure` の description は「MUST be used for every substantive task」で始まる。本文は、実質的な出力のたびに検査スクリプトを実行することと、成果物ごとに文脈なしの読み直しを行うことを求める。1回あたりの費用を計測した記録はない。この文書（約 490 行）に対する文脈なしの読み直しは、1回目が 115,430 トークン、2回目が 123,679 トークンを使った。[観測]
- 応答のたびに動く仕組みは、過去に2回外されている。spec 042 は、応答のたびにモデルを追加で呼ぶ Stop フックを、その費用を理由に削除した。`maintaining-living-documentation` の Stop フックは、誤って作業を止めた記録の後、2026-10-18 に外された。[出典: 経緯の調査]
- 6つの段階（根本原因の分析、解決策の選択、実行計画、アーキテクチャの決定、文書の共同作成、コードレビュー）に担い手がない。[観測: `docs/harness/capability-map.md`]

**e. サブエージェントの使い方が指示文だけで決まり、費用が大きい。**

- 頂点の方針は「求められるのを待たずに委任する」と定め、モデルは呼び出しのたびに引数で渡す。定義ファイルがあるのはレビュアーの1件だけで、それ以外の委任では、モデルも使える道具も固定されていない。[観測]
- 組み込みの検索用サブエージェント Explore は、今はメインの会話のモデルで動く。モデルを渡し忘れた検索は、小型のモデルではなくメインのモデルで動く。[出典 V5]
- Anthropic は、常設の委任の指示を、モデルが変わるたびに見直す項目に挙げている。[出典 S36]
- 保証レビューは1回あたり 85,000〜207,000 トークンを使い、spec 066・068・069 の3件で計 21 回行われた。[出典: 経緯の調査]

**f. ハーネス自身の検証が構造に偏っている。**

- 評価の仕組み（spec 066）はあるが、3回実行の基準値は、費用を理由に延期されている。[出典: 経緯の調査]
- `tests/` に専用のテストスクリプトがないスキルが 8 つある: `aws-research`、`clarifier`、`coder`、`git-workflow`、`problem-definition`、`product-strategy`、`scrum-master`、`apple-reminders`。評価のシナリオは `apple-reminders` を除く 7 つを対象にしているが、基準値がないので、結果はまだ記録されていない。[出典: 棚卸し、観測]
- CI（プッシュのたびに GitHub 上でテストを動かす設定）は、層の独立の検査と `tests/run-secure-logging-skill.sh` を実行しない。[観測: `.github/workflows/ci.yml`]
- 層の独立の検査が対象にするのは 17 スキルのうち 13 である。`apple-notes`、`apple-reminders`、`digital-agency-slides`、`maintaining-living-documentation` を外した理由は記録されていない。[観測、出典: 棚卸し]

**g. リポジトリの `settings.json` の `effortLevel` は、新規のインストールでは Opus 5.5 に適用されない。**

- リポジトリの `.claude/settings.json` は、メインの会話のモデルを opus（Opus 5.5 の別名）、`effortLevel` を xhigh と定め、`install.sh` がこれを `~/.claude/settings.json`（ユーザー設定）に入れる。設計文書 §3.3 は、メインの会話の effort を xhigh に固定する意図を記録している。[観測]
- 公式文書は、ユーザー設定の一番外側に書いた `effortLevel` が Opus 5.5 には適用されないと述べる。[出典 V1]
- 利用者のマシンでは、`modelSettings`（`/effort` で選んだ水準がモデルごとに保存される、ユーザー設定の項目）に xhigh が入っているので、意図どおり動いている。リポジトリの `settings.json` には `modelSettings` がない。[観測]

## 5. 根拠: 公式仕様と外部の知見は、同じ方向を指している

Claude Code の公式仕様、Anthropic の指針、外部の実践と研究は、5つの点で一致している。置き場所ごとに費用と強制力が違うこと、スキルはまとまった仕事を単位にすること、サブエージェントの効用は文脈の分離と並行にあること、検証はプログラムによる検査を先に置くこと、指示には強調より理由を書くことである。

### 5.1 仕組みごとに、文脈に入る時点と強制力が違う

次の表は、拡張仕様の調査（公式文書の要約）に基づく。V の番号を付けた項目は、別のサブエージェントが公式文書を取得して再確認した。原文の引用で確かめた点と、取得ツールの要約で確かめた点の別は、付録C に記した。

| 仕組み | 文脈に入る時点 | 強制力 |
|---|---|---|
| `settings.json` の拒否、サンドボックス、コマンドを実行する型のフック | 入らない（フックは出力を返したときだけ入る） | あり |
| 頂点の方針、`paths:` のないルール | 毎回の要求 | なし |
| `paths:` のあるルール | 一致するファイルを扱ったとき | なし |
| スキルの description | 毎回の要求。1スキル 1,536 字で切られ、全体はコンテキストの 1% [V2] | なし |
| スキルの本文 | 呼ばれたとき。圧縮（会話が長くなったときに行われる要約）の後は、スキルごとに先頭 5,000 トークン、合計 25,000 トークンまで再び添付される [V4] | なし |
| 前付けに `paths:` のあるスキル | 一致するファイルを扱うときだけ自動で読み込まれる [V3] | なし |
| 前付けに `disable-model-invocation: true` のあるスキル | 利用者が呼ぶまで入らない | なし |
| 前付けに `context: fork` のあるスキル、サブエージェント | メインの文脈には結果だけが入る | 使える道具の制限は強制される |

費用と速度に関わる、再確認済みの事実は次のとおりである。

- **モデルの切り替えはキャッシュを無効にする。** スキルの前付けの `model:` も切り替えにあたる。effort の変更は、Fable 5.1 以降、Opus 5.5、Sonnet 5.5、Haiku 5.5 ではキャッシュを保つ。[出典 V8]
- **サブエージェントは自分のキャッシュを持ち、既定の保持は5分である。** フォークは親のキャッシュを最初の要求から使う。[出典 V8]
- **サブエージェントのモデルは、呼び出しの引数、定義ファイルの `model`、環境変数、メインのモデルの順で決まる。** [出典 V6]
- **プラグイン（スキルやサブエージェントをまとめて配る単位）は、常時ロードの指示を配れない。** プラグインのサブエージェントは、定義ファイルの `hooks`、`mcpServers`、`permissionMode`（フック、MCP サーバー、権限の扱いを決める項目）を無視する。`tools`（使える道具）と `omitClaudeMd`（頂点の方針を読み込まない指定）が効くかは、文書に記述がない。[出典 V7、未検証]

この4点は、§6.2 と §6.4 の既定の根拠である。スキルの前付けではモデルを切り替えず、モデルを変えたい作業はサブエージェントに渡す。会話の履歴が要る副次的な作業には、親のキャッシュを使えるフォークを使う。

### 5.2 スキルの単位は「まとまった1つの仕事」であり、細かすぎても粗すぎても選択を誤る

- **公表されている目標は「まとまった仕事の単位」である。** 細かすぎると1つの作業で複数のスキルを読み込むことになり、粗すぎると正確に発動しない。[出典 S4]
- **スキルの数が増えると、選択の精度が下がる。** 1,141 スキル・15 モデルの測定では、精度はスキルの数の対数に比例して下がり、汎用的すぎるスキルが選択を奪った。[出典 B2-3]
- **スキルは助けにも妨げにもなる。** ベンチマーク SkillsBench（87 課題）では、手で整えたスキルが課題の合格率を 33.9% から 50.5% に上げ、構成要素（出典は modules と書く）が3つ以下の絞ったスキルが、網羅的なものより良かった。別の研究（Cheng ほか）では、スキルを与えると、モデルとエージェントの組み合わせによっては 36.78% の課題で成績が下がった。[出典 B2-2]
- **本文は 500 行、5,000 トークン未満にし、参照ファイルは本文から直接たどれるものだけにする。** 各参照ファイルに、読み込む条件を書く。[出典 S1、S3、S4]

### 5.3 サブエージェントの効用は文脈の分離と並行であり、答えの質ではない

- **Claude Code の公式文書は、サブエージェントが向く場合を4つ挙げる。** 独立した作業の並行、量の多い出力をメインの会話に入れないこと、独立したレビュアー、使える道具を絞ることである。答えの質は上がらないとも述べる。[出典 S10]
- **Anthropic の別の記事は、サブエージェントを残す条件を3つに絞る。** 文脈が大きくなることによる劣化が測れるとき、使い捨ての文脈で並行できるとき、道具の選択や指示が衝突するとき。[出典 S31]
- **費用は大きい。** エージェントはチャットの約4倍、複数のエージェントを使う構成は約15倍のトークンを使う。[出典 S18] 複数のエージェントを使うと、課題によって成績は +80.8% から −70.0% まで動き、順序のある作業では下がる。[出典 B2-7]
- **書き込みは1つのエージェントが行う。** 追加のエージェントは、読み取りと、判断の材料の提供を担う。Cognition 社の記述で、自社の報告である。[出典 B1-6]
- **サブエージェントの説明に費用を書くと、委任が約3分の1減り、課題の成功率は変わらなかった。** [出典 S36]

### 5.4 検証は、プログラムによる検査を先に置き、モデルによるレビューをリスクの高い変更に絞る

- **検査は2軸で分けられる。** 事前に導くもの（guides）と事後に確かめるもの（sensors）、プログラムが行うもの（computational）とモデルが行うもの（inferential）である。費用の小さい computational な sensor を毎回動かし、費用の大きい inferential なものは後の段階に置く。[出典 B1-1]
- **「テストが通った」は弱い証拠である。** 上位 30 のエージェントが解決済みとした修正の約5分の1は、意味の上で誤っていた。[出典 B2-5]
- **同じモデルによるレビューと、別のモデルによるレビューは、見つける誤りが部分的に違う。** 新しい文脈で動かした同じモデルのレビュアーと、別モデルのレビュアーの間で、見つけた誤りの数に有意な差はなかった。ただし、同じモデルのレビュー1件と別モデルのレビュー1件を組み合わせると、仕込んだ誤りの 56.7% を見つけ、同じモデルのレビュー2件では 42.7% だった。単著のプレプリントである。[出典 B2-6]
- **指示を変えるときは、評価の結果を採否の条件にする。** Anthropic は、応答の長さを制限する指示が評価の得点を 3% 下げた事例の後、システムプロンプトの変更ごとにモデル別の評価を行っている。[出典 S27] 別の記事は、ベンチマークの得点の差が 3 ポイント未満なら疑ってかかるべきだと述べる。[出典 S26]

### 5.5 現行のモデルには、強調より理由と範囲を書く

- **大文字や MUST の強調は、指示の過剰な適用を招く。** 例外を許さない指示は、フックか拒否の設定に置く。[出典 S10、S35]
- **指示に理由と範囲を書く。** 「決してしない」とだけ書いた指示のもとでは、利用者が承認した後でも、モデルがその操作を実行したのは約10回に1回だった。指示自体に「承認を得てから行う」と書くと、約10回に9回になった。[出典 S36]
- **古いモデル向けの指示は、モデルが変わるたびに外せるか確かめる。** Thoughtworks はこれを、regression testing（回帰テスト）と対にして progression testing と呼んでいる。[出典 B1-2]

## 6. 提案: 構成を5つの規則で組み直す

5つの規則は、置き場所（規則1）、スキルの単位と型（規則2）、段階の選び方（規則3）、サブエージェント（規則4）、計測と標準（規則5）を順に定める。スキルは、利用者の指示により、いったん破棄して作り直した（§6.6）。作り直したスキルは、サンドボックスの中で動くことを契約にしている（§6.8）。

### 6.1 規則1 — 指示は、強制できるかどうかと、いつ必要かで置き場所を決める

| 問い | 置き場所 |
|---|---|
| プログラムで判定でき、例外を許さないか | `settings.json`（拒否、サンドボックス、`settings.json` に直接書くコマンドのフック） |
| どの作業でも判断を変え、モデルが自分では導けないか | 常時ロード（頂点の方針と4ルール） |
| 特定の種類のファイルを扱うときだけ要るか | `paths:` つきのルール、または `paths:` つきのスキル |
| 特定の作業でだけ要る手順や知識か | スキル（本文は呼ばれたときに入る） |
| 利用者が明示して呼ぶときだけ要るか | `disable-model-invocation: true` のスキル |
| 読む量が多く、結果だけが要るか | `context: fork` のスキル、またはサブエージェント |

常時ロードについて、次の3つを行う。

1. **参考文献の節を、ルールから設計文書へ移す。** 3,058 字が減る。設計文書 §2 の判断基準をそのまま適用するだけで、判断を変える文は削らない。
2. **委任の項目を短くする。** モデルと effort の指定を定義ファイルへ移す（§6.4）。頂点の方針には、委任の条件と、「作業が完了したかはメインの会話のモデルが判定する」という定めだけを残す。
3. **それ以外の文は、外したときに振る舞いが変わるかを評価で確かめてから決める。** `pyramid-principle.md` の各文は、観測された誤り（spec 051〜057）に基づいて加えられたものなので、計測なしには削らない。
4. **このリポジトリの中での二重の読み込み（§4.3 a）を解消する。** 設定の `claudeMdExcludes`（読み込みから外す指示のファイルを指定する項目）を、このリポジトリのプロジェクトの設定に書く方法が考えられる。試していない。[出典: 拡張仕様の調査、未検証]

### 6.2 規則2 — スキルは「発動条件1つ・成果物1つ・完了確認1つ」を単位にし、型ごとに既定を決める

スキルを分けるか、スキルの中の参照ファイルにとどめるかは、次の基準で決める。

- **単独で頼まれる仕事か、別のスキルの手順が単独で必要とする仕事なら、スキルにする。**
- **ある条件のときだけ要る知識で、単独では頼まれないなら、スキルの中の参照ファイルにして、読み込む条件を書く。** `coder` の型安全の節がこれにあたる。
- **1つのスキルは、発動条件を 600 字程度までの description で書け、成果物と完了確認を1つずつ持ち、単独で評価できる。** 成果物は、そのスキルが作るか返すもの（オーバーレイでは判定の結果、監査では所見）である。完了確認は、終わったと言える条件である。600 字は、現行の平均（715 字）より短く、Agent Skills 標準の上限（1,024 字）に余裕を残す値として置いた、提案の目安である。[推論]

型は5つとする。`requirements-decomposition` の検査スクリプトが既に持つ役割の語彙（orchestrator、worker、auditor、checker）を広げて使う。

| 型 | 役割 | 動かし方の既定 | 現行の例 |
|---|---|---|---|
| 作業（worker） | 何かを作る、変える | メインの会話の中で動く | `coder`、`git-workflow`、`problem-definition` |
| オーバーレイ（overlay） | 作業の型のスキルに追加で適用する判断基準 | メインの会話の中で動く。対象のファイルが決まるものは `paths:` を付ける | `secure-logging`、`digital-agency-frontend`、`scrum-master` |
| 監査（auditor） | 読み取りだけで所見を返す | 読み取り専用のサブエージェントで動き、所見だけを返す | 保証レビュー、文脈なしの読み直し、文書とコードのずれの監査 |
| 連携（integration） | 外部のアプリを操作する | メインの会話の中で動く。副作用が大きいものは利用者が呼ぶ | `apple-notes`、`apple-reminders` |
| 親スキル（orchestrator） | 複数のスキルを決まった順で適用する | 子を宣言した親スキル。多数のファイルへ同じ作業を広げるときは、保存したワークフロー（スクリプトが複数のサブエージェントを決まった順で動かす Claude Code の機能） | `verified-delivery` |

検査スクリプト（checker）はスキルではなく、スキルと CI が呼ぶ部品として扱う。どの型でも、スキルの前付けの `model:` は使わない。モデルの切り替えはキャッシュを無効にするためである（§5.1）。モデルを変えたい作業は、サブエージェントに渡す。

各スキルの型、権限（読み取りのみ、作業ツリーへの書き込み、外部への作用）、受け取る成果物と渡す成果物を、前付けの `metadata` に宣言する。`metadata` は、Agent Skills 標準が定める任意の項目である。[出典 S1] この宣言から、2つのものを生成する。1つは、スキルどうしの関係を表すグラフである。`requirements-decomposition` の検査スクリプトが、監査の型のスキルが読み取り専用であることなどを、このグラフで確かめる。もう1つは、`docs/harness/capability-map.json`（`capability-map.md` の元になるファイル）の担い手の欄である。担い手の欄は今、各スキルの description が述べる受け持ちを、人が書き写して保守している。経緯の調査は、同じ内容を2か所に書いて食い違う問題を、このリポジトリで最も繰り返された問題に挙げている。宣言から生成すれば、書き写す箇所が1つ減る。[推論]

description には発動条件と除外だけを書き、手順の要約と、他の部品との併用の指示を外す。併用の定めは、頂点の方針が既に持っている。

### 6.3 規則3 — 踏む段階は、変更のリスク区分で決める

`verified-delivery` が既に定めるリスク区分を、すべての変更の始めに使う。区分ごとに必要な段階を次の表で定める。表の行は、`docs/harness/capability-map.md` の段階を6つにまとめたものである。表の中身は提案であり、合意の対象である。

| 段階 | 回答・調査のみ | low（局所的で戻せる変更） | medium（API、データの流れ、複数のモジュール） | high（認証、秘密、データ移行、権限、公開、戻しにくい変更） |
|---|---|---|---|---|
| 意図の確認 | 結果を変える不明点があるときだけ | 同左 | 同左 | 行う |
| 問題と要件 | 行わない | 完了条件を1文で書く | 問題カードと要件グラフ。challenger は、証拠が弱いときなどに行う | 問題カード、要件グラフ、challenger |
| 実装 | 行わない | 失敗する検査を見てから、最小の変更を行う | 同左を、要件グラフの葉ごとに行う | 同左 |
| 検証 | 根拠を示す | 検査の実行結果を示す | 検証マニフェストとゲート | 同左 |
| 独立したレビュー | 行わない | 行わない | 保証レビュー | 保証レビューと、人の承認 |
| 文書の同期 | 行わない | 影響がないことを明記する | 契約を説明する文書を更新し、レビューカードを渡す | 同左 |

medium と high の列は、現行の `verified-delivery` の定めを書き出したものである。medium を high と同じ記録で扱い続けるか、要件グラフを省くなどして軽くするかは、この表の合意の中で決める。軽くする場合は、ゲートの検査スクリプトの変更が要る。

受け入れ基準を書く場所は、要件グラフがある変更では要件グラフだけにする。この定めは `verified-delivery` と `coder` が既に持っており、`clarifier` の後半にも同じ定めを書く。

この規則が加える部品はない。行うのは次の3つである。

1. 頂点の方針の「比例させる」の1文を、リスク区分の語で書き直す。
2. 各スキルの description の発動条件に、どのリスク区分で使うかを書く。
3. 評価のシナリオに、区分ごとに「重い部品が使われないこと」の判定を足す。low についての判定は既にある（誤字の修正を頼むシナリオ `e-proportion-typo` が、`requirements-decomposition` が使われないことを確かめている）。

medium と high で子のスキルを決まった順に適用する役割は、現行どおり `verified-delivery` が担う。

担い手のない6段階には、失敗する評価が出るまでスキルを足さない。実行計画とコードレビューは、Claude Code に組み込まれた計画用のサブエージェント Plan と、公式の `code-review` プラグインが受け持つことを、`docs/harness/capability-map.json` に記録する。

### 6.4 規則4 — サブエージェントは3つの条件に当たるときだけ使い、定義ファイルで固定する

委任の条件を次の3つに限る。

1. **出力が長く、結果だけが要る。** テスト、ビルド、広い範囲の検索。
2. **互いに独立で、並行できる。** 複数の調査、複数のファイルへの同じ変更。
3. **書いた本人から独立した読み手が要る。** レビュー、文脈なしの読み直し。

この3つは、公式文書が挙げる4つの場合（§5.3）から、使える道具を絞ることを除いたものである。道具を絞ることは、定義ファイルが受け持つ。

役割ごとに定義ファイルを置き、モデル、effort、使える道具を固定する。役割の名前は仮のものである。

| 役割 | 条件 | モデルと effort | 使える道具 |
|---|---|---|---|
| 検査を実行する役 | 1 | haiku、low | Bash と読み取り。各コマンドと終了コードを報告し、失敗した出力を原文で引用する |
| 検索する役 | 1、2 | haiku、medium | Read、Grep、Glob |
| 独立した作業を行う役 | 2 | sonnet、xhigh | 作業に必要なもの |
| レビュアー（現行の `read-only-reviewer`） | 3 | sonnet、xhigh | Read、Grep、Glob |

設計文書 §3.3 は、モデルを指定せずに起動されたサブエージェントが会話の記録に見つかったら、定義ファイルを置く方式に移ると定めている。その例はまだ見つかっていない。それでも今移すことを提案する理由は2つある。Explore がメインのモデルで動くようになり、渡し忘れたときの費用が大きくなった。定義ファイルは、指示文と違って、使える道具の制限を強制できる。[推論]

各定義ファイルの説明には、起動の条件と、費用がかかることを書く。同じファイルへの書き込みを、複数のサブエージェントに並行させない。会話の履歴が要る副次的な作業には、フォークを使う。

### 6.5 規則5 — 計測を次の作業へ進む条件にし、標準を台帳で管理する

**計測。** 変更の前後で、次の3つを同じ条件で取る。変更の前の結果が基準値である。

| 測るもの | 手段 |
|---|---|
| 費用: 常時ロード、スキルの一覧、スキルごとの本文のトークン | Claude Code のコマンド `/context all`（文脈の内訳を表示する）と `/skill-doctor`（スキルごとの費用と使用回数を表示する） |
| 振る舞い: 期待した部品が選ばれ、約束した振る舞いをするか | 既存の評価。スキルごとに、発動すべき依頼と、紛らわしいが発動すべきでない依頼を 8〜10 件ずつ足す（以下、発動の依頼集） |
| 検査が実際に働くか | 各検査スクリプトに、既知の違反を1つ入れた入力を与え、検出することを確かめる |

**標準の台帳。** スキルが参照する標準（ISO、OWASP、WCAG など）を、スキルごとの参照ファイルに「名前、版または日付、URL、適用の仕方」の形で書き、そこから全スキル分の標準の一覧を生成する。適用の仕方は、スクリプトで検査する、チェックリストで確認する、参考にとどめる、の3つである。適合を主張するのは、検査できる証拠があるものだけにする。この定めは、`maintaining-living-documentation` が既に持つ定めと同じである。版の更新を確かめる手順は、利用者が呼ぶスキルにする。新しく取り入れる候補は付録A に挙げた。

Agent Skills 標準への適合（名前、description の長さ、参照ファイルの深さ）は、標準が提供する検査コマンド `skills-ref validate` をテストに加えて確かめる。[出典 S1]

CI は、リポジトリにあるオフラインのテストをすべて実行するようにする。層の独立の検査は、17 スキルすべてを対象にするか、外すスキルについて理由を記録する（§4.3 f）。

### 6.8 サンドボックスの中で動くことを、スキルの契約にする

## 7. 考察: この案の効果は計測前の仮説であり、成り立たなくなる条件が5つある

- **削減の効果を測っていない。** 常時ロードと description の縮小が振る舞いを保つか、速度がどれだけ変わるかは、§6.5 の計測で初めて分かる。評価を3回実行しただけでは、得点の小さな差を区別できない。
- **モデルによって結論が変わる。** Anthropic の文書は、Opus 5（出典の表記）が指示なしに自分の作業を検証し、Sonnet 5.5 は低い effort で検証を省くことがあると述べる。[出典 S37、S38] 検証やレビューの段階をどこまで求めるかは、使うモデルと effort ごとに確かめる必要がある。
- **`paths:` つきのスキルの挙動を確かめていない。** 公式文書は「一致するファイルを扱うときだけ自動で読み込む」と述べる。[出典 V3] 対象のファイルがまだない新規の作成で発動するかは未検証である。
- **スキルを細かくすると逆効果になりうる。** スキルの一覧が長くなり、選択の誤りが増える。§6.2 の基準は、分割より参照ファイルへの移動を先に選ぶためのものである。
- **外部資料の確度に幅がある。** Cognition の記述は自社の報告である。レビュアーの独立性の研究は単著のプレプリントである。

退けていない別の説明が1つある。利用者が求める応答の速さを下げている主な要因が、ハーネスの構成ではなく、effort の xhigh である可能性である。xhigh は利用者が 2026-11-07 に選んだ設定で、この案は変更を提案していない。effort を変えて同じ評価を実行すれば区別できる。ただし、評価の仕組みは今は effort を渡せない（`docs/harness-eval.md` §4 の5）。環境変数 `CLAUDE_CODE_EFFORT_LEVEL` は最も優先されると公式文書にあるので、評価の実行時にこれを設定する方法が考えられるが、試していない。[出典 V1、未検証]

### 8.2 オフラインのテスト 14 本は通っている。確かめていないことが4つある

結果は付録B 補足にある。古い `.claude/skills`、`.claude/agents`、`.claude/settings.json` は、利用者が削除した。サンドボックスがこの3つへの Bash からの書き込みを止め、サンドボックスの外での実行は自動承認の判定で拒否されたためである。`tests/run-removed-guardrails.sh` の検査 SRC-01 は、このリポジトリの `.claude/` に配布元のファイルが残っていないことを確かめる。空のディレクトリは数えない。Git は空のディレクトリを追跡せず、Claude Code 自身が `.claude/` の下に空の作業用ディレクトリを残すためである。

- **新しいスキルの実際の振る舞い。** 契約の検査が確かめるのは形である。スキルが正しく選ばれ、約束どおりに振る舞うかは、評価を実行するまで分からない。
- **サブエージェントの定義が意図どおりに使われるか。** 定義はまだインストールしていない。評価は、サブエージェントの起動を許していないので、これを観測しない。
- **ブラウザを使うスライドのテスト。** 検査用のブラウザを導入していないので、3項目が飛ばされた。
- **MCP サーバーの起動のテスト。** ネットワークが要るので、実行していない。

### 8.3 利用者の操作が要る作業は2つある

1. **プルリクエストのマージと、`install.sh` の実行。** どちらも依頼があるまで行わない。`install.sh` を実行すると、`~/.claude/skills/` の旧 17 スキルは新しい 16 スキルに置き換わり、`~/.claude/agents/` は4件になる。
2. **評価の基準値の取得。** 2026-11-07 の試行では、20 件で $6.03、1件あたり約 $0.30 だった（`docs/harness-eval.md`）。同じ単価なら、27 シナリオを3回で約 $24 になる。[推論] Claude の定額プランで動かす場合は、金額ではなく、5時間ごとに決まる利用量の上限を消費する。スキルの名前が変わったので、変更の前後を同じシナリオで比べることはできない。新しい木に対する基準値を取り、以後の変更と比べる。

提案が1つある。配布元を `harness/` へ移したことと、スキルを作り直したことは、構造を変え、戻しにくく、退けた代替案（`.claude/` に置き続ける、スキルを保ったまま整える、プラグインに分ける）がある。決定記録（ADR）を作る条件に当たる。作るかどうかは利用者が決める。

後に回した作業は3つある: スキルの一覧を設定で絞ること（使用の記録が取れてから）、スキルの中にあった評価の資料の作り直し、標準の台帳（§6.5）と付録A の候補の採否。
