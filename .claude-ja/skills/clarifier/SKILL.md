# 共通認識の形成、その後の形式的要件化

二段構成であり、順序を持つ。

**第1段 — 意図の共通認識**。AIがユーザーの意図をどう理解したかを、ユーザーが却下できる形で述べる。ケースの一覧ではなく判断基準で収束させる。

**第2段 — 形式的要件化**。合意を検証可能な要件へ変換する。

第2段は**第1段が成立した後にのみ**適用する。誰も確認していない解釈を形式化しても、間違った対象について精密な要件が得られるだけである。

## 発動条件

ユーザーが明示的に求めた場合、**または**次の齟齬の兆候が少なくとも一つ成立した場合に起動する。

1. ユーザーが直前の成果物を否定し、やり直しを求めた。
2. ユーザーが同一の論点を2回以上言い直した。
3. AIの要約・復唱にユーザーが訂正を入れた。
4. 新しい指示が既存の合意内容と矛盾する。
5. 依頼に対して実質的に異なる2つ以上の解釈が成立し、どちらでも作業が進んでしまう。

いずれも成立せず、ユーザーの要求もない場合は**起動しない**。認識可能な成果物やワークフローを指し示す短い依頼は、簡潔であるという理由だけでは曖昧とみなさない。

## 第1段 — 意図の共通認識

### 1. 理解を述べる。尋ねるのではない

AIの理解を、ユーザーが却下できる言葉にする。依頼の言い換えではなく、これから何を作るのかの記述であり、間違っていると判定できる程度に具体的であること。

次は**分離して**提示する。混在させてはならない。

| 区分 | 内容 |
|---|---|
| AIの理解 | 何を作ろうとしているか |
| 前提 | それぞれに確信度（高・中・低）を付す |
| スコープ外 | 明示的に扱わないもの |
| 未解決点 | 未決の事項と、それが何を変えるか |

ユーザーの訂正または承認を得るまで、対象作業の実装に着手しない。ただしユーザーが確認を明示的に拒否した場合（「いいから作って」）は、採用した解釈を前提として明示したうえで進む。

そもそもなぜ復唱するのかの根拠は設計根拠層の群F（`references/design-basis.md`、英語版）にある。設計根拠層のうちユーザーに名指ししてよいのはこの群だけであり、しかもAI自身の復唱の理由としてのみである。ユーザーの内心についての断定に用いてはならない。

### 2. ケースの一覧ではなく判断基準を提示する

何が該当するかを決める**判断基準（内包）**を述べる。ケースを一つずつ確認して意図を推し量ってはならない（外延）。

- 判断基準は、ユーザーが反例を挙げられる具体性で述べる。「適切に処理する」は反証できないため提示とみなさない。
- **質問してよいのは、AIが原理的にアクセスできない事項に限る**。ユーザーしか知らない事実、同等に妥当な選択肢の間の選好、外部の制約や期限。
- **解釈・境界・既定値は質問してはならない**。候補を提示し、却下を待つ。尋ねることは、AIができる作業をユーザーに差し戻すことである。

この違いは収束に効く。判断基準への一回の訂正は無数のケースを同時に正すが、ケースへの一回の訂正は一つのケースしか正さない。

### 3. 判断基準を名前のある枠組みに接地する

各判断基準は適用在庫（`references/applied-frameworks.md`、英語版）の名前のある実践・標準・枠組みから引き、それが生んだ判断に添えて名前を示す。

- **群単位で選ぶ**。ギャップの種別が群を決め、群の中では判断基準を最も直接に生成できるものを採る。平坦な一覧から選ばない。
- **一回の提示で名指しは最大2つ**。それを超えると読む負荷が上がり、枠組みの提示自体が目的のように見えはじめる。
- **名前は判断に添えてのみ示す**。枠組みを単独で提示せず、適用前に解説しない。
- **実際にその判断を支持している場合にのみ名指しする**。得ていない権威を借りるための名指しは、この規律が防ごうとしている当のものである。
- **在庫に該当がなければ、その旨を述べる**。確立した枠組みが存在しないこと、判断基準がAI自身の推論に基づくことを明示する。手近な枠組みにギャップを押し込まない。

名指しは二つのことを同時に行う。判断基準をこの会話の外にある情報源に照らして検証可能にすること、そしてユーザーが学習に時間を割かずに語彙を獲得できるようにすることである。後者は前者の帰結であり、別個の機能ではない。

この振る舞いを規定する理論は設計根拠層（`references/design-basis.md`、英語版）にある。群E・群G はユーザーに名指ししない。群F は上記の制限下でのみ。

### 4. 突き合わせは3往復を上限とする

訂正の往復は最大3回。収束しない場合は、収束していない事実と残る解釈候補を提示し、ユーザーの選択に委ねる。

この上限は恣意的な打ち切りではない。判断基準で進めている限り一回の訂正が多数のケースを同時に正すため、収束が期待される振る舞いである。したがって3往復で収束しないことは判断基準の側の兆候——反証可能でないか、ケースとして述べてしまっている——であり、4回目を足す前に基準の立て方を見直す。

### 5. 齟齬で起動した場合は、まず分岐点を特定する

否定されたのと同じ理解のまま成果物を作り直してはならない。適用在庫の群Cを用いて、二つの理解がどの段で分かれたか——選択したデータ、与えた意味づけ、置いた前提——を特定して述べる。再着手はその後である。

AIは自身の分岐を常に検知できるわけではない。上記の兆候は観測可能な代理指標であって保証ではない。したがってユーザーによる明示要求という経路は常に開いておき、冗長なものとして扱ってはならない。

### 6. 合意を記録する

合意が成立したら、**単一の自己完結したメモ**を次の順序で書く。

1. 依頼の要旨（ユーザーの言葉のまま）
2. AIの理解
3. スコープ（含む／含まない）
4. 前提（確信度付き）
5. 観測可能な完了条件
6. 未解決の論点とリスク

**保存先**。プロジェクトが番号付き `specs/<N>-*` 規約を採用していれば、その中の `shared-understanding.md`。採用していなければ `docs/shared-understanding/<slug>.md` のようなプロジェクトに適した既定の場所。

**記述言語**。メモは対話で使われている言語で書く。枠組みの名前と出典は原語のまま残す——訳語にすると出典との照合ができず、ユーザーが原典に到達できなくなる。

**自身が作成していないファイルへ書き込んだり変更したりしてはならない。**

上記で解決したパスに**既にメモが存在する場合**は、上書きか新バージョン保存かを確認する。同一性はパスの一致で判定し、内容の類似度では判定しない——閾値が恣意的になり検証できないためである。

**合意成立前にセッションが終了した場合**は、収集済みの内容を未完成である旨を明示したドラフトとして保存する。破棄しない。

## 第2段 — 形式的要件化

第1段の成立後に適用する。ここでの作業集合は適用在庫の群Dである。

### フラグを立てるべき曖昧さのパターン

- **曖昧な数量表現**: 「速く」「たくさん」「多くの」「すぐに」「堅牢な」「スケーラブルな」「使いやすい」 -> 数値＋単位を要求する。
- **未定義の代名詞・スコープ**: 「それ」「システム」「すべて」 -> 対象を明確に名指しする。
- **隠れた複合要件**: 複数の要件を束ねた「〜と〜」「〜または〜」を含む記述 -> 分割する。
- **暗黙の主体・トリガー**: 「必要に応じて」「自動的に」 -> 主体、イベント、前提条件を明示する。
- **要件への実装の混入**: 問題の合意より先に解決策が指定されている -> *何を*と*どうやって*を分離する。
- **肯定形のない否定**: 「遅くしないこと」 -> 測定可能な肯定形（「p95 < 200ms」）で言い換える。

### 引き出し（エリシテーション）ツールボックス（選択的に使用）

- 欠けている次元に対して5W2H。
- 測定可能な目標に対してSMART。
- ユーザーストーリーの品質に対してINVEST。
- テストシナリオに対してGiven/When/Then。
- スコープの優先順位付けに対してMoSCoW。
- 非機能要件に対してFURPS+。
- 要件文や品質目標により厳密な形が必要な場合に EARS、Volere の fit criterion、Planguage。

### 品質ゲート

実装に進む前に、各要件は次を満たしているべきである。

- 曖昧でないこと、
- 実現可能であること、
- 検証可能であること、
- 矛盾がないこと、
- 見積もりが可能な程度に範囲が定まっていること。

### 確認事項のテンプレート

```text
Blocking gaps:
1) <dimension>: <question>
   Default: <X>
   Alternative: <Y>
   Impact: <reversible/irreversible, scope>

Assumptions if proceeding:
- <assumption> (confidence: high/medium/low)
```

## 恒久的ユーザーモデル

今回の依頼が終わった後も有効な事実が現れたら、記録の候補として**提案する**。書き込みはユーザーの明示的な承認を得た後にのみ行う。

プロジェクトごとに1ファイル、`docs/shared-understanding/user-profile.md` に保持する。記録済みの内容と矛盾する新事実が現れた場合は、矛盾を提示し、現在有効な方を確認したうえで更新する。

**記録してよいのは、作業の進め方に関する事実のみ**——好む粒度、確認の頻度、使う語彙、成果物の形式の選好など。

**記録してはならないもの:**

1. 能力や習熟度の評価（「〇〇に不慣れ」等）。
2. 業務上の機微（未公開の計画、契約、組織の内情）。
3. 第三者に関する記述。

制限が承認だけでなく記録対象そのものに掛かるのは、このファイルがコミットされ、リポジトリを閲覧できる全員に永続的に可視となるためである。承認は承認時点の判断しか担保せず、永続的な可視性はそれを超えて残る。

## エッジケース

| 状況 | 対応 |
|---|---|
| 依頼が単一解釈しか許さない | 起動しない。作業へ進む |
| 合意成立前にセッションが終了した | 未完成マーカー付きドラフトとして保存する。破棄しない |
| 解決したパスにメモが既に存在する | 上書きか新バージョンかを確認する。サイレントに決定しない |
| ユーザーが確認を拒否した（「いいから作って」） | 突き合わせを打ち切り、採用した解釈を前提として明示して進む |
| 一つのギャップに複数の枠組みが該当する | 群を先に選び、その中で最も直接に判断基準を生成できるものを採る。名指しは最大2つ |
| 同じ枠組みを何度も適用してきた相手である | 名指しを維持する。習得済みかどうかは観測できず、名前を省くと判断を支持しているかの検証が失われる |
| 3往復しても収束しない | 収束していない事実と残る解釈候補を提示し、選択をユーザーに委ねる |

## アンチパターン

- 複数の解釈が成り立ちうる場合に、黙って一つの解釈を選ぶこと。
- 作業が終わった後で尋ねること（「Xを作りましたが、これで合っていますか？」）。
- ケースを一つずつ確認し、それらを決める判断基準を述べないこと。
- AIが提案できたはずの解釈・境界・既定値を、ユーザーに供給させること。
- 一括で確認せずに、ターンごとに確認事項を積み重ねること。
- 「もっと良くして」のような重大に曖昧な依頼を、合意されたフィット基準なしに実行可能なものとして扱うこと。
- 十分に定義された成果物の依頼を、一般的な要件ヒアリングへとそらしてしまうこと。
- ユーザーが同意していない受け入れ基準を作り出すこと。
- 実際には支持していない枠組みの名前を判断に添えること。
- 枠組みを適用せずに解説すること。

## 枠組みの索引

| 層 | 群 | ユーザーに名指しするか |
|---|---|---|
| 適用在庫（`references/applied-frameworks.md`、英語版） | 群A 接地の確認 ・ 群B 意図の渡し方 ・ 群C 分岐点の特定 ・ 群D 要件の記述と検証 | する——生んだ判断に添えて、一度に最大2つ |
| 設計根拠層（`references/design-basis.md`、英語版） | 群E 学習の設計 ・ 群F 復唱が必要な理由 ・ 群G 協調の理論 | しない——ただし群F はAI自身の振る舞いの理由としてのみ可 |
