目的: コード、設定、テスト、スクリプト、インターフェース、観測可能な振る舞いを安全に変更する。実装前に「何を」「なぜ」変更するのかを定義し、自動化可能な契約については失敗する自動チェックを、そうでない場合は変更前の具体的な観測記録を確立し、事実に基づく契約ドキュメントを同期し、システム境界の安全性を保つ。これらの責務は、別の独立して適用可能な能力がドメイン固有・成果物固有のガイダンスを提供する場合でも変わらない。セキュリティはOWASP Top 10 / OWASP ASVSおよびCWEを意識した欠陥対応に基づく。

# テスト駆動開発（TDD）

変更された契約が自動的にチェックできる場合は必ずレッド→グリーン→リファクタを用いる。実装前に、決定的なチェックを追加または特定し、それを実行して想定どおりの失敗を観測する。自動化できない変更については、編集前に現状の具体的な振る舞いや構造を記録し、意図した変更をどのように検証するかを定義する。

- テストは自動化可能な契約を定義し、実装がそれを満たす。関連するチェックが通過するまでは完了とみなさない。
- テストが書きにくい場合はそれ自体が設計上のシグナルである。テストではなくインターフェースを修正する。
- テスト名は実装ではなく振る舞いを説明する（例: `user_cannot_login_with_invalid_password`）。
- 現実的な範囲で1テストにつき1アサーションとする。複数のアサーションは1つの論理的な結果を検証する場合にのみ許容する。
- 決定的であることのみを許容する — 乱数や時刻はモックする。
- テストスイートを通すために失敗しているテストを削除・無効化してはならない。根本原因を修正する。
- 意味のあるアサーションができない文章、ポリシー、構造については、結果を変更前に記録した観測と比較し、定めたレビューを実施する。TDDを名乗るためだけに壊れやすいトークン存在チェックのテストを作成してはならない。

# 仕様駆動開発（SDD）

仕様は、機能が*何を*行い*なぜ*行うのかについての唯一の信頼できる情報源である。コードは仕様を満たし、ドキュメントは現在のコードを説明する。

- 観測可能な振る舞いを追加・変更する場合、仕様なしに実装作業を行ってはならない。些細な内部リファクタリングについてはTDDのみで十分である。
- 仕様は**何を**と**なぜ**のみを定義する — 技術やフレームワークの選択は仕様に含めない。
- 受け入れ基準は検証可能でなければならない（Given/When/Then、または測定可能な`SC-001…`形式）。仕様から失敗するテストを書けない場合、その仕様はまだ曖昧である — コーディング前に明確化する。
- 乖離が生じた場合は実装を修正する — ただし仕様自体が誤っている場合は作業を止めてユーザーに提示する。壊れたコードに合わせて仕様を黙って編集してはならない。
- 実装によって仕様のギャップが明らかになった場合 → そのギャップを文書化し、埋める前に確認を取る。

SDDとTDDは組み合わさる: 仕様が振る舞いを定義し、テストがそれを強制し、実装が両方を満たす。

プロジェクトがすでに[github/spec-kit](https://github.com/github/spec-kit)を使用している場合は、簡略化した代替手順を即興で行うのではなく、導入済みの仕様策定・計画・タスク・整合性分析・実装のライフサイクルに明示的に従う。

# ドキュメント同期

変更された公開インターフェース、振る舞い、設定項目、スキーマ、利用契約それぞれについて正典となる説明箇所を特定し、**同じ変更の中で**更新する。

- 計画や経緯ではなく、コードが**現在**何を行うかを記述する。掲載する例は現在のコードベースに対して実際に動作するものでなければならない。
- ドキュメント更新の代わりにTODOコメントを使わない。
- 完了を報告する前に、影響を受ける契約ドキュメントが事実として整合していることを確認する。古くなった成果物を認可された作業範囲内で更新できない場合は、それを明示的に指摘する — 黙って誤ったままにしない。

## トリガー

| コードの変更 | 更新すべきドキュメント |
|---|---|
| CLIフラグまたは環境変数の追加・削除 | README の使用方法、`docs/configuration` |
| APIエンドポイントまたはシグネチャの追加・変更 | `docs/api` またはインラインのdocstring |
| デフォルトの振る舞いの変更 | README、マイグレーション/changelog |
| 新規依存関係またはインストール手順の追加 | README の前提条件 / セットアップ |
| 機能の非推奨化 | README + インラインの非推奨通知 |

# 型安全性

静的型付けまたは漸進的型付けをサポートする言語（例: TypeScript、型ヒント付きPython、Go、Rust、Swift、Kotlin、Java、C#）を使用している場合に適用される。後述の「言語・スタックの規約」と組み合わさる — リポジトリの既存の型付け規約に合わせ、新しい型システムを導入したり、触れていないコードに注釈を付けたり、合意されたタスクを超えて無関係な型付けリファクタリングを行ったりしない。

- **公開インターフェースに注釈を付ける**: 新規または変更された公開関数、エクスポートされる値、クラスメンバーには、プロジェクトの既存の規約に沿った明示的な型注釈を付ける。変更が型付けされたインターフェースの入力または出力を変える場合は、実装だけでなく、同じ変更の中で注釈も更新する。
- **デフォルトで安全でない回避策を使わない**: 型チェックエラーが発生した場合は、`any`、包括的なキャスト、抑制コメント（`# type: ignore`、`@ts-ignore`）、非nullアサーションに頼るのではなく、根本にある型の不一致を修正する（絞り込み、正しい型付け、小さなリファクタリングなど）。回避策が本当にやむを得ない場合（型定義のないサードパーティライブラリなど）は、理由を1行のコメントで記し、そのトレードオフをユーザーに提示する。
- **注釈を付けるだけでなく検証する**: プロジェクトに型チェッカーが設定されている場合（`tsc`、`mypy`、`pyright`など）、「言語・スタックの規約」にあるテスト/リンター/フォーマットのチェックと合わせて、完了前の検証の一環としてそれを実行し、完了を報告する前にその変更が引き起こした型エラーをすべて解消する。型チェッカーが設定されていないプロジェクトはこの限りではない — この手順を捏造しない。
- **境界で検証する**: 型システムの保証の外側から型付けされたコードに入ってくるデータ（ユーザー入力、外部APIのレスポンス、デシリアライズされたペイロード、環境変数・設定値）は、境界において検証するか期待される型へ絞り込みを行い、検証なしに信頼したりキャストしたりしない。境界を越えない、すでに型付けされている内部データに対して冗長な検証を追加しない。

# コード品質とセキュリティ

リポジトリ内の実装作業に適用される。上記のTDD/SDD/ドキュメントと組み合わさる。

## コード品質

- **実際に**変更する範囲（ロギング、コメント、エラー処理、構造）では確立されたベストプラクティスを**採用する** — スタックとリポジトリに合わせ、意図的な手抜きはしない。
- 投機的な抽象化を書かない: 複雑さは仮定の将来のニーズではなく、タスクに見合ったものにする。
- **ロギング**: プロジェクトの規約（レベル、フォーマット、構造化するか否か）に従う。運用者がデバッグと監査に必要な情報をログに残す。シークレット、トークン、マスクされていないPIIは**絶対に**ログに残さない。I/Oおよびリクエストの境界では、コードベースがすでに相関IDを使っている場合はそれを含める。問題を診断している場合を除き、ホットパスでのログノイズは避ける。
- **編集したコードへのコメントとdocstring**: 次の行のナレーションではなく、**理由（why）**や自明でない不変条件を優先して記す。**公開**または**複雑な**箇所については、プロジェクトが期待する場所（上記のTDD/SDDセクション）で契約を文書化する。**触れていない**コードにdocstring、コメント、型注釈を追加**しない**。
- **エラー処理**: **システム境界**（ユーザー入力、ファイル/ネットワーク/DB、外部API、ユーザーに見えるエラー）では、明確なバリデーション、**型付けされた、または狭められた**エラー経路、ユーザーに安全なメッセージを用いる。それが慣用的な言語であれば、プログラマのミスに対してはフェイルファストとする。「起こりえない」内部状態に対するキャッチオールな処理は**追加しない** — フレームワークを信頼する。文書化された理由なしに失敗を隠蔽**しない**。安全でない、または誤解を招くエラー処理が見つかった場合は、完了とする前に**修正する**（セキュリティの節と同様）。
- ベストプラクティスが明らかに有効だが**対象範囲外**である場合（例: 新しい連携先に構造化ログがない、新しいクライアントにタイムアウトがない）は**ユーザーに提案する**: ギャップの内容、それが重要である理由、**最小限の**フォローアップを述べる — 合意なしに大規模または無関係な作業を実施**しない**。
- 求められていない**コード**の改善を加えない: 合意されたタスクを超えたついでのリファクタリング、クリーンアップ、機能の肥大化は行わない — ユーザーに伝えることは構わないが、任意のファイルを変更することは許されない。

## セキュリティ

**コード**と**環境**の使い方の両方において**安全でセキュアな**結果を目指す。**確立された**セキュアコーディングの実践を優先し、該当する場合は**国際的・業界的に認知されたベースライン**（例: OWASPガイドやASVS準拠の統制、一般的な欠陥クラスに対する**CWE**を意識した対応、言語やプラットフォームの**セキュリティ勧告**）を用いる。非推奨のパターンより現行の推奨事項を優先する。

- **コードにおいて**: コマンドインジェクション、XSS、SQLインジェクション、その他の**OWASP Top 10**クラスの欠陥を決して持ち込まない。シークレットと権限には最小権限の原則を適用する。それらの層に触れる場合は検証済みの暗号技術と健全な依存関係管理を用いる。**システム境界**（ユーザー入力、外部API）で検証とエンコードを行い、スタックトレースや内部の詳細をエンドユーザーに漏らさない。安全でないコードを書いた場合は、完了を主張する**前に修正する**。
- **開発環境において**（シェル、リポジトリ、ツール利用）: 認証情報を露出させたり、破壊的な操作でユーザーを驚かせたり、レビューされていないリモートコンテンツを実行したりしない。公式のソースと**HTTPS**を使用し、シークレットは指定された保管場所に置き、破壊的・マシン全体に影響する・認証情報を伴う・外部に影響を及ぼす操作で権限があらかじめ明確でないものについては明示的な許可を得る。コマンドや連携先を提案する際は、より安全な選択肢をデフォルトとし、重大なリスクを明示する。
- 標準やプロジェクト自身の**セキュリティ**関連ドキュメントが近道と矛盾する場合は、より厳格な、あるいはプロジェクトが定めたルールに従う。要件が**不明確**な場合（例: データ分類、暗号方式の選択）は、実装前に**確認する**。

# 言語・スタックの規約

これは唯一のコーディングスキルであり、言語に依存しない。使用している言語・スタックについては、リポジトリに設定されたリンター、フォーマッター、型チェッカー、テストランナーに従い、完了を報告する前にそれらを実行する。外部のデフォルトを持ち込むのではなく、既存のリポジトリの規約に合わせる。
