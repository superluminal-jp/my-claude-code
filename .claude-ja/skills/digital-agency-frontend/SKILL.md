# デジタル庁フロントエンド

人々が行政サービスのタスクを完了させたり、データを理解したりする助けとなる、ソースに裏付けられた React/Tailwind インターフェースを構築する。公式の DADS 資料は適応可能な出発点であり、そのまま組み込めるコンポーネントライブラリではなく、それ自体がアクセシビリティの証明になるものでもない。

## 対象範囲

- このスキルは、DADS のデザイン、ソース選定、ダッシュボード、アクセシビリティに関する意思決定に使用する。
- 対象リポジトリのアーキテクチャと指示をそのまま維持する。このスキルを適用したいという理由だけで React や Tailwind CSS を導入してはならない。
- Web に限定する。`.pbit`、Power BI テーマ、Power BI の編集は対象外とする。
- 意図を勝手に推測するのではなく、実装(ステップ1)に入る前に、利用者、タスク、利用状況、データ、制約、完了基準における重大な曖昧さを解消する。

## 同梱されているソース

`references/dads-docs/` は、デザインシステムサイトのデジタル庁公式 Markdown エクスポートをそのまま複製したものであり、ガイダンス、基盤(ファウンデーション)、すべてのコンポーネント仕様、アクセシビリティ方針を含む。これはデザインガイダンスであり、コードはほとんど含まれていない。推測に頼らず grep で検索すること。また、決して編集しないこと。

アーカイブ自身のマニフェストを使って、日本語名から該当ページを見つける。

```sh
DADS="${CLAUDE_SKILL_DIR}/references/dads-docs"
grep -o '\[[^]]*ボタン[^]]*\]([^)]*)' "$DADS/MANIFEST.md"    # → components/button/index.md
grep -m1 '^# ' "$DADS/index.md"                              # → current archive version
```

各ページのフロントマターには `source_url` が記載されている。最新の詳細が重要な場合はこれを開くこと。アーカイブは特定時点のスナップショットであり、常に最新のライブ公式情報源が優先される。

## リファレンスを段階的に読み込む

| 読む対象 | いつ読むか |
|---|---|
| `references/sourcing-and-licensing.md` | どの情報源を信頼するか判断するとき、アーカイブを更新するとき、または帰属表示(アトリビューション)を記述するとき |
| `references/component-implementation.md` | DADS の React/Tailwind コードを記述・移植・レビューするとき — トークンクラスとコンポーネントの慣用パターン |
| `references/accessibility-gate.md` | インターフェース関連の作業を完了と報告する前 |
| `references/dashboard-design.md` | タスクがダッシュボードを作成・変更・レビューする場合 |
| `references/dads-docs/<path>` | 実装対象となっている特定の基盤(ファウンデーション)またはコンポーネント |

バージョン番号、トークン名、パッケージ API を記憶に頼って引用してはならない。アーカイブ、インストール済みパッケージ、またはライブの情報源から読み取ること。

## ワークフロー

### 1. スコープと根拠を確立する

`package.json`、ロックファイル、Tailwind および TypeScript の設定、ルーティング、状態管理とデータアクセス、コンポーネントの規約、そしてテスト・lint・フォーマット・ビルドの各コマンドを確認する。`@digital-go-jp/*` パッケージが既にインストールされているかどうかを確認する — インストール済みであれば、それらがトークンとコンポーネント API に関して権威ある情報源となる。

主たる利用者、タスクまたは意思決定、利用状況、コンテンツやデータ、制約、そして検証可能な完了基準を把握する。既存のインターフェースについては、ソースコードだけから体験全体を推測するのではなく、ブラウザやテストツールが利用できる場合はレンダリングされた実際の挙動を確認する。

### 2. 最新のガイダンスを確認する

ネットワークに接続できる場合は、同梱アーカイブよりもライブの公式情報源を優先し、パッケージのバージョンはタスク実行時点で確定させる。調査対象はデジタル庁のサイトと公式の `digital-go-jp` 組織に限定する。ライブの内容がアーカイブと食い違う場合は、ライブの情報源に従い、その乖離(ドリフト)を開示し、古くなったパスを明示する。最新情報に到達できない場合はアーカイブを使用し、鮮度が未検証であることを明記する。詳細: `references/sourcing-and-licensing.md`。

### 3. 実装前に設計する

各ユーザータスクを、適切な最小限の基盤(ファウンデーション)、コンテンツパターン、コンポーネント群にマッピングする。ネイティブなセマンティクスと素直な文書構造を保ち、ネイティブな HTML では表現できない挙動がある場合に限り ARIA を追加する。プロジェクトの既存のプリミティブが既に DADS の意図を満たしている場合はそれを再利用し、重大な逸脱がある場合はその理由とともに記録する。ダッシュボードの場合は、チャートを選ぶ前に `dashboard-design.md` に沿って対象読者・意思決定・種類・情報階層の検討を終わらせる。完全な意思決定の手順は `references/dashboard-design.md` を参照する。

### 4. テストファーストかつ型安全に実装する

リポジトリが契約を自動化できる箇所では、実装前に失敗する振る舞いテストまたはアクセシビリティテストを作成または更新する。変更は型安全に保つこと — コードをコンパイルさせるために型チェッカーを弱めたり回避したりしてはならない。

ソースをコピーするより、公式の npm パッケージに依存することを優先する。プロジェクトがそのコードを自ら所有し、そこから分岐させる必要がある場合に限りコピーし、その旨を明記する。ディレクトリを丸ごとコピーしたり無理にバージョンを下げたりするのではなく、取り込む内容は対象プロジェクトの React、Tailwind、TypeScript のバージョンに合わせて適応させる。外部データはその境界で検証し、信頼できないテキストは React の通常のエスケープ処理を通じてレンダリングする。トークンクラスとコンポーネントの慣用パターン: `references/component-implementation.md`。

### 5. アクセシビリティゲートを適用する

`references/accessibility-gate.md` を最初から最後まで実行する。既知のレベル A または AA の不適合が未開示のまま残っている状態で、完了を報告してはならない。

### 6. 締めくくる

プロジェクトのテスト・型チェック・lint・フォーマット・ビルドの各コマンドを実行する。公開コンポーネント契約に変更が生じた場合は、同じ変更の中でドキュメント成果物を更新する。以下を報告する: 確認したソースおよび鮮度が検証されたかどうか、DADS の適応と逸脱、該当する場合はダッシュボードに関する意思決定、自動および手動によるアクセシビリティの検証結果、未解決のリスク。公式コンテンツやコードを再利用する場合は、`references/sourcing-and-licensing.md` の帰属表示ルールを適用する。

## ガードレール

- あるインターフェースがデジタル庁の製品である、またはデジタル庁の承認を受けていると主張してはならない。
- 色、ホバー、ポインターの精密な操作、アニメーション、またはチャート単体だけに本質的な意味を担わせてはならない。
- トークン、コンポーネント、チャートのルール、バージョン番号、適合性に関する主張を捏造してはならない。プロジェクト固有の追加事項は、そのように明示すること。
- Figma データ、Power BI テンプレート、アイコン、イラストをベンダリング(取り込み)してはならない — これらは MIT ライセンスのコードや帰属表示のみで利用可能なドキュメントとは別の利用条件を伴う。
