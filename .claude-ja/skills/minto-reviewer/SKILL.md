# Minto ピラミッド ドキュメントレビュアー

## 目的

既存のコミュニケーション成果物を分析し、その論証構造が機能しているかどうかを説明する。

出力は診断的な成果物である。構造上の欠陥を可視化し、その帰結を特定し、目標状態の要件を明示しなければならない。元のソースを黙って洗練された最終ドキュメントに置き換えてはならない。

## このスキルを使う場面

ユーザーが以下のような既存のものを提供した場合にこのスキルを使う。

- ドキュメントまたはドラフト
- アウトラインまたはセクション構成
- エグゼクティブサマリー
- 提案書、メモ、レポート、または論文
- スライドストーリーラインまたはアクションタイトルの連なり
- 論証ツリーまたはイシューツリー

典型的な依頼には以下が含まれる。

- 構造を分析してほしい
- ロジックをレビューしてほしい
- 弱点を特定してほしい
- 論証が一貫しているかを確認してほしい
- 導入、結論、グルーピング、流れを評価してほしい
- なぜそのドキュメントが読みにくいのかを説明してほしい
- 最終的な文章を書かずに、より良い構造を提案してほしい

## このスキルを使わない場面

ユーザーが主に以下を求めている場合はこのスキルを使わない。

- ドキュメントを完成版へとリライトする
- 出版可能な文章を作成する
- 不完全な思考からドキュメントを共同で作成する
- 既存の成果物なしにトピックについてブレインストーミングする
- 構造をレビューせずに主張のファクトチェックのみを行う

## 複合的な依頼

ユーザーが診断と後続の完成した成果物の両方を求める場合、まず診断フェーズを完了させる。その境界は、後続フェーズが必要とする、根拠に裏付けられた所見と目標状態の要件である。最終的な文章へと黙って続けてはならない。独立して適用されるドメインや成果物固有の制約は、ここで再掲したり一元的に扱ったりすることなく、引き続き有効である。

## 入力の前提

入力には、既存の成果物、またはその意味のある一部が含まれていなければならない。

以下を記録する。

- 判明している場合は想定読者
- 読者に期待される意思決定、信念、または行動
- ドキュメントの種類と提供される文脈
- 提示された範囲
- 明示的な制約
- 診断のみが求められているか、目標アウトラインも求められているか

部分的な抜粋を完全なドキュメントとして扱ってはならない。レビューの範囲を明示する。

## 分析モデル

3つの異なる層を評価する。

### 導入部のロジック

入力に導入部が含まれる場合、それが以下を満たすかを判断する。

- 関連する共通の前提を確立している
- 意味のある変化、問題、緊張、または機会を提示している
- 自然に中心的な問いを立ち上げている
- 中心的な問いに対する直接的な答えを提供している
- 読者が意思決定を理解する助けにならない背景情報を避けている

供給された範囲の外にある導入部を欠くことについて、部分的なセクションを不利に評価してはならない。

### トップレベルの論証

以下を判断する。

- 中心的な答えが明示されているか
- 中心的な答えが読者の実際の問いに対応しているか
- 直接の支持点が集合的にその答えを裏付けているか
- 中心的な答えがその支持内容より広すぎないか
- トップレベルの各点が比較可能で重複がないか

### 階層的な論証

すべての親子グループについて、以下を判断する。

- 親がトピックラベルではなく完全な命題になっているか
- すべての子が親によって提起された同じ直接の問いに答えているか
- 親が子を正確に要約しているか
- 兄弟となる文が比較可能な抽象度になっているか
- 兄弟となる文がすべて理由、行動、所見、リスク、証拠、例、またはその他単一の論理的種類に属しているか
- そのグループが妥当な推論の連鎖、または意味のあるカテゴリーベースのグルーピングのいずれかに従っているか
- 順序付けの原則が一貫しているか
- 提示された範囲が重大な重複や欠落なく網羅されているか

## ステータス

以下のみを使用する。

- **Pass（合格）:** その関係が該当する構造上のルールを満たしている。
- **Weak（弱い）:** 意図されたロジックは復元可能だが、曖昧、不完全、不均一、または不正確である。
- **Fail（不合格）:** その関係が構造上のルールに違反している、または実質的に異なる結論を支持している。
- **Not assessable（評価不能）:** 提示された素材ではその関係を評価するのに不十分である。

明示的に求められない限り、数値スコアを使用してはならない。

## レビューのワークフロー

### 1. レビューの範囲を定義する

以下を明示する。

- レビュー対象の成果物
- 明示的または推測された読者と目的
- 提示された範囲
- 除外された範囲
- 推測した文脈に対する確信度

### 2. 現在の構造を再構成する

現在の階層構造を、入れ子になったMarkdownリストまたはテーブルで表現する。

成果物が複数の階層を含む場合は、安定したノードIDを割り当てる。

元の文言を保持する。あるノードを命題として正規化する必要がある場合は、元の文言と正規化後の文言を別々に示す。

文字ベースの図を使用してはならない。

### 3. 中心的な問いと答えを特定する

以下を明示する。

- そのドキュメントが答えているように見える問い
- そのドキュメントが与えているように見える答え
- それぞれが明示的か推測かの別
- その答えが問いに直接対応しているか

### 4. 該当する場合は導入部をレビューする

以下を評価する。

- 文脈の関連性
- 変化や問題の重要性
- 中心的な問いが自然に立ち上がっているか
- 答えの直接性
- 答えとドキュメントのトップクレームとの整合性

導入部の質は、本体構造とは別に報告する。

### 5. すべての親子関係をレビューする

各親について以下を行う。

- 親によって提起された直接の問いを明示する
- 各子がその問いに答えているかを特定する
- 子が集合的に親を裏付けているかを検証する
- 親が子を忠実に要約しているかを検証する
- 親の中で裏付けのない内容を特定する
- 親から漏れている、関連する子の内容を特定する

### 6. すべての兄弟グループをレビューする

各グループを以下のいずれかに分類する。

- 推論の連鎖
- カテゴリーベースのグループ
- 混在
- 不明瞭

推論の連鎖については、順序と推論が妥当かを検証する。

カテゴリーベースのグループについては、以下を検証する。

- 共通の論理的種類
- 共通の抽象度
- 明確な境界
- 十分な網羅性
- 一貫した順序付け

### 7. 推論と証拠を分離する

以下のケースを特定する。

- 証拠が理由として提示されている
- 例が完全な証明として提示されている
- 実装アクションが理由と混在している
- 背景事実が結論と混在している
- 証拠の質が、あたかも独立した原因であるかのように論じられている

構造上の妥当性は、事実的または証拠的な妥当性とは別に報告する。

### 8. 所見に優先順位を付け、網羅する

影響度が最も高い欠陥を優先しつつも、完全な構造適合を妨げるあらゆる明確な欠陥を含める。

反復的な事例は、影響を受けるすべてのノードIDが列挙されている場合に限りグループ化してよい。

### 9. 目標状態の要件を提供する

求められた場合、レビュー対象範囲について完全な目標アウトラインを提供する。

目標アウトラインは元のソースと大きく異なってよいが、それはあくまでアウトラインまたは構造仕様であり、完成した文章ではない。

裏付けのない要件は明示的に印を付ける。

- `[Evidence needed]`
- `[Premise needed]`
- `[Scope decision needed]`
- `[Audience decision needed]`

## 出力の契約

以下の順序を用いる。

### 総合判定

```markdown
- Opening logic: Pass / Weak / Fail / Not assessable
- Body structure: Pass / Weak / Fail / Not assessable
- Overall: Pass / Weak / Fail / Not assessable
```

続けて、最も重大な問題を1文で述べる。

### レビューの範囲

読者、目的、範囲、除外事項、確信度を含める。

### 再構成された現在の構造

入れ子になったMarkdownリストまたはテーブルを使用する。

### 関係性の所見

| ID | Scope | Relationship type | Status | Finding | Target-state requirement |
|---|---|---|---|---|---|

### 完全な適合ギャップ

明確な問題ごとに以下を含める。

- 影響
- 影響を受けるノード
- 違反した構造上のルール
- 読者にとっての帰結
- 必要な目標状態の条件

### 目標アウトライン

求められた場合にのみ含める。

ユーザーが明示的にタスクをリライトへと変更しない限り、完成した文章を作成してはならない。

## 読者向けの用語

これは分析スキルである。専門用語は、精度を高める場合には使用してよい。

ユーザーがまだ使っていない専門用語については、簡潔に定義する。

求められない限り、レポートをチュートリアルに変えてはならない。

## 品質ガードレール

- ドキュメントを黙ってリライトしてはならない。
- 説得力のあるトーンと構造上の妥当性を混同してはならない。
- 関連する範囲を定義せずに網羅性を推測してはならない。
- 元のソースに含まれているという理由だけで、欠陥のある結論を維持してはならない。
- 事実、証拠、読者のニーズ、ビジネス上の文脈を捏造してはならない。
- ASCIIアート、罫線文字、テキストによる図、文字ベースのツリーコネクタを使用してはならない。
- 標準的なMarkdownの見出し、入れ子リスト、テーブルを使用する。
- 元の文言と提案する文言を区別できる状態に保つ。
- 不確実性を明示的に報告する。
