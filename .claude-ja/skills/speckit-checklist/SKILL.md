## チェックリストの目的：「英語のための単体テスト」

**重要な概念**: チェックリストは **要件記述のための単体テスト（UNIT TESTS FOR REQUIREMENTS WRITING）** である。特定のドメインにおける要件の品質・明確さ・完全性を検証するものである。

**検証／テストの対象では「ない」**:

- ❌ 「ボタンが正しくクリックされることを確認する」ではない
- ❌ 「エラーハンドリングが機能することをテストする」ではない
- ❌ 「APIが200を返すことを確認する」ではない
- ❌ コード／実装がspecと一致しているかどうかのチェックではない

**要件品質の検証が「対象」**:

- ✅ 「すべてのカードタイプについて視覚的階層の要件が定義されているか？」（完全性）
- ✅ 「『目立つ表示』は具体的なサイズや配置で定量化されているか？」（明確さ）
- ✅ 「ホバー状態の要件はすべてのインタラクティブ要素間で一貫しているか？」（一貫性）
- ✅ 「キーボードナビゲーションに関する要件がアクセシビリティ要件として定義されているか？」（カバレッジ）
- ✅ 「ロゴ画像の読み込みに失敗した場合の挙動をspecは定義しているか？」（エッジケース）

**比喩**: あなたのspecが英語で書かれたコードだとすれば、チェックリストはその単体テストスイートである。実装が動くかどうかではなく、要件が適切に書かれているか、完全か、曖昧でないか、実装可能な状態にあるかをテストしているのである。

## ユーザー入力

```text
$ARGUMENTS
```

（空でない場合）進める前に必ずユーザー入力を考慮**しなければならない**。

## 実行前チェック

**拡張フックの確認（チェックリスト生成前）**:
- プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。
- 存在する場合は読み込み、`hooks.before_checklist` キー配下のエントリを探す。
- YAMLがパースできない、または不正な場合は、フックチェックを黙ってスキップし通常通り継続する。
- `enabled` が明示的に `false` であるフックは除外する。`enabled` フィールドがないフックはデフォルトで有効として扱う。
- 残った各フックについて、フックの `condition` 式を解釈・評価しようと**しない**こと:
  - フックに `condition` フィールドがない、またはnull/空である場合は、そのフックを実行可能として扱う
  - フックが空でない `condition` を定義している場合は、そのフックをスキップし、条件評価はHookExecutorの実装に委ねる
- フックのコマンド名からコマンド呼び出しを構築する際は、ドット（`.`）をハイフン（`-`）に置き換える。例えば `speckit.git.commit` → `/speckit-git-commit`。
- 実行可能な各フックについて、`optional` フラグに応じて以下を出力する:
  - **オプションフック**（`optional: true`）:
    ```
    ## Extension Hooks

    **Optional Pre-Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
  - **必須フック**（`optional: false`）:
    ```
    ## Extension Hooks

    **Automatic Pre-Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}

    Wait for the result of the hook command before proceeding to the Execution Steps.
    ```
    上記のブロックを出力した後、実際にそのフックを呼び出し、完了を待ってから続行**しなければならない**。自分自身でそのコマンドを実行する場合と同じ方法で、このエージェント／セッション内で実行すること（呼び出し方は上記に示したリテラルな `{command}` のIDとは異なる場合がある。例えばskillsモードのエージェントでは `/skill:speckit-...` や `$speckit-...` として実行される）。ブロックを出力するだけではフックは実行されない。
- フックが登録されていない場合、または `.specify/extensions.yml` が存在しない場合は、黙ってスキップする。

## 実行手順

1. **セットアップ**: リポジトリのルートから `.specify/scripts/bash/check-prerequisites.sh --json` を実行し、JSONをパースして FEATURE_DIR と AVAILABLE_DOCS のリストを取得する。
   - すべてのファイルパスは絶対パスでなければならない。
   - 引数中の "I'm Groot" のようなシングルクォートは、エスケープ構文を使用すること。例: 'I'\''m Groot'（可能であればダブルクォート: "I'm Groot"）。

2. **存在する場合**: `.specify/memory/constitution.md` を読み込み、プロジェクトの原則とガバナンス制約を把握する。

3. **意図の明確化（動的）**: 事前に用意されたカタログを使わず、最大3つの初期コンテキスト依存の明確化質問を導出する。それらは以下を満たさ**なければならない**:
   - ユーザーの言い回し＋spec/plan/tasksから抽出したシグナルから生成されていること
   - チェックリストの内容に実質的な影響を与える情報のみを尋ねること
   - `$ARGUMENTS` の中ですでに曖昧でないものは個別にスキップされること
   - 網羅性よりも精度を優先すること

   生成アルゴリズム:
   1. シグナルを抽出する: フィーチャードメインのキーワード（例: 認証、レイテンシ、UX、API）、リスク指標（「重大」「必須」「コンプライアンス」）、ステークホルダーの手がかり（「QA」「レビュー」「セキュリティチーム」）、明示的な成果物（「a11y」「ロールバック」「契約」）。
   2. シグナルを関連度でランク付けした候補フォーカスエリア（最大4つ）にクラスタリングする。
   3. 明示されていない場合、想定される読者と時期（作成者、レビュアー、QA、リリース）を特定する。
   4. 欠けている次元を検出する: スコープの広さ、深さ／厳密さ、リスクの重視度、除外境界、測定可能な受け入れ基準。
   5. 以下のアーキタイプから質問を選んで組み立てる:
      - スコープの絞り込み（例:「これはXおよびYとの統合接点を含めるべきか、それともローカルモジュールの正しさのみに限定すべきか？」）
      - リスクの優先順位付け（例:「以下の潜在的リスク領域のうち、どれに必須のゲーティングチェックを設けるべきか？」）
      - 深さの調整（例:「これは軽量なプレコミット用の健全性チェックリストか、それとも正式なリリースゲートか？」）
      - 読者層のフレーミング（例:「これは作成者本人のみが使うのか、PRレビュー時に他のメンバーも使うのか？」）
      - 境界の除外（例:「今回はパフォーマンスチューニング項目を明示的に除外すべきか？」）
      - シナリオクラスのギャップ（例:「リカバリーフローが検出されていません。ロールバック／部分的失敗パスはスコープ内ですか？」）

   質問フォーマットのルール:
   - 選択肢を提示する場合、列「Option | Candidate | Why It Matters」を持つコンパクトな表を生成する
   - 選択肢はA〜Eまでとする。自由記述の方が明確な場合は表を省略する
   - ユーザーがすでに述べたことを繰り返し尋ねない
   - 推測によるカテゴリ（ハルシネーション）を避ける。不確かな場合は明示的に尋ねる:「Xがスコープに含まれるか確認してください」

   対話が不可能な場合のデフォルト:
   - 深さ: 標準
   - 読者層: コード関連であればレビュアー（PR）、そうでなければ作成者
   - フォーカス: 関連度上位2つのクラスタ

   質問（Q1/Q2/Q3とラベル付けする）を出力する。回答後、2つ以上のシナリオクラス（代替／例外／リカバリー／非機能ドメイン）が依然として不明確な場合、さらに最大2つの的を絞ったフォローアップ（Q4/Q5）を、それぞれ一行の理由（例:「未解決のリカバリーパスのリスク」）とともに尋ねて**もよい**。合計で5問を超えてはならない。ユーザーがそれ以上の質問を明示的に拒否した場合はエスカレーションをスキップする。

4. **ユーザーリクエストの理解**: `$ARGUMENTS` と明確化の回答を組み合わせる:
   - チェックリストのテーマを導出する（例: セキュリティ、レビュー、デプロイ、UX）
   - ユーザーが明示した必須項目を統合する
   - フォーカスの選択をカテゴリの骨組みにマッピングする
   - spec/plan/tasksから欠けているコンテキストを推測する（ハルシネーションをしないこと）

5. **フィーチャーコンテキストの読み込み**: FEATURE_DIRから以下を読み込む:
   - spec.md: フィーチャーの要件とスコープ
   - plan.md（存在する場合）: 技術的な詳細、依存関係
   - tasks.md（存在する場合）: 実装タスク

   **コンテキスト読み込み戦略**:
   - アクティブなフォーカスエリアに関連する必要な部分のみを読み込む（ファイル全体のダンプは避ける）
   - 長いセクションは簡潔なシナリオ／要件の箇条書きに要約することを優先する
   - 段階的開示を用いる: ギャップが検出された場合にのみ追加の取得を行う
   - ソースドキュメントが大きい場合は、生のテキストを埋め込む代わりに暫定的な要約項目を生成する

6. **チェックリストの生成** - 「要件のための単体テスト」を作成する:
   - `FEATURE_DIR/checklists/` ディレクトリが存在しない場合は作成する
   - 一意なチェックリストファイル名を生成する:
     - ドメインに基づいた短く説明的な名前を使用する（例: `ux.md`、`api.md`、`security.md`）
     - フォーマット: `[domain].md`
   - ファイル処理の挙動:
     - ファイルが存在**しない**場合: 新規ファイルを作成し、CHK001から項目に番号を付ける
     - ファイルが存在する場合: 既存ファイルに新規項目を追加し、最後のCHK IDから続ける（例: 最後の項目がCHK015であれば、新規項目はCHK016から開始する）
   - 既存のチェックリスト内容を削除・置換することはせず、常に保持したうえで追加する

   **中核原則 - 実装ではなく要件をテストする**:
   すべてのチェックリスト項目は、以下の観点から要件そのものを評価**しなければならない**:
   - **完全性**: 必要な要件がすべて存在しているか？
   - **明確さ**: 要件は曖昧でなく具体的か？
   - **一貫性**: 要件同士が整合しているか？
   - **測定可能性**: 要件は客観的に検証できるか？
   - **カバレッジ**: すべてのシナリオ／エッジケースが対応されているか？

   **カテゴリ構造** - 要件品質の次元ごとに項目をグループ化する:
   - **要件の完全性**（必要な要件がすべて文書化されているか？）
   - **要件の明確さ**（要件は具体的で曖昧でないか？）
   - **要件の一貫性**（要件は矛盾なく整合しているか？）
   - **受け入れ基準の品質**（成功基準は測定可能か？）
   - **シナリオカバレッジ**（すべてのフロー／ケースが対応されているか？）
   - **エッジケースカバレッジ**（境界条件が定義されているか？）
   - **非機能要件**（パフォーマンス、セキュリティ、アクセシビリティなどが規定されているか？）
   - **依存関係と前提条件**（文書化され検証されているか？）
   - **曖昧点と矛盾点**（何が明確化を必要としているか？）

   **チェックリスト項目の書き方 - 「英語のための単体テスト」**:

   ❌ **誤り**（実装をテストしている）:
   - 「ランディングページに3つのエピソードカードが表示されることを確認する」
   - 「デスクトップでホバー状態が機能することをテストする」
   - 「ロゴをクリックするとホームに遷移することを確認する」

   ✅ **正しい**（要件の品質をテストしている）:
   - 「注目エピソードの正確な数とレイアウトが規定されているか？」［完全性］
   - 「『目立つ表示』は具体的なサイズや配置で定量化されているか？」［明確さ］
   - 「ホバー状態の要件はすべてのインタラクティブ要素にわたって一貫して定義されているか？」［一貫性］
   - 「すべてのインタラクティブなUIについてキーボードナビゲーションの要件が定義されているか？」［カバレッジ］
   - 「ロゴ画像の読み込みに失敗した場合のフォールバック挙動が規定されているか？」［エッジケース］
   - 「非同期のエピソードデータに対するローディング状態が定義されているか？」［完全性］
   - 「競合するUI要素の視覚的階層をspecは定義しているか？」［明確さ］

   **項目の構造**:
   各項目は以下のパターンに従うべきである:
   - 要件品質について尋ねる質問形式
   - spec/planに「書かれているか（あるいは書かれていないか）」に焦点を当てる
   - 品質次元を角括弧で示す ［Completeness/Clarity/Consistency/etc.］
   - 既存の要件を確認する場合はspecセクション `[Spec §X.Y]` を参照する
   - 欠けている要件を確認する場合は `[Gap]` マーカーを使用する

   **品質次元別の例**:

   完全性:
   - 「すべてのAPI障害モードについてエラーハンドリングの要件が定義されているか？ [Gap]」
   - 「すべてのインタラクティブ要素についてアクセシビリティ要件が規定されているか？ [Completeness]」
   - 「レスポンシブレイアウトについてモバイルのブレークポイント要件が定義されているか？ [Gap]」

   明確さ:
   - 「『高速な読み込み』は具体的なタイミング閾値で定量化されているか？ [Clarity, Spec §NFR-2]」
   - 「『関連エピソード』の選定基準は明示的に定義されているか？ [Clarity, Spec §FR-5]」
   - 「『目立つ』は測定可能な視覚的プロパティで定義されているか？ [Ambiguity, Spec §FR-4]」

   一貫性:
   - 「ナビゲーションの要件はすべてのページで整合しているか？ [Consistency, Spec §FR-10]」
   - 「カードコンポーネントの要件はランディングページと詳細ページの間で一貫しているか？ [Consistency]」

   カバレッジ:
   - 「ゼロ状態のシナリオ（エピソードなし）についての要件が定義されているか？ [Coverage, Edge Case]」
   - 「同時ユーザー操作のシナリオが対応されているか？ [Coverage, Gap]」
   - 「部分的なデータ読み込み失敗についての要件が規定されているか？ [Coverage, Exception Flow]」

   測定可能性:
   - 「視覚的階層の要件は測定可能／テスト可能か？ [Acceptance Criteria, Spec §FR-1]」
   - 「『バランスの取れた視覚的重み』は客観的に検証できるか？ [Measurability, Spec §FR-2]」

   **シナリオ分類とカバレッジ**（要件品質重視）:
   - Primary、Alternate、Exception/Error、Recovery、Non-Functionalの各シナリオについて要件が存在するかを確認する
   - シナリオクラスごとに問う:「［シナリオタイプ］の要件は完全で、明確で、一貫しているか？」
   - シナリオクラスが欠けている場合:「［シナリオタイプ］の要件は意図的に除外されているのか、それとも欠落しているのか？ [Gap]」
   - 状態変更が発生する場合は復元力／ロールバックを含める:「マイグレーション失敗時のロールバック要件が定義されているか？ [Gap]」

   **トレーサビリティ要件**:
   - 最低要件: 項目の80%以上が、少なくとも1つのトレーサビリティ参照を含んでい**なければならない**
   - 各項目はspecセクション `[Spec §X.Y]` を参照するか、`[Gap]`、`[Ambiguity]`、`[Conflict]`、`[Assumption]` のマーカーを使用するべきである
   - IDシステムが存在しない場合:「要件および受け入れ基準のIDスキームが確立されているか？ [Traceability]」

   **問題の可視化と解消**（要件品質の問題）:
   要件そのものについて質問する:
   - 曖昧点:「『高速』という用語は具体的な指標で定量化されているか？ [Ambiguity, Spec §NFR-1]」
   - 矛盾点:「§FR-10と§FR-10aの間でナビゲーション要件が矛盾していないか？ [Conflict]」
   - 前提条件:「『常時利用可能なポッドキャストAPI』という前提は検証されているか？ [Assumption]」
   - 依存関係:「外部ポッドキャストAPIの要件は文書化されているか？ [Dependency, Gap]」
   - 未定義の定義:「『視覚的階層』は測定可能な基準で定義されているか？ [Gap]」

   **内容の統合**:
   - ソフトキャップ: 候補項目が生の状態で40を超える場合、リスク／影響度で優先順位付けする
   - 同じ要件側面をチェックしている類似項目は統合する
   - 影響度の低いエッジケースが5件を超える場合、1つの項目にまとめる:「エッジケースX、Y、Zは要件で対応されているか？ [Coverage]」

   **🚫 絶対に禁止** - これらは要件のテストではなく実装のテストにしてしまう:
   - ❌ 「Verify」「Test」「Confirm」「Check」で始まり、実装の挙動を続ける項目
   - ❌ コード実行、ユーザー操作、システムの挙動への言及
   - ❌ 「正しく表示される」「正しく機能する」「期待通りに動作する」
   - ❌ 「クリック」「遷移」「レンダリング」「読み込み」「実行」
   - ❌ テストケース、テストプラン、QA手順
   - ❌ 実装の詳細（フレームワーク、API、アルゴリズム）

   **✅ 必須パターン** - これらは要件の品質をテストする:
   - ✅ 「［シナリオ］について［要件タイプ］は定義／規定／文書化されているか？」
   - ✅ 「［曖昧な用語］は具体的な基準で定量化／明確化されているか？」
   - ✅ 「［セクションA］と［セクションB］の間で要件は一貫しているか？」
   - ✅ 「［要件］は客観的に測定／検証できるか？」
   - ✅ 「［エッジケース／シナリオ］は要件で対応されているか？」
   - ✅ 「specは［欠けている側面］を定義しているか？」

7. **構造の参照**: `.specify/templates/checklist-template.md` にある正典テンプレートに従い、タイトル、メタセクション、カテゴリ見出し、ID書式でチェックリストを生成する。テンプレートが利用できない場合は以下を使用する: H1タイトル、目的／作成日のメタ行、CHK001から始まるグローバルに増加するIDを持つ `- [ ] CHK### <requirement item>` 行を含む `##` カテゴリセクション。

8. **報告**: チェックリストファイルへのフルパス、項目数、今回の実行が新規ファイルを作成したのか既存ファイルに追加したのかの要約を出力する。以下を要約する:
   - 選択されたフォーカスエリア
   - 深さのレベル
   - 想定読者／時期
   - 組み込まれたユーザー明示の必須項目

**重要**: `/speckit-checklist` コマンドの各呼び出しは、短く説明的なチェックリストファイル名を使用し、新規ファイルを作成するか既存ファイルに追加するかのいずれかを行う。これにより以下が可能になる:

- 異なるタイプの複数のチェックリスト（例: `ux.md`、`test.md`、`security.md`）
- チェックリストの目的を示す、シンプルで覚えやすいファイル名
- `checklists/` フォルダ内での容易な識別とナビゲーション

散らかりを避けるため、説明的なタイプ名を使い、不要になったチェックリストは完了後に整理すること。

## アンチパターン: やってはいけないこと

**❌ 誤り - これらは要件ではなく実装をテストしている:**

```markdown
- [ ] CHK001 - Verify landing page displays 3 episode cards [Spec §FR-001]
- [ ] CHK002 - Test hover states work correctly on desktop [Spec §FR-003]
- [ ] CHK003 - Confirm logo click navigates to home page [Spec §FR-010]
- [ ] CHK004 - Check that related episodes section shows 3-5 items [Spec §FR-005]
```

**✅ 正しい - これらは要件の品質をテストしている:**

```markdown
- [ ] CHK001 - Are the number and layout of featured episodes explicitly specified? [Completeness, Spec §FR-001]
- [ ] CHK002 - Are hover state requirements consistently defined for all interactive elements? [Consistency, Spec §FR-003]
- [ ] CHK003 - Are navigation requirements clear for all clickable brand elements? [Clarity, Spec §FR-010]
- [ ] CHK004 - Is the selection criteria for related episodes documented? [Gap, Spec §FR-005]
- [ ] CHK005 - Are loading state requirements defined for asynchronous episode data? [Gap]
- [ ] CHK006 - Can "visual hierarchy" requirements be objectively measured? [Measurability, Spec §FR-001]
```

**主な違い:**

- 誤り: システムが正しく動作するかをテストする
- 正しい: 要件が正しく書かれているかをテストする
- 誤り: 挙動の検証
- 正しい: 要件品質の検証
- 誤り: 「それはXを行うか？」
- 正しい: 「Xは明確に規定されているか？」

## 実行後チェック

**拡張フックの確認（チェックリスト生成後）**:
プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。
- 存在する場合は読み込み、`hooks.after_checklist` キー配下のエントリを探す。
- YAMLがパースできない、または不正な場合は、フックチェックを黙ってスキップし通常通り継続する。
- `enabled` が明示的に `false` であるフックは除外する。`enabled` フィールドがないフックはデフォルトで有効として扱う。
- 残った各フックについて、フックの `condition` 式を解釈・評価しようと**しない**こと:
  - フックに `condition` フィールドがない、またはnull/空である場合は、そのフックを実行可能として扱う
  - フックが空でない `condition` を定義している場合は、そのフックをスキップし、条件評価はHookExecutorの実装に委ねる
- フックのコマンド名からコマンド呼び出しを構築する際は、ドット（`.`）をハイフン（`-`）に置き換える。例えば `speckit.git.commit` → `/speckit-git-commit`。
- 実行可能な各フックについて、`optional` フラグに応じて以下を出力する:
  - **オプションフック**（`optional: true`）:
    ```
    ## Extension Hooks

    **Optional Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
  - **必須フック**（`optional: false`）:
    ```
    ## Extension Hooks

    **Automatic Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}
    ```
    上記のブロックを出力した後、実際にそのフックを呼び出し、完了を待ってから続行**しなければならない**。自分自身でそのコマンドを実行する場合と同じ方法で、このエージェント／セッション内で実行すること（呼び出し方は上記に示したリテラルな `{command}` のIDとは異なる場合がある。例えばskillsモードのエージェントでは `/skill:speckit-...` や `$speckit-...` として実行される）。ブロックを出力するだけではフックは実行されない。
- フックが登録されていない場合、または `.specify/extensions.yml` が存在しない場合は、黙ってスキップする。
