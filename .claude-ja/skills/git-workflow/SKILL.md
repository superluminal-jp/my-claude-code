# Git ワークフロー

ユーザーの権限を実装から公開へと勝手に拡張することなく、リポジトリの履歴をレビュー可能な状態に保つ。

## 権限と状態の確立

1. Git の状態を変更する前に、現在のブランチ、ステータス、リモート、および関連するプロジェクトの慣習を確認する。
2. 由来が不明なコミットされていない変更は、ユーザーの所有物として扱う。関係のないファイルは保持し、タスクを簡略化するために破棄したり書き換えたりしてはならない。
3. 要求されたワークフローで必要な場合にのみブランチを作成または切り替える。保護されたトランクブランチに直接書き込んではならない。
4. コミット、プッシュ、マージ、またはプルリクエストのオープンは、ユーザーがその操作を要求した場合にのみ行う。一つの操作に対する許可が他の操作の許可を意味するわけではない。

## ブランチ

- リポジトリで定義されたブランチ命名規則が存在する場合はそれに従う。存在しない場合は、規約に沿った変更種別と具体的な成果を示す `<type>/<short-kebab-summary>` を使用する。
- 構造化されたフィーチャーワークフローによってすでに確立された番号付きフィーチャーブランチはそのまま維持する。手動でのリネームや複製をしてはならない。
- ブランチは一つの一貫した成果に焦点を絞り、統合後の削除が許可されている場合にのみ削除する。

## コミット

- Conventional Commits を使用する: `<type>(<scope>)?: <imperative subject>`。
- リポジトリで定義された種別が存在する場合はそれに従う。存在しない場合は、`feat`、`fix`、`docs`、`refactor`、`test`、`perf`、`build`、`ci`、`style`、`chore`、`revert` の中から最も適切な最小限の種別を使用する。
- 件名は50文字以内を目安とし、72文字を超えてはならない。末尾にピリオドを付けない。
- テストと同期したドキュメントを含む一つのロジカルな変更を、一つのコミットにまとめる。ついでのクリーンアップをそこに混在させてはならない。
- コミット前にステージされた差分を確認し、結果として生成されたコミット識別子と検証の根拠を報告する。

## プルリクエストとリモート操作

- プルリクエストのタイトルにもコミット件名と同じ文法を用いる。
- 本文ではまず結論を述べ、続いて変更内容、理由、検証方法、既知の制限事項を説明し、利用可能であれば安定した要求事項や課題へのリンクを付ける。
- 指定されたブランチのみをプッシュし、最初のプッシュ時には明示的にアップストリームを設定する。
- 再試行するのは、一時的な障害である可能性が高い失敗のみとし、上限を設けた指数バックオフで行う。認証、認可、履歴拒否、ポリシー、バリデーションの失敗を、ネットワークノイズであるかのように再試行してはならない。

## 安全性の境界

- ハードリセット、強制プッシュ、追跡されていないファイルのクリーニング、履歴の書き換え、ブランチの削除、コミットされていない作業の上書きなど、破壊的または復旧困難な操作の直前には明示的な許可を必須とする。
- ユーザーが明示的に文書化された例外を許可し、かつ環境がそれを許容する場合を除き、フック、必須チェック、レビューポリシー、ブランチ保護を決してバイパスしてはならない。
- 非対話型コマンドを優先し、影響のある書き込みを行う前には必ず正確な対象を示す。

## 完了確認

- 要求された Git 操作――かつその操作のみ――が、意図したリポジトリ、ブランチ、リモートに対して実行されたこと。
- 差分またはコミットに、そのテストとドキュメントを伴う一つの一貫した変更が含まれていること。
- 検証結果、リモート状態の変更、および実行されなかった事項が明示的に報告されていること。
