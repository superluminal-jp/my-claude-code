## User Input

```text
$ARGUMENTS
```

ユーザー入力が空でない場合、進める前に**必ず**それを考慮しなければならない。

## Pre-Execution Checks

**拡張フックの確認（clarification実行前）**:
- プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。
- 存在する場合は読み込み、`hooks.before_clarify` キー配下のエントリを探す。
- YAMLがパースできない、または不正な場合は、フックの確認を黙って省略し、通常どおり続行する。
- `enabled` が明示的に `false` になっているフックは除外する。`enabled` フィールドがないフックはデフォルトで有効として扱う。
- 残った各フックについて、フックの `condition` 式を解釈・評価しようと**しない**こと。
  - フックに `condition` フィールドがない、またはnull/空である場合は、そのフックを実行可能として扱う。
  - フックが空でない `condition` を定義している場合は、そのフックをスキップし、条件評価はHookExecutorの実装に委ねる。
- フックのコマンド名からコマンド呼び出しを組み立てる際は、ドット（`.`）をハイフン（`-`）に置き換える。例えば `speckit.git.commit` → `/speckit-git-commit`。
- 実行可能な各フックについて、`optional` フラグに応じて以下を出力する。
  - **任意のフック**（`optional: true`）:
    ```
    ## Extension Hooks

    **Optional Pre-Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```
  - **必須のフック**（`optional: false`）:
    ```
    ## Extension Hooks

    **Automatic Pre-Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}

    Wait for the result of the hook command before proceeding to the Outline.
    ```
    上記ブロックを出力した後、Outlineに進む前に、実際にそのフックを呼び出し、完了を待たなければならない。これはあなた自身がこのagent/セッションでコマンドを実行するのと同じ方法で実行する（呼び出し方法は上記に示された文字どおりの `{command}` IDとは異なる場合がある。例えばskillsモードのagentでは `/skill:speckit-...` や `$speckit-...` として実行する）。ブロックを出力するだけではフックは実行されない。
- 登録されているフックがない、または `.specify/extensions.yml` が存在しない場合は、黙ってスキップする。

## Outline

目標: アクティブな機能仕様書における曖昧さや欠落した意思決定ポイントを検出・削減し、その明確化内容を仕様書ファイルに直接記録する。

注記: このclarificationワークフローは `/speckit-plan` を呼び出す**前に**実行（かつ完了）されることが想定されている。ユーザーがclarificationを明示的にスキップすると述べた場合（例: 探索的なスパイクである等）は続行してもよいが、下流の手戻りリスクが増加することを警告しなければならない。

実行手順:

1. リポジトリルートから `.specify/scripts/bash/check-prerequisites.sh --json --paths-only` を**一度だけ**実行する（`--json --paths-only` の組み合わせモード／`-Json -PathsOnly`）。最小限のJSONペイロードのフィールドをパースする:
   - `FEATURE_DIR`
   - `FEATURE_SPEC`
   - （将来のチェーン処理のために `IMPL_PLAN`、`TASKS` を任意で取得してもよい。）
   - JSONのパースに失敗した場合は中止し、ユーザーに `/speckit-specify` を再実行するか、フィーチャーブランチ環境を確認するよう指示する。
   - "I'm Groot" のような引数中のシングルクォートには、エスケープ構文を使用する。例: 'I'\''m Groot'（可能であればダブルクォートを使用: "I'm Groot"）。

2. **存在する場合**: プロジェクトの原則やガバナンス上の制約について `.specify/memory/constitution.md` を読み込む。

3. 現在の仕様書ファイルを読み込む。以下の分類法を用いて、構造化された曖昧さ・網羅性のスキャンを行う。各カテゴリについて、状態を Clear（明確）／Partial（部分的）／Missing（欠落）としてマークする。優先順位付けに使う内部的なカバレッジマップを作成する（質問を一切しない場合を除き、生のマップをそのまま出力しない）。

   Functional Scope & Behavior（機能スコープと振る舞い）:
   - コアとなるユーザーゴールと成功基準
   - 明示的なスコープ外の宣言
   - ユーザーの役割／ペルソナの区別

   Domain & Data Model（ドメインとデータモデル）:
   - エンティティ、属性、関係
   - 識別性・一意性のルール
   - ライフサイクル／状態遷移
   - データ量／スケールに関する想定

   Interaction & UX Flow（インタラクションとUXフロー）:
   - 重要なユーザージャーニー／シーケンス
   - エラー／空／ローディング状態
   - アクセシビリティやローカライゼーションに関する注記

   Non-Functional Quality Attributes（非機能品質特性）:
   - パフォーマンス（レイテンシ、スループット目標）
   - スケーラビリティ（水平／垂直、上限）
   - 信頼性と可用性（稼働率、復旧に関する期待値）
   - オブザーバビリティ（ログ、メトリクス、トレースのシグナル）
   - セキュリティとプライバシー（認証／認可、データ保護、脅威に関する想定）
   - コンプライアンス／規制上の制約（該当する場合）

   Integration & External Dependencies（統合と外部依存）:
   - 外部サービス／APIとその障害モード
   - データのインポート／エクスポート形式
   - プロトコル／バージョニングに関する想定

   Edge Cases & Failure Handling（エッジケースと障害対応）:
   - ネガティブシナリオ
   - レート制限／スロットリング
   - 競合解決（例: 同時編集）

   Constraints & Tradeoffs（制約とトレードオフ）:
   - 技術的制約（言語、ストレージ、ホスティング）
   - 明示的なトレードオフや却下された代替案

   Terminology & Consistency（用語と一貫性）:
   - 正式な用語集の語
   - 避けるべき同義語／非推奨の用語

   Completion Signals（完了のシグナル）:
   - 受け入れ基準のテスト可能性
   - 測定可能なDefinition of Done的な指標

   Misc / Placeholders（その他／プレースホルダー）:
   - TODOマーカー／未解決の意思決定
   - 定量化を欠いた曖昧な形容詞（"robust"、"intuitive" など）

   状態がPartialまたはMissingの各カテゴリについて、以下のいずれかに該当しない限り、候補となる質問機会を追加する:
   - その明確化が実装や検証戦略を実質的に変えないと考えられる場合
   - 情報を計画フェーズに先送りしたほうがよい場合（内部的にメモしておく）

4. （内部的に）候補となる明確化質問の優先順位付きキュー（最大5件）を生成する。すべてを一度に出力しては**いけない**。以下の制約を適用する:
    - セッション全体を通じて最大5件の質問とする。
    - 各質問は、次のいずれかの方法で回答可能でなければならない:
       - 短い多肢選択（2〜5個の相互排他的で明確に区別される選択肢）、または
       - 一語／短いフレーズでの回答（明示的に制約する: "5語以内で回答してください"）。
    - 回答がアーキテクチャ、データモデリング、タスク分解、テスト設計、UXの振る舞い、運用上のレディネス、コンプライアンス検証に実質的な影響を与える質問のみを含める。
    - カテゴリのカバレッジのバランスを確保する: 未解決のカテゴリのうち影響度の高いものから優先的にカバーするよう試みる。1つの高影響領域（例: セキュリティ姿勢）が未解決のまま、低影響の質問を2つ行うことは避ける。
    - 既に回答済みの質問、些末なスタイル上の好み、計画レベルの実行詳細（正確性を阻害しない限り）は除外する。
    - 下流の手戻りリスクを減らす、あるいは不整合な受け入れテストを防ぐ明確化を優先する。
    - 未解決のカテゴリが5つを超える場合は、（Impact * Uncertainty）ヒューリスティックにより上位5件を選択する。

5. 逐次的な質問ループ（対話形式）:
    - 一度に**厳密に1問だけ**提示する。
    - **質問の書き方の品質（多肢選択・短答式のいずれにも適用）:**
       - `**Question:**` で始め、`?` で終わる完全な疑問文を続ける。`?` の前の質問文はそれ単体で意味が通らなければならない。
       - トピックラベルやセクション見出し、要件IDをそのまま質問として使っては**いけない**。例えば `Acceptance device/runtime matrix (FR-023)` は無効である ― それはラベルであって質問ではない。
       - `?` の後に許される接尾辞は、括弧書きの要件／質問IDのみである。正確な形式は `**Question:** <疑問文>?` または `**Question:** <疑問文>? (FR-023)`。IDを `?` の前に置いてはならず、ID（単独でもトピックラベルとの組み合わせでも）をプロンプト全体として使ってはならない。
       - 質問行の直後に、推奨案／選択肢の前に、平易な言葉で「Why it matters（なぜ重要か）」の一文（受け入れや出荷にとっての利害）を1文追加する。
       - 日常的な語彙を用い、専門用語を使う場合は同じ文の中で定義する。セルフチェック: Spec Kitを知らない読み手でも、Questionの行だけを読んで回答できなければならない。簡潔であることは構わないが、判じ物のようなラベルは不可。
    - 多肢選択式の質問の場合:
       - **すべての選択肢を分析**し、以下に基づいて**最も適切な選択肢**を判断する:
          - プロジェクトの種類に対するベストプラクティス
          - 類似実装における一般的なパターン
          - リスク低減（セキュリティ、パフォーマンス、保守性）
          - 仕様書に見える明示的なプロジェクトの目標や制約との整合性
       - **推奨する選択肢**を、その理由（1〜2文で、なぜそれが最良の選択かを説明）とともに目立つ形で先頭に提示する。
       - 次の形式で表記する: `**Recommended:** Option [X] - <理由>`
       - その後、すべての選択肢をMarkdownテーブルとしてレンダリングする:

       | Option | Description |
       |--------|-------------|
       | A | <選択肢Aの説明> |
       | B | <選択肢Bの説明> |
       | C | <選択肢Cの説明>（必要に応じてD/Eを最大5つまで追加） |
       | Short | 別の短い回答を提供する（5語以内）（自由記述の代替が適切な場合のみ含める） |

       - テーブルの後に以下を追加する: `You can reply with the option letter (e.g., "A"), accept the recommendation by saying "yes" or "recommended", or provide your own short answer.`
    - 短答式（意味のある離散的な選択肢がない場合）:
       - ベストプラクティスと文脈に基づいて**提案する回答**を示す。
       - 次の形式で表記する: `**Suggested:** <提案する回答> - <簡潔な理由>`
       - その後、次を出力する: `Format: Short answer (<=5 words). You can accept the suggestion by saying "yes" or "suggested", or provide your own answer.`
    - ユーザーが回答した後:
       - ユーザーが "yes"、"recommended"、"suggested" のいずれかで返答した場合は、あなたが先に述べた推奨案／提案をその回答として使用する。
       - それ以外の場合は、その回答がいずれかの選択肢に対応するか、5語以内の制約に収まっているかを検証する。
       - あいまいな場合は、簡潔な曖昧さ解消を求める（これは同じ質問のカウントに含まれ、質問を先へは進めない）。
       - 満足のいく回答が得られたら、それを作業メモリに記録し（まだディスクには書き込まない）、次のキュー内の質問に進む。
    - 以下のいずれかに該当する場合、それ以上の質問を停止する:
       - すべての重大な曖昧さが早期に解消され、キューに残っている項目が不要になった場合、または
       - ユーザーが完了の意思を示した場合（"done"、"good"、"no more" など）、または
       - 質問数が5件に達した場合。
    - 今後のキュー内の質問を事前に明かしてはならない。
    - 開始時点で有効な質問が存在しない場合は、直ちに重大な曖昧さがない旨を報告する。

6. 各回答が受理されるたびの統合処理（インクリメンタルな更新アプローチ）:
    - 仕様書のインメモリ表現（開始時に一度だけ読み込む）と生のファイル内容の両方を保持する。
    - このセッションで最初に統合される回答については:
       - `## Clarifications` セクションが存在することを確認する（存在しない場合は、仕様書テンプレートに沿って、最上位の文脈／概要セクションの直後に作成する）。
       - その下に、（存在しなければ）今日の日付の `### Session YYYY-MM-DD` 見出しを作成する。
    - 受理された直後に、次の形式で箇条書きを追加する: `- Q: <question> → A: <final answer>`。
    - その後、直ちにその明確化を最も適切なセクションに反映する:
       - 機能上の曖昧さ → Functional Requirements内の箇条書きを更新または追加する。
       - ユーザーインタラクション／アクターの区別 → User Storiesまたは（存在すれば）Actorsサブセクションを、明確化された役割・制約・シナリオで更新する。
       - データの形状／エンティティ → Data Modelを更新する（フィールド、型、関係を追加）。順序は保持し、追加された制約は簡潔に記す。
       - 非機能的な制約 → Success Criteria > Measurable Outcomesに測定可能な基準を追加／修正する（曖昧な形容詞をメトリクスや明示的な目標値に変換する）。
       - エッジケース／ネガティブフロー → Edge Cases / Error Handlingの下に新しい箇条書きを追加する（テンプレートにそのためのプレースホルダーがあれば、そのサブセクションを作成する）。
       - 用語の衝突 → 仕様書全体で用語を正規化する。必要な場合のみ、一度だけ `(formerly referred to as "X")` を付記して元の用語を残す。
    - その明確化が以前の曖昧な記述を無効化する場合は、重複させるのではなくその記述を置き換える。矛盾する古い文言を残してはならない。
    - コンテキスト消失のリスクを最小化するため、各統合の**後に**仕様書ファイルを保存する（アトミックな上書き）。
    - フォーマットを保持する: 無関係なセクションを並べ替えず、見出しの階層をそのまま保つ。
    - 挿入する各明確化は最小限かつテスト可能なものにする（説明の肥大化を避ける）。

7. 検証（各書き込み後および最終パスの後に実施）:
   - Clarificationsセッションには、受理された回答ごとに厳密に1つの箇条書きが存在すること（重複なし）。
   - 質問（受理済み）の総数が5件以下であること。
   - 更新されたセクションに、新しい回答が解消するはずだった曖昧なプレースホルダーが残っていないこと。
   - 矛盾する以前の記述が残っていないこと（無効になった代替案が削除されているかスキャンする）。
   - Markdownの構造が妥当であること。追加を許される見出しは `## Clarifications`、`### Session YYYY-MM-DD` のみであること。
   - 用語の一貫性: 更新されたすべてのセクションで同じ正式な用語が使われていること。

8. 更新された仕様書を `FEATURE_SPEC` に書き戻す。

9. **仕様品質チェックリストの再検証**（存在する場合）:
   - `FEATURE_DIR/checklists/requirements.md` が存在するか確認する。
   - 存在**しない**場合は、このステップを黙ってスキップする。
   - 存在する場合:
     1. チェックリストファイルを読み込む。
     2. コードフェンスの外にある、GitHubのタスクリスト形式のチェックボックス行 ― `- [ ]`、`- [x]`、`- [X]` にマッチする行（大文字小文字を区別せず、ネストされた項目の先頭の空白も許容する）をすべて特定する。それ以外の内容（見出し、注記、チェックボックスでない箇条書き、メタデータ）は無視する。
     3. 各チェックボックス行について、現在のマーカー状態（チェック済みか未チェックか）と項目のテキストを、変更前のスナップショットリストとして記録する。
     4. 各チェックボックス項目を、**更新後の**仕様書（ステップ7で保存されたばかりのバージョン）に照らして再評価する。
     5. 各チェックボックス項目について、チェック済み／未チェックの状態が実際に変わった場合のみ更新する:
        - その項目が今は合格していて、以前は未チェックだった場合: `[ ]` を `[x]` に変更する。
        - その項目が今は不合格で、以前はチェック済みだった場合: `[x]`／`[X]` を `[ ]` に変更する。
        - 状態が変わらない場合は、マーカーをそのままにする（見た目上の差分を避けるため、既存の大文字小文字はそのまま保持する）。
     6. 更新後のチェックリストファイルを保存する。**状態が変化したチェックボックス行の `[ ]`／`[x]` マーカー部分のみを切り替える。**それ以外のファイル内容 ― 見出し、メタデータ、注記、行の順序、空白 ― は、ノイズの多い差分を避けるためすべて変更してはならない。
     7. 変更前のスナップショットと現在の状態を比較し、Completion Reportのために以下の3つのリストを算出する:
        - **Newly passing（新たに合格）**: 未チェックからチェック済みに変わった項目。
        - **Regressions（後退）**: チェック済みから未チェックに変わった項目。
        - **Still unchecked（依然として未チェック）**: 未チェックのまま残っている項目。
     8. 変更前後の合格数を、チェック済み／総チェックボックス項目数として記録する（例: "12/16 → 15/16 items passing"）。

Behavior rules（振る舞いのルール）:

- 意味のある曖昧さが見つからない場合（または、考えられるすべての質問が低影響である場合）は、次のように返答する: "No critical ambiguities detected worth formal clarification."（正式な明確化に値する重大な曖昧さは検出されませんでした）そして先に進むことを提案する。
- 仕様書ファイルが存在しない場合は、ユーザーにまず `/speckit-specify` を実行するよう指示する（ここで新しい仕様書を作成してはならない）。
- 質問の総数は5件を超えてはならない（1つの質問に対する再質問は、新しい質問としてカウントされない）。
- 機能的な明確さを阻害しない限り、投機的な技術スタックに関する質問は避ける。
- ユーザーによる早期終了のシグナル（"stop"、"done"、"proceed"）を尊重する。
- 網羅性が十分であるため質問が行われなかった場合は、簡潔なカバレッジサマリー（すべてのカテゴリがClear）を出力し、その後、先に進むことを提案する。
- 上限に達した時点で未解決の高影響カテゴリが残っている場合は、それらを理由とともにDeferred（先送り）として明示的にフラグを立てる。

## Mandatory Post-Execution Hooks

**このセクションは、ユーザーに完了を報告する前に必ず完了させなければならない。**

プロジェクトルートに `.specify/extensions.yml` が存在するか確認する。
- 存在しない場合、または `hooks.after_clarify` の下にフックが登録されていない場合は、Completion Reportへスキップする。
- 存在する場合は読み込み、`hooks.after_clarify` キー配下のエントリを探す。
- YAMLがパースできない、または不正な場合は、フックの確認を黙って省略し、Completion Reportへ続行する。
- `enabled` が明示的に `false` になっているフックは除外する。`enabled` フィールドがないフックはデフォルトで有効として扱う。
- 残った各フックについて、フックの `condition` 式を解釈・評価しようと**しない**こと。
  - フックに `condition` フィールドがない、またはnull/空である場合は、そのフックを実行可能として扱う。
  - フックが空でない `condition` を定義している場合は、そのフックをスキップし、条件評価はHookExecutorの実装に委ねる。
- フックのコマンド名からコマンド呼び出しを組み立てる際は、ドット（`.`）をハイフン（`-`）に置き換える。例えば `speckit.git.commit` → `/speckit-git-commit`。
- 実行可能な各フックについて、`optional` フラグに応じて以下を出力する。
  - **必須のフック**（`optional: false`） ― **必須の各フックについて `EXECUTE_COMMAND:` を必ず出力しなければならない**:
    ```
    ## Extension Hooks

    **Automatic Hook**: {extension}
    Executing: `/{command}`
    EXECUTE_COMMAND: {command}
    ```
    上記ブロックを出力した後、実際にそのフックを呼び出し、完了を待たなければならない。これはあなた自身がこのagent/セッションでコマンドを実行するのと同じ方法で実行する（呼び出し方法は上記に示された文字どおりの `{command}` IDとは異なる場合がある。例えばskillsモードのagentでは `/skill:speckit-...` や `$speckit-...` として実行する）。ブロックを出力するだけではフックは実行されない。
  - **任意のフック**（`optional: true`）:
    ```
    ## Extension Hooks

    **Optional Hook**: {extension}
    Command: `/{command}`
    Description: {description}

    Prompt: {prompt}
    To execute: `/{command}`
    ```

## Completion Report

完了を報告する（質問ループの終了後または早期終了後）:
- 質問した数と回答された数。
- 更新された仕様書へのパス。
- 変更が加えられたセクション（名称のリスト）。
- 仕様品質チェックリストの状態（`FEATURE_DIR/checklists/requirements.md` が再検証された場合）: 変更前後の合格数を示し（例: "Spec Quality Checklist: 12/16 → 15/16 items passing"）、状態が変化した項目 ― 新たにチェックされたもの（未チェック→チェック済み）と後退したもの（チェック済み→未チェック）の両方をリストする。未チェックのまま残る項目があれば、対応が必要な領域としてリストする。
- 各分類法カテゴリと、その状態（Resolved: PartialまたはMissingだったものが対応された、Deferred: 質問数の上限を超えたか計画フェーズに適している、Clear: 既に十分である、Outstanding: 依然としてPartialまたはMissingだが影響度が低い）を一覧にしたカバレッジサマリーテーブル。
- OutstandingまたはDeferredの項目が残っている場合、`/speckit-plan` に進むべきか、計画後にあらためて `/speckit-clarify` を実行すべきかを推奨する。
