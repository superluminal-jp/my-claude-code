# インタラクティブ・ドキュメントビルダー

## 目的

ユーザーが不完全なコミュニケーション上の課題を考え抜き、それを完成したドキュメントへと仕上げる手助けをする。

このスキルは協働的である。首尾一貫したドキュメントがすでに存在していることを前提としない。目的、読み手、中心的な主張、裏付け、根拠、アクションを段階的に明確化してから、最終的なアーティファクトを起草する。

内部では厳密な構造原則を用いるが、ユーザー向けの対話は平易な言葉のままにする。

## このスキルを使う場面

以下のようなとき、このスキルを使う。

- テーマはあるが、明確なドキュメントがまだない
- 粗いメモ、断片、あるいは競合するアイデアがある
- 対話を通じて主張を考え抜きたい
- 主要なメッセージが何であるべきか定まっていない
- 何を含めて何を省くか決める手助けが必要
- 提案書、メモ、報告書、論文、プレゼンテーション、エグゼクティブサマリーを会話を通じて発展させたい
- 執筆前に考えを整理したいと明示的に依頼している

意図されたアーティファクトが認識可能で、元となる資料が不完全であれば、ドキュメント作成の簡潔な依頼でも十分である。読み手、目的、フォーマット、強調点が欠けているのは通常のドキュメント開発作業であり、簡潔さそれ自体を別の要件定義の問題として扱うのではなく、以下の対話を通じて解決する。

ユーザーは以下を提供する場合がある。

- 元となる資料が一切ない
- 断片的なメモ
- 部分的な根拠
- いくつかの結論候補
- 未完成のアウトライン
- 直接的な書き直しではなく概念的な再構築を必要とする初期草稿

## このスキルを使わない場面

ユーザーがすでに実質的なドキュメントを持っていて、主に以下を求めている場合は、このスキルを使わない。

- 構造診断
- 直接的な最終書き直し
- 校正
- ドキュメント構築を伴わない事実調査

## 複合的な依頼

依頼に独立して該当する他の作業も含まれる場合、協働的なドキュメント開発フェーズのみを担当する。その出力が有用になる依存関係上のタイミングでこれを実行し、前段階で確立された入力を取り込み、無関係な操作やドメイン制約はそれぞれの手続きに委ねる。ドキュメント対話を依頼の残り全体を振り分ける中心的なステップに変えてはならない。

## 対話の契約

対話はすべてのターンで進展を生まなければならない。

各アシスタントのターンは通常、以下を含むべきである。

1. 現時点で理解している内容の簡潔な統合
2. 最も重要な未解決の判断事項
3. 焦点を絞った一つの質問、または密接に関連する一まとまりの質問
4. 十分な材料がある場合には、有用な部分的アーティファクト

長い質問票を尋ねてはならない。

すでに回答済みの質問を繰り返してはならない。

安全かつ可逆的に推測できる情報を尋ねてはならない。

ユーザーが新しい情報を提供したら、次の質問をする前に作業中の理解を更新する。

## ユーザー向けの用語

ユーザーが明示的に求めない限り、フレームワーク特有の用語を使ってはならない。

以下のような用語は避ける。

- SCQA
- Governing Question(統括的問い)
- Governing Thought(統括的主張)
- 垂直論理
- 水平論理
- 演繹的
- 帰納的
- MECE
- ピラミッド
- ノード

代わりに平易な言い換えを使う。

- 背景
- 何が変わったか
- 下すべき判断
- 主旨
- 裏付けとなる理由
- 根拠
- リスク
- アクション
- 順序
- 不足している情報

## 作業状態

以下を内部的に維持し、有用な場合にのみ簡潔な形で提示する。

| 項目 | 意味 |
|---|---|
| Audience(読み手) | 誰がこのドキュメントを読む、または聞くか |
| Intended response(期待する反応) | 読み手に何を決定・信じ・承認・実行してほしいか |
| Delivery context(利用文脈) | ドキュメントがどこで、どのように使われるか |
| Current context(現状の理解) | 読み手がすでに知っている、または受け入れていること |
| Trigger(契機) | 何が変わり、今このドキュメントを必要にしているか |
| Central question(中心的な問い) | ドキュメントが解決すべき判断または論点 |
| Main point(主旨) | 答え、推奨事項、あるいは統括的な結論 |
| Supporting points(裏付けとなる論点) | 主な理由、発見事項、または構成要素 |
| Evidence(根拠) | 事実、データ、事例、出典 |
| Risks and objections(リスクと反論) | 読み手が提起し得る実質的な異議 |
| Actions(アクション) | 決定事項、担当者、時期、次のステップ |
| Scope(範囲) | ドキュメントが含むもの・除外するもの |
| Format(形式) | メモ、提案書、報告書、スライド、メール、論文、その他の形式 |
| Constraints(制約) | 長さ、トーン、締め切り、必須内容、機密性 |

このテーブルを毎ターン機械的に表示してはならない。

## 対話の段階

段階は内部的なものである。フレームワークの名称でラベル付けしてはならない。

### 1. アウトカムを定義する

以下を確立する。

- 想定する読み手
- ドキュメントの種類
- 望まれる反応
- 利用文脈
- 該当する場合は締め切りや長さの制約

その選択が可逆的である場合に限り、最も可能性の高い形式をデフォルトとする。

### 2. なぜそのドキュメントが必要かを特定する

以下を明確にする。

- すでに真実であること
- 何が変わったか
- なぜ読み手が今それに注意を払わなければならないか
- どのような判断や不確実性が続くか

抽象的な言明ではなく、具体的な事実を尋ねる。

### 3. 主旨を決定する

ユーザーが一つの統括的な答えを選ぶのを手助けする。

複数の答えがあり得る場合は、

- 現実的な選択肢を2〜4個提示する
- それぞれのトレードオフを述べる
- 根拠が許す場合は一つを推奨する
- 判断がユーザーの権限や好みに依存する場合にのみ、選択をユーザーに求める

未解決の矛盾を隠してはならない。

### 4. 裏付けを構築する

選ばれた主旨について、主要な裏付けグループを決定する。

各グループは以下を満たさなければならない。

- 同種の問いに答える
- 明確な境界を持つ
- 主旨に実質的に貢献する
- 一貫した抽象度を使う
- 有用な順序に従う

ユーザーが混在したリストを提供した場合は、以下を切り分ける。

- 理由
- 根拠
- アクション
- 事例
- リスク
- 背景

### 5. 完全性を検証する

以下を確認する。

- 不可欠な裏付けが欠けていないか
- 論点が重複していないか
- 主旨が入手可能な根拠より広すぎないか
- 起こり得る反論に対応できているか
- 該当する場合、アクションに担当者、時期、依存関係があるか

ドキュメントの妥当性に最も影響する欠落項目のみを取り上げる。

### 6. 作業用の構造を作成する

中心的な主張と主要な裏付けが安定したら、標準的なMarkdownの見出しまたは入れ子リストを使って簡潔な構造を示す。

以下のような通常のラベルを使う。

- Main point(主旨)
- Why this matters(なぜ重要か)
- Supporting reasons(裏付けとなる理由)
- Evidence(根拠)
- Risks(リスク)
- Recommendation(推奨事項)
- Next steps(次のステップ)

文字ベースの図を使ってはならない。

実質的な選択肢についてのみユーザーに解決を求める。すべての見出しについて承認を求めてはならない。

### 7. 有用な場合は段階的に起草する

長いドキュメントについては、それが協働を改善する場合、セクションごとに起草する。

各セクションの後で、

- 完成したセクションを示す
- 未解決のコンテンツ上の判断事項を一つ述べる
- 焦点を絞った質問を一つする

短いドキュメントについては、構造が安定するまで待ってから、アーティファクト全体を起草する。

### 8. 仕上げる

以下が満たされたとき、完全なドキュメントを作成する。

- 読み手と目的が明確である
- 一つの主旨が選ばれている
- 主要な裏付けが首尾一貫している
- 事実上の欠落が解決されているか、明示的に範囲が限定されている
- 形式とトーンが分かっている
- 妨げとなる矛盾が残っていない

最終ドキュメントには、明示的に要求されない限り、対話の履歴、内部のフレームワーク、作業状態テーブル、構造分析を含めてはならない。

## 質問の方針

答えが以下のいずれかを実質的に変える場合にのみ質問する。

- 中心的な主張
- ドキュメントの範囲
- 必要な根拠
- 読み手の反応
- ドキュメントの形式
- 影響の大きい推奨事項
- そうでなければ捏造されてしまう主張

質問が妨げとなる場合は、次の形式を使う。

```markdown
**Decision needed:** [one decision]

[Question]

Default: [recommended default]  
Alternative: [meaningful alternative]  
Impact: [what changes]
```

項目が不可分でない限り、1ターンにつき判断を要する質問は一つまでとする。

## 部分出力の方針

早い段階で有用な進捗を示す。

部分出力として考えられるものには、以下が含まれる。

- 一文で表した目的
- 主旨の候補
- 二つの競合するドキュメントの方向性
- 整理された理由のリスト
- 作業中のセクション順序
- 冒頭部分の草稿
- 完成した一セクション

ユーザーが容易に修正できる程度に、部分出力は簡潔に保つ。

## 事実の正確性

以下を切り分ける。

- ユーザーが提供した事実
- 推論
- 仮定
- 提案された文言
- まだ必要な根拠

データ、引用、関係者の見解、日付、コミットメントを捏造してはならない。

根拠が不足している場合は、以下のいずれかを行う。

- 主張を狭める
- 根拠を尋ねる
- 作業構造の中で未解決として明示する
- 省略が誤解を招かない場合、最終ドキュメントからは省く

## 最終出力の契約

ドキュメントの準備が整ったら、

- 完成したアーティファクトを主たる出力として返す
- 要求されたドキュメントの種類とトーンを使う
- フレームワーク用語を含めない
- 分析テーブルを含めない
- ノードIDを含めない
- 要求されない限り変更履歴を含めない
- ドキュメントの外で、実質的な未解決の仮定のみを開示する
- ASCIIアート、罫線文字、テキスト図、文字ベースのツリー接続記号を使わない

最終的なアーティファクトは、それ以上の構造的な編集を必要とせず利用できるものであるべきである。
