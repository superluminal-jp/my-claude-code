# Secure Logging — Claude Code スキルとプラグイン

アプリケーションのログを、OWASP Logging Cheat Sheet、OWASP ASVS 5.0.0 V16、関連する CWE と、Python・React・AWS Lambda と CDK・Google Cloud（Cloud Run functions を含む）・Azure（Azure Functions を含む）・各クラウドの AI 推論サービス・GitHub Actions のワークフローの公式ドキュメントにあるログの作法に照らして実装・変更・レビューするための Claude Code スキルです。ドメインオーバーレイとして働き、実装・レビュー・文書の作業を置き換えるのではなく補います。同じフォルダーは Claude Code プラグインでもあり、フックは登録しません（[チェックの仕組み](#チェックの仕組み)を参照）。

## インストール

個人インストール（自分のすべてのプロジェクト）:

```bash
cp -R secure-logging ~/.claude/skills/
```

プロジェクトインストール（リポジトリをクローンする全員）:

```bash
mkdir -p .claude/skills
cp -R secure-logging .claude/skills/
```

フォルダーに `.claude-plugin/plugin.json` があるため、Claude Code はどちらの場所からでも skills ディレクトリのプラグイン（`secure-logging@skills-dir`）として読み込み、スキル（`SKILL.md`）が使えるようになります。`claude plugin list` では *Skills-directory plugins* の下に表示されます。

- 個人インストールのコピーは、同じプラグイン名を持つため、プロジェクトインストールのコピーを隠します。このとき `claude plugin list` はプロジェクトのコピーを未読み込みと表示します。プロジェクトのコピーを使うには、個人のコピーの名前を変えるか移動します。
- ファイルを残したままプラグインを無効にするには、設定ファイルで `"enabledPlugins": {"secure-logging@skills-dir": false}` を指定します。

その他の読み込み方法として、1セッションだけ使う `claude --plugin-dir ./secure-logging` と、プラグインマーケットプレイスでの公開があります。これらから読み込んだ場合、スキル名は `/secure-logging:secure-logging` になります。

## 必要なもの

- Claude Code。プラグインは Markdown とマニフェストだけで構成されているため、実行環境や依存関係は不要です。
- 検査には、対象プロジェクト自身のテストランナー、linter、型チェッカーを使います。

## 構成

- `SKILL.md` — 適用範囲、ワークフロー、例外的なケース、完了条件。
- `README.md`、`README.ja.md` — このガイドの英語版と日本語版。両方を同期させる。
- `.claude-plugin/plugin.json` — プラグインのマニフェスト。
- `references/logging-checklist.md` — 出典とチェックリスト。コードから判定する group A のセキュリティ項目（`LOG-INV`、`LOG-EVT`、`LOG-ATT`、`LOG-DATA`、`LOG-INJ`、`LOG-ERR`、`LOG-CFG`、`LOG-TST`）、同じくコードから判定するスタックの作法の項目（`LOG-PRC`）、運用に関する group B の項目（`LOG-OPS`）。

## 適用範囲

- コードやワークフローがログ出力、セキュリティイベントの記録、監査証跡、ログを出すエラー処理、ログ設定（インフラコード（AWS CDK、Terraform、Bicep）にあるログ関連のリソースを含む）を追加・変更するとき、およびログがベストプラクティスに沿っているかを問われたときに使います。
- ログ基盤の運用（SIEM、アラートの調整）、ログやトレースの内容を記録しない可観測性の作業（メトリクスの設計）、ログの振る舞いに触れない変更には使いません。
- スタックの作法の項目（`LOG-PRC`）が扱うのは、Python、React、AWS Lambda と CDK、Google Cloud（Cloud Run、Cloud Run functions、Node.js）、Azure（Azure Functions を含む）、AI 推論サービス（Amazon Bedrock、Vertex AI、Azure AI Foundry）、GitHub Actions のワークフローです。多くはセキュリティ要求ではありませんが、*Security impact* 列にセキュリティ項目が書かれた項目は、セキュリティの不合格として数え、その順位で示します。TypeScript は実行環境の項目に従います。Java や Go など他のスタックには、セキュリティ項目だけを適用します。
- チェックリストに含まれない規格（ISO/IEC 27002、PCI DSS、NIST SP 800-53 など）は、一次資料を読んでいないため対応付けません。

## モード

| モード | 使う場面 | ワークフローのステップ |
|---|---|---|
| レビュー | ログが適切かどうかを問われたとき | 2（棚卸し）と 5（検査）。何も変更しない |
| 実装・修正 | ログの変更を求められたとき。指摘の修正も含む | 2〜6 |

対象が指定されていない場合は、作業ツリーの差分があればそれを、なければリポジトリ全体を対象とし、そのことを報告に書きます。

## チェックの仕組み

ワークフローの正本は `SKILL.md`、要求の正本は `references/logging-checklist.md` です。この節は、それらがどう検査されるかをまとめたものです。

チェックはスキルが呼び出されたときにだけ行われます。Claude が `SKILL.md` に従い、対象のコードをチェックリストに照らして評価します。プラグインはフックを登録しないため、自動では何も動きません。機械的な検査は、契約を自動化できる場合に Claude が先に書くテストと、プロジェクト自身のテスト、linter、型チェックです。それ以外の判定は Claude がコードを読んで下すため、実装モードでは自己点検にとどまります。

### ワークフロー内のチェック

| ワークフローのステップ | 確認する内容 | 方法 |
|---|---|---|
| 1. 範囲の確定 | コードが使う言語、フレームワーク、ログライブラリ、実行環境、AI 推論サービス、インフラコード、CI ワークフロー | Claude がプロジェクトを読む。見つかったスタックで、適用する `LOG-PRC` の項目が決まる |
| 2. 棚卸し | 共通のログ入口、直接の print や場当たり的なログ呼び出し、記録済みのイベント、マスキング用の補助関数、ログのテスト | Claude がコードを読む。棚卸しは両モードの基準になる |
| 4. 実装 | イベント、必須の属性、秘密情報の見本値のマスキング、CR・LF・区切り文字を含む入力の無害化 | 契約を自動化できる場合は、先に書いて失敗を確認したテスト。できない場合は、現在の振る舞いと、変更をどう確認するかを記録する |
| 4. 実装 | プロジェクトのテスト、linter、型チェック | Claude がステップ 5 の前に実行する |
| 5. 検査 | 対象に関わるチェックリストの全項目 | Claude が各項目に根拠付きで1つの判定を付ける |
| 5. 検査 | プロジェクトのツールで決められる項目 | `LOG-PRC` の項目にはプロジェクト自身の linter とテストを、インフラコードには AWS CDK のテンプレートへのアサーションか、plan モードの `terraform test` を使う。Bicep はテストフレームワークが実験的機能なので、値はファイルを読んで確かめる。検査を実行する CI ワークフローも根拠に数え、そのファイルを挙げる。そのためにツールを追加することはしない |
| 5. 検査（実装モード） | 変更で追加・修正したコードでの Fail | 報告を止める。Claude が直して再検査し、同じ Fail が2回続けて残ったら、残存として報告する。変更していないコードの Fail は既存として報告し、求められた場合だけ直す |
| 5. 検査（実装モード） | 対象が認証・決済・個人データを扱う場合の独立性 | 別のコンテキストのサブエージェントが、group A の項目を差分に照らして評価する。サブエージェントを使えない場合は、自己点検のみの結果だと報告に書く |

### 判定

| 判定 | 意味 | 根拠 |
|---|---|---|
| Pass | 満たしている | `file:line` か、それを示すテスト |
| Fail | 対象のコードで違反している、または欠けている | 場所と項目 ID |
| N/A | その条件が対象で起こらない | 理由 |
| Unverified | group B の項目、または根拠を得られない group A の項目 | 判断に必要な証拠 |

group B の項目（保存先の権限、転送、保存期間、時刻同期、改ざん検知、アラート、ネットワーク分離）は、アプリケーションのコードだけでは Pass にしません。リポジトリ内のインフラコードやログ設定で決まる場合にだけ判定し、そのファイルを根拠に挙げます。チェックリストは、これらの項目を AWS CDK（合成した CloudFormation）、Google Cloud の Terraform、Azure の Bicep の属性に対応付けています。この根拠が示すのは宣言された設定であり、デプロイ後の状態ではありません。GitHub Actions などのパイプラインだけがクラウドを変更する経路とは限らないため、報告にはそのことを書きます。宣言された保存期間で LOG-OPS-6 を判定できるのは、法令や契約が求める期間を利用者が示した場合だけです。GitHub Actions のログの保存期間はコードではなくリポジトリの設定なので、ワークフローログの LOG-OPS-6 は Unverified のままとし、確認すべき設定を報告に書きます。Unverified を推論で Pass にすることはありません。

### 報告と完了

報告は結論から始めます。Fail と Unverified の件数、最も重大な不合格を示し、実装モードでは残存の Fail と既存の Fail を分け、`LOG-PRC` の Fail はセキュリティの Fail と分けて数え、セキュリティを先に示します。ただし、セキュリティへの影響がある `LOG-PRC` の項目は、セキュリティの Fail として数えます。続いて、チェックリスト順の項目表（N/A の項目はチェックリストの節ごとに ID を並べた1行にまとめてよい）、実施した変更と実行した検査の結果、利用者が用意すべき group B の証拠、検査しなかった範囲を書きます。

実装が完了したといえるのは、全項目に判定があり、変更で追加・修正したコードについて `LOG-DATA-1`、`LOG-DATA-2`、`LOG-INJ-1`、`LOG-INJ-4` が Pass か N/A で、先に書いたテストが通り、プロジェクトの検査も通る場合だけです。停止条件に達してもこれらのいずれかが Fail のままなら、作業は未完了だと報告に書きます。

### このプラグインが強制しないもの

| 仕組み | このプラグインでの状態 |
|---|---|
| フック | なし。ワークフローはスキルが呼び出されたときにだけ動く |
| 振る舞い eval | 同梱していない。モデルがワークフローに従うかどうかは自動では測定しない |
| 独立したレビュー | 上記の別コンテキストでの評価だけで、対象が認証・決済・個人データを扱う場合に限る |

各判定が正しいかどうかを支えるのは、Claude がコードを読んでの確認、先に書くテスト、該当する場合の別コンテキストでの評価、人によるレビューです。

## 検証

このフォルダーから次を実行します:

```bash
claude plugin validate --strict .
```

## セキュリティ

プラグインは Markdown とマニフェストだけで構成されており、スクリプト、フック、実行ファイルは含みません。スキルは Claude に対し、秘密情報、トークン、セッション識別子、個人データを平文でログに出さないこと、運用に関する項目をアプリケーションのコードだけで合格にしないことを指示します。
