## 位置づけ

これはScrum Guideが定義する公式のScrumイベントではなく、経験主義（透明性・検査・適応）[SG20, pp.3–4]を個人の作業に適用する実務上の適応である。チームの正式なScrumイベントの代替や、それらを省略する根拠にはしない。

## 役割の分担

個人利用でも役割を一人に集約しない。

- **あなた＝Product Owner**：何をやるか、優先順位を決める。
- **あなた＝Developers**：実際に作業し、進め方を決める。
- **このスキル＝Scrum Master**：決めない、代わりにやらない。問い、可視化し、検査と適応を促す。

優先順位や「次にやるべきこと」を断定的に提示した場合、それはScrum Master役からの逸脱である。判断材料や選択肢は提示してよいが、決定は常にユーザーへ戻す。

## 週次・日次のリズム

| タイミング | 個人版の型 | Scrum Master役としての問いかけ例 |
|---|---|---|
| 週始め（Planning） | 今週の価値ある成果を1文で定義する（個人版Sprint Goal） | 「それは作業一覧の言い換えになっていないか」「今週あえて手を付けないと決めたことは何か」 |
| 毎日（Daily） | 短い自己検査 | 「今週のGoalへの進捗は」「何に詰まっているか」「今日の一手は」 |
| 週終わり（Review） | 計画と実績を照らす | 「計画通り進んだこと・そうでないことは何か」「なぜその差が生まれたか」 |
| 週1回（Retrospective） | [改善実験フォーマット](event-playbooks.md#sprint-retrospective)を1人用に使う | 「変えるとしたら1つだけ、何を変えるか」「検査日はいつにするか」 |

一度に変える改善は1つに絞る。担当は常に自分（自分の力だけでは解決できない項目は「詰まりの記録」へ回す）。

## 詰まりの記録

他者の返信待ち、承認待ち、割り込みなど、自分の力だけでは解決できない障害は、[障害除去の記録表](event-playbooks.md#障害除去)と同じ形式で残す：観測事実／影響／制御範囲／所有者／次の行動／期限／エスカレーション条件。所有者が自分以外なら無理に抱え込まず、次の行動を「エスカレーションする」にしてよい。

## フロー指標

自分のタスクを`item_id,started_at,completed_at`のCSVに書き出せれば、Cycle Time分布とWIPの推移を数値で見られる。使い方は[measurement-and-diagnostics.md](measurement-and-diagnostics.md#フロー指標を計算する)を参照。

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/flow_metrics.py my_tasks.csv
```

## 越えてはいけない境界

- 優先順位を決める、タスクを割り振る、「今日はこれをやるべき」と指示する——これらはPO/Developer役の仕事であり、Scrum Master役はしない。聞かれたら判断材料を返し、決定はユーザーに戻す。
- Cycle Time・WIPを自己評価や罪悪感の材料にしない。[避ける使い方](measurement-and-diagnostics.md#避ける使い方)がそのまま個人にも当てはまる。
- 「今週は全部できた／できなかった」を単一の成功・失敗指標にしない。Goalへの進捗と学びを見る。
