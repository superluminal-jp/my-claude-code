# Requirements decomposition

A change may start only when its problem is backed by evidence, its requirements trace to that problem, and every objection raised against them has been answered. This skill produces the three records that make this checkable — a problem card, a requirements graph, and a challenge report — and runs the bundled checker's gate over them. The gate is deterministic; finding meaning errors (a solution stated as the problem, a parent that fails while all its children pass) is the challenger's job, and the challenger is a model whose errors can correlate with yours.

## Steps

Work in this order. Each step names the file it writes; keep the files together, for example under the project's spec or change directory. Run the checker after each step: `python3 <skill-dir>/scripts/check_graph.py FILE`, where `<skill-dir>` is this skill's base directory (Claude Code shows it when the skill loads) (exit 0 passes, 1 lists violations, 2 means the file cannot be read). The formats and every rule are in [references/checker.md](references/checker.md); [examples/](examples/) has one complete set whose gate is ready.

1. **Problem card** (`problem-card.json`). Start from a problem statement the person has agreed to; if there is none, stop and define the problem first, which is a separate capability. Copy the ideal state, the current state, the gap, and why it matters. Put every observation that supports the current state in `evidence` with its source (a test, a log, a scanner alert, a reproduction), and every observation against it in `counter_evidence`. Keep causes in `hypotheses` and fixes in `proposed_solutions`; never let either leak into `gap`. Set `status` to `verified` only when the evidence shows the current state, `refuted` when counter-evidence shows the problem does not exist as stated, and `unverified` otherwise; explain the status in `status_rationale` whenever there is counter-evidence.
2. **Requirements graph** (`requirements-graph.json`, `schema_version` 2 with the card's id as `problem_id`). Make one root: the requirement that closes the gap. Decompose with `AND` when every child is needed and `OR` only for real alternatives, giving each alternative its selection condition and scope. Give every parent its own acceptance criterion at `L2` (integration across its children) or `L3` (the whole system), never only its children's `L1` tests, and list in `counterexamples` how all children could pass while the parent fails. Give a criterion that can only be verified after the change is deployed (a value observed in production, for example) `"stage": "post_deploy"`, so that the decision before deploy can leave it out; decide this here, where the challenger sees it, and never move a criterion that could be verified earlier. Give every requirement, and every parent's own `L2` or `L3` level, at least one criterion verifiable before deploy as well, or the decision before deploy stays blocked for it. When a person directed a requirement rather than it following from the gap, record who and where in `origin` (`{"kind": "instruction", "by": "<the person>", "ref": "<where the direction can be read: a conversation's date and question, an issue, a decision record>"}`); never put `origin` on a requirement you derived yourself, and never name an agent in `by`. Stop decomposing a node when it is one requirement with a clear acceptance criterion that can be verified on its own with a small change. The graph is the only place for the acceptance criteria: in a project that also keeps a specification (for example spec-kit's `spec.md`), the specification cites the graph's acceptance ids instead of restating them.
3. **Challenge** (`challenge-report.json`). Run it when the change touches authentication, authorization, secrets or personal data, data migration, infrastructure permissions, or anything hard to undo; when the evidence is thin or contested; or when the same agent wrote the card and the graph and will implement them. Write a copy of the card without `proposed_solutions` (for example `problem-card.challenger.json`). Start a new `read-only-reviewer` subagent (with the plugin's prefix, such as `<plugin>:read-only-reviewer`, when these skills came as a plugin); its definition allows only Read, Grep, and Glob and starts it without CLAUDE.md (a CLAUDE.md in a directory whose files it reads still loads, as do the MCP servers' instructions). If no subagent of that name is available, stop and tell the person; do not start another type in its place. Give it the prompt in [references/challenger.md](references/challenger.md) with the paths of that copy and the graph and the language the records are written in — not the proposed solutions or the planned implementation, so it cannot inherit your fix. It did not review when it ended with an error, was stopped or timed out, answered `NOT REVIEWED`, returned anything but the JSON the prompt asks for, or left a file it was given out of that JSON's `read`: start a new one once more with the same input, and if that also fails, write no report, stop, and tell the person the challenge did not run. Copy its findings into the report, as they are, as `open`; the report's `findings` is empty only when the challenger read both files and returned no finding. In `reviewer`, write the subagent type, the agentId the Agent tool returned, the date, and how many files it read. Then answer each one: fix the card or the graph and mark it `accepted` with what changed, or mark it `rejected` with the reason. Reject a finding only for one of two reasons: the line of the problem card or the graph that shows the finding does not hold, cited by field; or a decision you asked the person for, written with who answered, when, and their words, and added to the card's `evidence`. Never write as the person's decision what the person has not answered. When the reason rests on something neither file shows (a conversation, a convention, a system you can read and the challenger cannot), add it to the card's `evidence` with its source and cite that, or ask the person. You wrote what is under review: wanting to reject a finding is not evidence that it is wrong. Never delete a finding.
4. **Gate**. Run `python3 <skill-dir>/scripts/check_graph.py --gate problem-card.json requirements-graph.json [challenge-report.json]`. On `ready`, hand the requirements graph to implementation, which is a separate capability, and report the gate result with `challenge: recorded` or `challenge: not_run` as it is. On `blocked`, go back to the step the reason names: G-01 to the card, G-02 to the graph, G-03 to the report, G-04 to the open findings.

Stop and ask the person instead of looping when the gate gives the same reason three times in a row, when a finding needs a decision that belongs to the person (accepting a risk, changing the scope), or when the evidence cannot be obtained with the access you have.

## What the gate does not show

- `ready` does not mean the decomposition is sufficient: the checker cannot read the meaning of a statement, and no finding is not the same as no error.
- `permission` and `role` in a skill composition graph are declarations; enforcement belongs to the runtime's permission settings.
- A challenger running on the same model family is a second opinion, not independent evidence. For high-risk changes, a person with the authority to accept the risk still decides.

## Other declarations the checker reads

The same script checks a skill composition graph (`skills`), the one-level `## Child skills` declarations of a skills directory (`--skills-dir DIR`), and a version 1 requirements graph without a problem. [references/checker.md](references/checker.md) describes each.
