# Verified delivery

A person can accept a change without rereading all of it when every acceptance criterion — of each leaf, of each parent, and of the system — has its own evidence from the commit under review, and nothing about risk, approval, or weakened tests is left open. This skill applies its children in order, records that evidence in a verification manifest, and lets the bundled checker decide. The checker cannot tell whether an evidence reference really shows what it claims; that rests on the system that produced it, which is why AI statements never count as evidence.

## Child skills

- `problem-definition`
- `requirements-decomposition`
- `coder`

## Steps

1. **Problem.** If there is no problem statement the person has agreed to, apply `problem-definition` first.
2. **Decomposition.** Apply `requirements-decomposition` to write the problem card and the version 2 requirements graph and to run its gate. Go on only when that gate says `ready`. The graph is the only place for the acceptance criteria: in a project that also keeps a specification (for example spec-kit's `spec.md`), the specification cites the graph's acceptance ids instead of restating them.
3. **Implementation.** Apply `coder`, one leaf requirement at a time: observe the failing check before the fix, keep each change small, and do not delete, skip, or weaken a test to make it pass.
4. **Verification manifest** (`verification-manifest.json`; format in [references/manifest.md](references/manifest.md)). Commit the change first: that commit is `reviewed_commit`. When the person has asked for the change to be pushed and the project's CI runs on pushes or pull requests, push `reviewed_commit` before any of its records — opening the pull request first if CI runs only on pull requests and the person has asked for one — and wait for CI to finish on it, so the CI job's evidence names `reviewed_commit`; then commit the records, review (step 5), and push the records after the review. Do the same for every fix commit. A pull request's CI often tests a merge of the change into the base branch rather than the change itself; record the commit the job checked out, and treat its result as evidence for `reviewed_commit` only while the base branch has not moved since the change branched from it. Keep every record of the change in one record directory. Records are data files (JSON, Markdown, text, XML and the like); a script kept there to make evidence is part of the change, and the review reads it with the change. The records written before implementation — the problem card, the graph, the challenge report — and any fix to them go in with the change, so the reviewed commit carries the requirements it was built to. The records that name `reviewed_commit` — the manifest, its evidence, the assurance reviews, and the review card — go only in later commits that change nothing outside the record directory, because a commit cannot contain its own SHA. Set `implementer` to whoever made the change. Classify the risk in this order and stop at the first that applies: `high` for authentication, authorization, secrets or personal data, data migration, payments, infrastructure permissions, network or public exposure, or anything hard to undo; `medium` for an API, a data flow, or several modules; `low` for a local change that touches no permission and no external contract; otherwise `unclassified`. Write one check per acceptance criterion. Mark one `not_applicable` only with a reason, and for an `L2` or `L3` check also with `approved_by`, the person other than the implementer who agreed. Turn test reports into checks with `python3 <skill-dir>/scripts/assure.py collect-junit REPORT --graph GRAPH --commit SHA --ref REF` for JUnit XML, or `collect-jest` with the same arguments for the output of `jest --json`, where `<skill-dir>` is this skill's base directory (Claude Code shows it when the skill loads). Save raw evidence (logs, test reports) in the record directory as `.txt`, or in the tool's own format (`.xml`, `.json`), so that an ignore rule such as a global `*.log` cannot drop it: before the records commit, `git check-ignore -v` on the evidence files must print nothing, and after it, `git ls-files --error-unmatch` must list every file the manifest cites. Record a CI job by its URL and the commit it ran on, and save the job's result lines with that URL and commit in a file of the record directory to cite as the reference, so the assurance review can read them; record a scanner by its run or alert, and a person's check as `human_review`; an AI review goes in as `ai_review` and never passes a check. List every deleted, skipped, or weakened test in `test_changes` and every permission expansion, public exposure, deletion, or replacement from an infrastructure diff in `infra_changes`.
5. **Assurance review** (for `medium` and `high` risk). Before each round, commit the records, run `python3 <skill-dir>/scripts/review_prep.py check --records <record directory>` and the gate (step 6), and fix every reason except those that wait for this review, a person, or CI, so the reviewer is not the one to find a record error a program can find. Then run `python3 <skill-dir>/scripts/review_prep.py bundle --records <record directory> --base <the commit the change started from> --out <a new directory outside the repository>`, adding `--previous <the previous round's reviewed_commit> --previous-review <its record>` from the second round on ([references/reviewer.md](references/reviewer.md) describes the bundle). Its `scope.json` names the round: `whole` reads the whole change with the first-round prompt; `fixes` — the requirements graph changed only in its text fields, the problem card and the risk class did not change — reads the fix diff with the later-round prompt, which checks that the accepted findings were fixed, that the rejected ones really do not hold, that the graph's text changes weaken nothing, and the fix diff itself. Start a new `read-only-reviewer` subagent (with the plugin's prefix, such as `<plugin>:read-only-reviewer`, when these skills came as a plugin), with that prompt and the language the records are written in, and give it the bundle directory — not the conversation or your own summary. Its definition allows only Read, Grep, and Glob and starts it without CLAUDE.md (a CLAUDE.md in a directory whose files it reads still loads, as do the MCP servers' instructions), so it cannot run git or the scripts; what it needs must be in the bundle or in the repository's files. If no subagent of that name is available, stop and tell the person; do not start another type in its place. It did not review when it ended with an error, was stopped or timed out, answered `NOT REVIEWED`, returned anything but the JSON the prompt asks for, or left out of that JSON's `read` a file the prompt names (the files under the bundle's `evidence/` it reads as needed): start a new one once more with the same bundle, and if that also fails, write no review record, stop, and tell the person the review did not run. Copy its findings into the review record (format in [references/manifest.md](references/manifest.md)) as they are, as `open`; the record's `findings` is empty only when the reviewer read every file the prompt names and returned no finding. In `reviewer`, write the subagent type, the agentId the Agent tool returned, the date, and how many files it read. Then answer each one: fix the change or the manifest and mark it `accepted` with what changed, or mark it `rejected` with why it does not hold. Reject a finding only for one of two reasons: the file and line that shows the finding does not hold, in a file the next reviewer can read (the bundle, or a committed file of the repository); or a decision you asked the person for, written with who answered, when, and their words. Never write as the person's decision what the person has not answered. When the reason rests on something no such file shows (a conversation, a convention, a system the reviewer cannot read), write it into a file of the record directory, commit it, and cite that, or ask the person. You made the change: wanting to reject a finding is not evidence that it is wrong. Never delete a finding. A fix to the change makes a new commit: collect its evidence and start the next round. Keep each round's record (for example `assurance-review-2.<sha>.json`) and give the gate the latest. Before starting the sixth round of the same change, and again before every fifth round after that, stop and ask the person whether to run another round, to decide the open findings themselves, or to go back to step 2; count a round by the review record it wrote, so a reviewer that did not review is not counted. Ask the same when a finding churns: fixing it would undo what the fix for an earlier finding of this change changed. Name that earlier finding in the resolution, and when unsure whether a finding churns, ask. The reviewer's agreement is an opinion, not evidence.
6. **Gate.** Confirm with `review_prep.py check` that the commits after `reviewed_commit` change only the record directory and that the evidence the manifest cites is committed. Run `python3 <skill-dir>/scripts/assure.py check verification-manifest.json`, then `python3 <skill-dir>/scripts/assure.py gate requirements-graph.json verification-manifest.json --report challenge-report.json --review assurance-review.json`, passing each record whenever there is one. The gate checks the graph's structure and both records again itself, so a step that was skipped blocks the change instead of passing it. When the graph has criteria that can only be verified after deploy (`stage` `post_deploy`), decide before deploying with `--stage pre_deploy`: it leaves out the post-deploy checks that have not run and decides everything else as for acceptance, blocking a requirement — or a parent's own `L2` and `L3` checks — left with nothing verified before deploy, so its `pass` means the change may be deployed, not that it is accepted. After deploy, record the post-deploy checks and run the gate without `--stage` to accept. A `high` change without a challenge report is blocked: go back to step 2 and run the challenger. A `medium` or `high` change without an assurance review of `reviewed_commit` is blocked: go back to step 5. On `pass`, present the decision with its counts per level. On `fail`, go back to step 3 for the failing check, or to step 2 if the requirement itself is wrong. On `blocked`, obtain the missing evidence, classify the risk, answer the open findings, fix the graph in step 2, or ask for the approval the reason names. Never change a status, a commit, a risk class, a criterion's stage, or a finding's disposition only to get past the gate.
7. **Review card.** Run `python3 <skill-dir>/scripts/assure.py card --problem problem-card.json --graph requirements-graph.json --manifest verification-manifest.json [--report challenge-report.json] [--review assurance-review.json] [--lang ja]` and give the person the card it prints — in the pull request description, for example — as the first thing they read. For a graph with post-deploy criteria the card shows the decision before deploy under the acceptance decision. The card shows the gate's decisions as they are; never write your own summary of the result in its place.

Stop and ask the person when the same reason blocks or fails the gate three times in a row, before the sixth assurance review round of a change and every fifth round after it, when a finding churns (step 5), when the next step needs authority you do not have (a commit, push, or pull request the person has not asked for, a deployment, production access, a credential, accepting a risk), or when evidence can only be obtained from a system you may not touch.

## Measuring whether this saves time

To decide whether to keep using this skill, compare it with the current review on comparable past requests, following [references/pilot.md](references/pilot.md): preregister the target and the quality gates before the first case, record each person's working minutes and each gate per case, and run `python3 <skill-dir>/scripts/pilot.py preregistration.json cases.json`. Adopt only on `adopt`; a shorter time with a broken quality gate is `not_adopted`.

## What a pass does not show

- That the change is secure or complete beyond its acceptance criteria: the gate checks the records against the requirements graph, and the graph can miss a requirement.
- That an approval is genuine: `approvals` records names, and the checker does not verify identities.
- That the checks are strong: a weak test that passes is still a passed check. The assurance review and the person's own reading are what catch that.
