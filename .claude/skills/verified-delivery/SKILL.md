# Verified delivery

A person can accept a change without rereading all of it when every acceptance criterion — of each leaf, of each parent, and of the system — has its own evidence from the commit under review, and nothing about risk, approval, or weakened tests is left open. This skill applies its children in order, records that evidence in a verification manifest, and lets the bundled checker decide. The checker cannot tell whether an evidence reference really shows what it claims; that rests on the system that produced it, which is why AI statements never count as evidence.

## Child skills

- `problem-definition`
- `requirements-decomposition`
- `coder`

## Steps

1. **Problem.** If there is no problem statement the person has agreed to, apply `problem-definition` first.
2. **Decomposition.** Apply `requirements-decomposition` to write the problem card and the version 2 requirements graph and to run its gate. Go on only when that gate says `ready`. The graph is the only place for the acceptance criteria: in a project that also keeps a specification (for example spec-kit's `spec.md`), the specification cites the graph's acceptance ids instead of restating them.
3. **Implementation.** Apply `coder`, one leaf requirement at a time: observe the failing check before the fix, keep each change small, and do not delete, skip, or weaken a test to make it pass.
4. **Verification manifest** (`verification-manifest.json`; format in [references/manifest.md](references/manifest.md)). Commit the change first: that commit is `reviewed_commit`. Keep every record of the change in one record directory. The records written before implementation — the problem card, the graph, the challenge report — and any fix to them go in with the change, so the reviewed commit carries the requirements it was built to. The records that name `reviewed_commit` — the manifest, its evidence, the assurance reviews, and the review card — go only in later commits that change nothing outside the record directory, because a commit cannot contain its own SHA. Set `implementer` to whoever made the change. Classify the risk in this order and stop at the first that applies: `high` for authentication, authorization, secrets or personal data, data migration, payments, infrastructure permissions, network or public exposure, or anything hard to undo; `medium` for an API, a data flow, or several modules; `low` for a local change that touches no permission and no external contract; otherwise `unclassified`. Write one check per acceptance criterion. Mark one `not_applicable` only with a reason, and for an `L2` or `L3` check also with `approved_by`, the person other than the implementer who agreed. Turn test reports into checks with `python3 <skill-dir>/scripts/assure.py collect-junit REPORT --graph GRAPH --commit SHA --ref REF` for JUnit XML, or `collect-jest` with the same arguments for the output of `jest --json`, where `<skill-dir>` is this skill's base directory (Claude Code shows it when the skill loads). Save raw evidence (logs, test reports) in the record directory as `.txt`, or in the tool's own format (`.xml`, `.json`), so that an ignore rule such as a global `*.log` cannot drop it: before the records commit, `git check-ignore -v` on the evidence files must print nothing, and after it, `git ls-files --error-unmatch` must list every file the manifest cites. Record a CI job by its URL and the commit it ran on, a scanner by its run or alert, and a person's check as `human_review`; an AI review goes in as `ai_review` and never passes a check. List every deleted, skipped, or weakened test in `test_changes` and every permission expansion, public exposure, deletion, or replacement from an infrastructure diff in `infra_changes`.
5. **Assurance review** (for `medium` and `high` risk). Start a new subagent that can only read and search, with the prompt in [references/reviewer.md](references/reviewer.md) and the language the records are written in, and give it the requirements graph, the diff up to `reviewed_commit`, and the raw evidence (logs, reports) — not the conversation or your own summary. Copy its findings into the review record (format in [references/manifest.md](references/manifest.md)) as they are, as `open`. Then answer each one: fix the change or the manifest and mark it `accepted` with what changed, or mark it `rejected` with why it does not hold. Never delete a finding. A fix to the change makes a new commit: collect its evidence and review that commit with the later-round prompt in [references/reviewer.md](references/reviewer.md), which gets the previous review record and the diff from the previously reviewed commit only. Review the whole diff again instead when the requirements graph or the risk class changed since the previous round. Keep each round's record (for example `assurance-review-2.<sha>.json`) and give the gate the latest. The reviewer's agreement is an opinion, not evidence.
6. **Gate.** Confirm that `git diff --name-only <reviewed_commit> HEAD` lists only files in the record directory. Run `python3 <skill-dir>/scripts/assure.py check verification-manifest.json`, then `python3 <skill-dir>/scripts/assure.py gate requirements-graph.json verification-manifest.json --report challenge-report.json --review assurance-review.json`, passing each record whenever there is one. The gate checks the graph's structure and both records again itself, so a step that was skipped blocks the change instead of passing it. When the graph has criteria that can only be verified after deploy (`stage` `post_deploy`), decide before deploying with `--stage pre_deploy`: it leaves out the post-deploy checks that have not run and decides everything else as for acceptance, blocking a requirement — or a parent's own `L2` and `L3` checks — left with nothing verified before deploy, so its `pass` means the change may be deployed, not that it is accepted. After deploy, record the post-deploy checks and run the gate without `--stage` to accept. A `high` change without a challenge report is blocked: go back to step 2 and run the challenger. A `medium` or `high` change without an assurance review of `reviewed_commit` is blocked: go back to step 5. On `pass`, present the decision with its counts per level. On `fail`, go back to step 3 for the failing check, or to step 2 if the requirement itself is wrong. On `blocked`, obtain the missing evidence, classify the risk, answer the open findings, fix the graph in step 2, or ask for the approval the reason names. Never change a status, a commit, a risk class, a criterion's stage, or a finding's disposition only to get past the gate.
7. **Review card.** Run `python3 <skill-dir>/scripts/assure.py card --problem problem-card.json --graph requirements-graph.json --manifest verification-manifest.json [--report challenge-report.json] [--review assurance-review.json] [--lang ja]` and give the person the card it prints — in the pull request description, for example — as the first thing they read. For a graph with post-deploy criteria the card shows the decision before deploy under the acceptance decision. The card shows the gate's decisions as they are; never write your own summary of the result in its place.

Stop and ask the person when the same reason blocks or fails the gate three times in a row, when the next step needs authority you do not have (a deployment, production access, a credential, accepting a risk), or when evidence can only be obtained from a system you may not touch.

## Measuring whether this saves time

To decide whether to keep using this skill, compare it with the current review on comparable past requests, following [references/pilot.md](references/pilot.md): preregister the target and the quality gates before the first case, record each person's working minutes and each gate per case, and run `python3 <skill-dir>/scripts/pilot.py preregistration.json cases.json`. Adopt only on `adopt`; a shorter time with a broken quality gate is `not_adopted`.

## What a pass does not show

- That the change is secure or complete beyond its acceptance criteria: the gate checks the records against the requirements graph, and the graph can miss a requirement.
- That an approval is genuine: `approvals` records names, and the checker does not verify identities.
- That the checks are strong: a weak test that passes is still a passed check. The assurance review and the person's own reading are what catch that.
