# Feature Specification: アプリケーションログの実装と検査スキル(secure-logging)

**Feature Branch**: `050-secure-logging-skill`

**Created**: 2026-10-17

**Status**: Draft

**Input**: User description: "OWASP Logging Cheat Sheet、ASVS 5.0.0 V16、OWASP Top 10:2025 A09、CWE-117/532/778/779、OWASP Logging Vocabulary、OpenTelemetry Logs Data Model、背景としての NIST SP 800-92 Rev.1 草案だけを根拠に、アプリケーションログの実装とレビューの両方を行うドメインオーバーレイのスキル `secure-logging` を追加する。コードで検証できる項目は証拠付きで判定し、運用項目は未検証として報告する。実装はテスト先行。ISO/IEC 27002、PCI DSS、NIST SP 800-53 は一次情報を読むまで含めない。"

**Authority**: 作業ツリーに未コミットの直接実装の下書き(スキルのファイル、README、テストの編集)がある。これは試作の入力であり、承認済みの設計ではない。本仕様が正であり、下書きが本仕様と食い違う場合は下書きを直す。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - ログの実装が良い慣行に沿っているか証拠付きで分かる (Priority: P1)

開発者が、既存コードのログ出力が良い慣行に沿っているかを知りたいと頼む。結果として、項目ごとの判定(合格・不合格・該当なし・未検証)と、その根拠となるコード上の場所を受け取る。

**Why this priority**: 検査が最小で独立した価値であり、実装の完了確認にも同じ検査を使うため、他の機能の土台になる。

**Independent Test**: ログ出力に既知の欠陥(秘密情報の出力、改行の未処理、認証失敗の未記録)を仕込んだ小さなコードに対して検査を依頼し、各欠陥が不合格として場所付きで報告され、運用項目が未検証として別に報告されることを確認する。

**Acceptance Scenarios**:

1. **Given** 認証失敗を記録しないコード、**When** 検査を依頼する、**Then** 認証イベントの項目が不合格で、該当箇所と項目IDが示される。
2. **Given** パスワードやトークンをそのまま出力するログ呼び出し、**When** 検査を依頼する、**Then** 機密データの項目が不合格で、該当の呼び出しが示される。
3. **Given** 利用者入力を改行の無害化なしで出力するコード、**When** 検査を依頼する、**Then** ログインジェクションの項目が不合格になる。
4. **Given** 保存先の権限、保持期間、改ざん検知など、コードでは確認できない項目、**When** 検査結果を受け取る、**Then** それらは合格とされず「未検証」として、判断に必要な証拠とともに報告される。
5. **Given** リポジトリ内のインフラ設定が運用項目を決定づける場合、**When** 検査を依頼する、**Then** その設定ファイルを根拠として判定できる。

---

### User Story 2 - ログの実装をテスト先行で進められる (Priority: P2)

開発者が、新機能にセキュリティイベントのログを足す、または検査で見つかった不合格を直すよう頼む。結果として、先に失敗するテストが書かれ、それを通す最小の変更が入り、既存の検査も通る。

**Why this priority**: 検査だけでなく是正まで一貫して行えることが依頼の中心だが、検査(P1)が先に成立している必要がある。

**Independent Test**: 認証失敗が記録されない関数に対して実装を依頼し、先に失敗するテストが存在し、実装後にそれが通り、秘密情報の見本値がログに現れないことをテストが確認することを確かめる。

**Acceptance Scenarios**:

1. **Given** 自動化できる契約、**When** 実装を依頼する、**Then** 実装より先に、イベントの出力、必要な属性、秘密情報の不出力、改行の無害化を確認するテストが失敗の状態で存在する。
2. **Given** 既存のログ機構があるプロジェクト、**When** 実装する、**Then** 既存の機構と慣行を使い、不要な依存や新しい形式を持ち込まない。
3. **Given** ログの書き込みに失敗する状況、**When** リクエストを処理する、**Then** 処理結果が変わらず、情報も漏れない。
4. **Given** 呼び出し元に返すエラー、**When** 例外が起きる、**Then** 呼び出し元には一般的なメッセージだけが返り、詳細はログに残る。
5. **Given** 実装の完了、**When** 結果を報告する、**Then** 検査を再度実行した結果と、実行したテストの結果が示される。

---

### User Story 3 - 根拠が確認済みの一次情報に限られ、リポジトリの規約に適合する (Priority: P3)

保守者が、このスキルの各項目の根拠をたどり、確認済みの一次情報だけが使われていること、リポジトリのスキル層の規約に違反していないことを確かめられる。

**Why this priority**: 信頼性と保守性の条件であり、利用者の直接の価値ではないが、誤った根拠を載せないために不可欠である。

**Independent Test**: チェックリストの各項目に一次情報への参照があること、除外した規格が除外として明記されていること、リポジトリの構造テストが新スキルを含めて通ることを確認する。

**Acceptance Scenarios**:

1. **Given** チェックリストの任意の項目、**When** 根拠を調べる、**Then** 確認済みの一次情報(出典名と節または要件ID)が示されている。
2. **Given** ISO/IEC 27002、PCI DSS、NIST SP 800-53、**When** チェックリストを調べる、**Then** 一次情報を読んでいないため含めていないことが明記されている。
3. **Given** NIST SP 800-92 Rev.1、**When** 調べる、**Then** 草案であることが示され、要件としては引用されない。
4. **Given** スキルのパッケージ、**When** リポジトリの構造テストを実行する、**Then** 他スキルの名指しも、インストール先パスの固定記述もなく、全項目が合格する。
5. **Given** 英語と日本語の README、**When** スキルの一覧を読む、**Then** 両方に同じ内容で新スキルが載っている。

### Edge Cases

- ログ機構がまだ無いコードベースでは、検査は不足を不合格として報告し、実装は利用可能な標準機構から選ぶ。
- 対象にログ呼び出しが一つも無い変更では、検査は該当なしと報告する。
- 検査対象がリポジトリ全体と変更差分のどちらかを明示されない場合、差分があれば差分を、無ければ全体を対象とし、その仮定を報告に書く。
- 一次情報の版が更新された場合、チェックリストに記した版と異なる可能性があるため、利用者は版を確認できる。
- 検査のための証拠が得られない項目は、推測で合格にせず「未検証」とする。
- 規格の対応付けを求められたが、含めていない規格だった場合、含めていない理由を示し、対応付けは行わない。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: スキルは、ログの実装、変更、レビュー、およびログが良い慣行に沿っているかの質問に対して、ほかの該当する作業と併用される領域別の補助として働かなければならない。
- **FR-002**: スキルは、ログ基盤の運用(SIEM、保持、アラート調整)、セキュリティイベントと無関係な可観測性設計、ログに触れない変更を対象外としなければならない。
- **FR-003**: スキルは、チェックリストの項目を「コードで検証できる群」と「コードでは検証できない群」に分けなければならない。
- **FR-004**: コードで検証できる各項目は、合格・不合格・該当なし・未検証のいずれかの判定と、合格・不合格には根拠となる場所を持たなければならない。
- **FR-005**: コードでは検証できない項目は、リポジトリ内の設定が根拠になる場合を除き、合格としてはならず、判断に必要な証拠とともに未検証として報告しなければならない。
- **FR-006**: チェックリストは少なくとも次を含まなければならない: 記録すべきイベント、イベントの属性(いつ・どこで・誰が・何を)、時刻表記、除外すべきデータ、過剰出力の抑制、ログインジェクション対策、ログ失敗時の安全な振る舞い、エラー応答の一般化、ログレベルの無効化防止、ログに関するテスト。
- **FR-007**: 各チェックリスト項目は、確認済みの一次情報(出典名と節または要件ID)を根拠として示さなければならない。
- **FR-008**: チェックリストは、OWASP Logging Cheat Sheet、OWASP ASVS 5.0.0 V16、OWASP Top 10:2025 A09、CWE-117、CWE-532、CWE-778、CWE-779、OWASP Logging Vocabulary、OpenTelemetry Logs Data Model のみを要件の根拠とし、NIST SP 800-92 Rev.1 は草案として背景に限らなければならない。
- **FR-009**: チェックリストは、ISO/IEC 27002、PCI DSS、NIST SP 800-53 を一次情報を読むまで含めないこと、およびその理由を明記しなければならない。
- **FR-010**: 実装の依頼では、自動化できる契約について、実装より先に失敗するテストを作り、失敗を確認してから実装しなければならない。自動化できない場合は、現状の観測と確認方法を記録しなければならない。
- **FR-011**: 実装は、既存のログ機構と慣行を維持し、既存の機構で満たせない場合に限って新しい依存や形式を導入しなければならない。
- **FR-012**: 実装の完了時、スキルは検査を再度実行し、実行したテストの結果と合わせて報告しなければならない。
- **FR-013**: 検査結果の報告は、結論(不合格と未検証の件数、重大なもの)を先頭に置き、続いて項目別の判定、実施した変更、利用者が用意すべき運用側の証拠、未検査の範囲を示さなければならない。
- **FR-014**: スキルは、観測した事実、出典に基づく要件、推論を区別して報告しなければならない。
- **FR-015**: スキルのパッケージは、リポジトリのスキル層の規約を守らなければならない: 他スキルの名指しをせず、インストール先のパスを固定記述しない。
- **FR-016**: スキルは、リポジトリの構造テストの対象一覧と、ルーティングを確認する検査に登録されなければならない。
- **FR-017**: 英語と日本語の README は、新スキルの目的と、コードで検証できる項目だけを判定する性質を同じ内容で記載しなければならない。
- **FR-018**: ログに秘密情報、トークン、個人情報、決済情報を出力してはならないことを、検査の合否と実装の完了確認の両方に含めなければならない。

### Key Entities

- **チェックリスト項目**: 識別子、要件の文、群(コードで検証できる/できない)、根拠(出典と節または要件ID)を持つ。
- **判定**: 項目に対する合格・不合格・該当なし・未検証のいずれかと、根拠の場所または理由。
- **一次情報**: 出典名、版、確認日を持ち、チェックリストの根拠として引用される。
- **検査報告**: 結論、項目別の判定、実施した変更、利用者が用意すべき証拠、未検査の範囲。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 既知の欠陥を仕込んだ検証用コードに対する検査で、仕込んだ欠陥のすべてが、場所付きの不合格として報告される。
- **SC-002**: 検査結果のうち、コードでは検証できない項目が合格として報告される件数は 0 件である。
- **SC-003**: チェックリストの全項目に、確認済みの一次情報への参照がある(根拠の無い項目は 0 件)。
- **SC-004**: 実装の依頼で、実装より前に失敗するテストが存在することを、完了の報告から確認できる。
- **SC-005**: 秘密情報の見本値を含む入力に対し、実装後のログ出力に見本値が現れない。
- **SC-006**: リポジトリの構造テストが、新スキルを含めて全件通る。
- **SC-007**: 日本語と英語の README の両方に新スキルが記載され、リンク検査でエラーが 0 件である。

## Assumptions

- 対象は、アプリケーションコードのログ出力であり、ログの収集・保管の基盤は含まない。基盤の設定がリポジトリ内にある場合に限り、検査の根拠として読む。
- 利用者のプロジェクトは何らかのログ機構を使うか、標準の機構を使える言語である。特定の言語やライブラリには依存しない。
- 検査の対象が指定されなければ、差分を優先し、差分が無ければ全体とする。この仮定は報告に書く。
- 出典の内容は 2026-10-17 に一次情報から確認したものである。版が変わった場合は、利用時に確認する。
- 試作の下書きは参考にするが、承認済みの設計ではない。本仕様と食い違う箇所は下書きの側を直す。
- スキル層の規約(他スキルの名指しの禁止、インストール先パスの固定記述の禁止)と構造テストは、既存のものをそのまま使う。
- 規格(ISO/IEC 27002、PCI DSS、NIST SP 800-53)への対応付けは、一次情報を読んだ後の別の変更で扱う。
