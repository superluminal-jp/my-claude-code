# Feature Specification: 問題カード・要求グラフ・反証の記録を結び、実装へ進めるかを判定する(引き継ぎ書 Phase 2)

**Feature Branch**: `feat/goal-refinement`(`feat/refinement-graph-checker` から分岐)

**Created**: 2026-11-06

**Status**: Draft

**Input**: User description: "Phase 2 から先も順に実装"(2026-11-06。spec 059 の Phase 1 の完了報告への返答)

**要旨**: 新しい自作スキル `goal-refinement` を加える。このスキルは、合意済みの問題を、根拠と仮説と解決策を分けた**問題カード**に記録し、spec 059 の形式の**要求の論理グラフ**へ分解し、読み取り専用の**反証役**のサブエージェントに異議を出させて**反証の記録**に残す。同梱の検査器は3つの形式を検査し、**実装へ進めるかの判定**(`ready` か `blocked`)を返す。spec 059 の検査器は、このスキルのパッケージへ移す。検査器が保証するのは、根拠のない問題、結び付いていない成果物、未対応の異議が実装へ進まないことだけである。意味の誤り(手段を問題とする、親が偽になる反例など)を見つけるのは AI の反証役であり、その検出の力は4件の評価でしか確かめていない。

**利用者の指示と、Claude が決めた既定**: 利用者は Phase 2 以降を順に実装するよう指示した。引き継ぎ書 §21.8 は、Phase 2 の着手前に問題カードと要求グラフの1件の実例を利用者に示すとしたが、利用者の指示に従い、実例の確認を待たずに進める。実例は本スキルの例のファイルとして示す。Claude は次の既定を選んだ。いずれも Git の履歴から戻せる。

## 用語

spec 059 の用語(要求の論理グラフ、分解の型、受け入れ条件、水準 L1〜L3、スキル合成グラフ、互換モード、規則 S-00〜S-11、終了コード、引き継ぎ書)は、そのまま使う。

- **問題カード**: 1つの問題を、理想、現状、根拠(観測とその出典)、反対の根拠、差分、重要性、原因の仮説、解決策の案、範囲外、状態に分けて書いた JSON の宣言。引き継ぎ書 §4 の問題カードを機械が検査できる形にしたものである。
- **問題の状態**: `verified`(根拠で現状が確かめられた)、`unverified`(根拠がまだない)、`refuted`(反対の根拠で問題が否定された)のいずれか。
- **反証役**: 実装の文脈と解決策を与えられず、問題カードと要求グラフだけを読む、読み取り専用のサブエージェント。問題の誤検知、別の原因、手段を問題とする誤り、事実と仮説と解決策の混在、子がすべて真でも親が偽になる反例、子の欠け、OR の枝の重なりを探す。
- **反証の記録**: 反証役の指摘と、それへの対応を書いた JSON の宣言。
- **実装へ進めるかの判定(以下、判定)**: 問題カード、要求グラフ、反証の記録(任意)を受け取り、`ready`(実装へ進める)か `blocked`(進めない)を、理由とともに返す検査器の動き方。
- **規則 C-xx、R-xx、G-xx**: 本仕様の規則の名前。C は問題カード、R は反証の記録、G は判定の規則である。

## 背景

Phase 1 の検査器は、要求グラフの構造の誤りを見つけるが、要求が正しい問題から来ているかは見ない。引き継ぎ書 §21.2 は、AI が問題の存在や対策の目標を取り違えたまま子の要求を並べると、構造の合格が誤った対応を後押しし得るとした(仮説)。このため、問題の根拠と、要求への分解と、独立した異議とを、実装の前に結び付けて止める仕組みが要る。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 根拠のない問題や否定された問題は、実装へ進まない (Priority: P1)

保守者または Claude が問題カードを書き、要求グラフとともに判定にかける。根拠のない問題や否定された問題は `blocked` になり、その理由が示される。

**Independent Test**: 問題カードの正例と負例、および判定を検査器にかけ、規則 ID と判定を確かめる。

**Acceptance Scenarios**:

1. **P2-01** **Given** 根拠が1件もないのに状態が `verified` の問題カード、**When** 検査する、**Then** C-01 の違反になる。**Given** 根拠のない `unverified` の問題カード、**When** 判定する、**Then** `blocked` で、理由は問題が確かめられていないことである。
2. **P2-02** **Given** 検出器の警告(例: CodeQL の検出)を根拠に持つが、対象の経路に到達しないことを反対の根拠として持ち、状態が `refuted` で理由を書いた問題カード、**When** 検査する、**Then** 違反はない。**When** 判定する、**Then** `blocked` である。**Given** 反対の根拠があるのに状態の理由がない問題カード、**Then** C-02 の違反になる。
3. **Given** 状態が `refuted` なのに反対の根拠がない問題カード、**Then** C-02 の違反になる。

---

### User Story 2 - 問題・要求・反証の3つが結び付き、未対応の異議があれば止まる (Priority: P1)

保守者または Claude が、問題カードに結び付けた要求グラフ(v2)と、反証役の指摘を書いた反証の記録を判定にかける。結び付きの欠け、存在しない対象への指摘、未対応の指摘、理由のない対応は `blocked` または違反になる。

**Independent Test**: 判定の正例と負例を検査器にかけ、判定と理由を確かめる。

**Acceptance Scenarios**:

1. **Given** `verified` の問題カード、その ID を `problem_id` に持つ v2 の要求グラフ、すべての指摘が対応済みの反証の記録、**When** 判定する、**Then** `ready` で、終了コードは 0 である。
2. **Given** 反証の記録がない同じ組、**When** 判定する、**Then** `ready` だが、結果に `challenge: not_run` が示される。
3. **P2-04** **Given** 根の要求に対する `counterexample`(第三の取得経路)の指摘が `open` の反証の記録、**When** 判定する、**Then** `blocked` である。**Given** その指摘を `accepted` にし、第三の経路の子と親の統合試験を加えた要求グラフ、**Then** `ready` である。
4. **P2-03・P2-05・P2-06** **Given** `solution_as_problem`、`or_overlap`、`mixed_statement` の指摘が `open` の反証の記録、**When** 判定する、**Then** それぞれ `blocked` である。
5. **Given** `problem_id` が問題カードと異なる要求グラフ、または `problem_id` のない v1 の要求グラフ、**When** 判定する、**Then** `blocked` である。
6. **Given** 要求グラフにも問題カードにもない ID を対象にした指摘、**When** 判定する、**Then** R-03 の違反として `blocked` である。
7. **Given** 理由のない `rejected` の指摘、**When** 検査する、**Then** R-02 の違反になる。

### User Story 3 - スキルの手順で問題カードから判定まで進め、反証役の検出の力を測る (Priority: P2)

Claude が `goal-refinement` スキルを読み、問題カードを書き、要求グラフへ分解し、必要なときに反証役を起動し、判定を実行する。反証役の検出の力を、P2-03〜P2-06 の4件の入力で実際に起動して測る。

**Independent Test**: スキルの構造を `tests/run-config-pyramid.sh` で、検出の力を4件の評価で確かめる。

**Acceptance Scenarios**:

1. **Given** 変更後のリポジトリ、**When** `tests/run-config-pyramid.sh` を実行する、**Then** `goal-refinement` を含む自作スキルの検査がすべて通る。
2. **Given** P2-03〜P2-06 の4件の入力(問題カードと要求グラフ)、**When** 反証役の指示文で読み取り専用のサブエージェントを起動する、**Then** 各件で期待する種類の指摘が出たかを、出なかった件と誤検知とともに作業記録に残す。

### Edge Cases

- **判定の合格の意味**: `ready` は、根拠のある問題に結び付き、構造が規則に合い、記録された異議がすべて対応済みであることだけを意味する。異議が出なかったことは、誤りがないことの証明ではない。
- **反証役の独立性**: 反証役は同じ系列のモデルであり、誤りが相関し得る。別の文脈で起動することは助けになるが、独立した証拠の代わりにならない(引き継ぎ書 §7.2)。
- **v1 の要求グラフ**: spec 059 の v1 の要求グラフは、引き続き単独の検査に合格する。判定では、問題に結び付いていないため `blocked` になる。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 検査器は、最上位の `problem_card`(オブジェクト)または `challenge_report`(オブジェクト)を持つ宣言ファイルも読み、規則 C-xx または R-xx を判定する。要求グラフは `schema_version` 1 と 2 を受け付け、2 では最上位の `problem_id`(空でない文字列)を必須とする。
- **FR-002**: 問題カードの欄と規則は次のとおりとする。欄の詳細は [contracts/declarations.md](contracts/declarations.md) にある。

  | 規則 | 合格の条件 |
  |---|---|
  | C-00 | 必須の欄(`id`、`ideal`、`current`、`gap`、`significance`、`status`、`evidence`)があり、値の型が正しく、定義していない欄がない |
  | C-01 | `status` が `verified` なら、`evidence` に、空でない `source` と `observation` を持つ根拠が1件以上ある |
  | C-02 | `counter_evidence` が1件以上あれば `status_rationale` が空でない。`status` が `refuted` なら `counter_evidence` が1件以上ある |
  | C-03 | `status` が `verified`、`unverified`、`refuted` のいずれかである |

- **FR-003**: 反証の記録の欄と規則は次のとおりとする。

  | 規則 | 合格の条件 |
  |---|---|
  | R-00 | 必須の欄(`problem_id`、`reviewer`、`context_given`、`findings`)があり、値の型が正しく、定義していない欄がない |
  | R-01 | 指摘の `id` が空でなく一意で、`kind` と `severity` と `disposition` が定めた値のいずれかである |
  | R-02 | `disposition` が `accepted` か `rejected` の指摘は、空でない `resolution` を持つ |
  | R-03 | 判定のとき、各指摘の `target` が、問題カードの `id` か、要求グラフのノードの ID である |

- **FR-004**: 判定は、引数 `--gate CARD GRAPH [REPORT]` で実行し、次の規則を順に判定する。どれか1つでも満たさなければ `blocked` とし、満たさない規則と理由をすべて示す。

  | 規則 | `ready` の条件 |
  |---|---|
  | G-01 | 問題カードに違反がなく、`status` が `verified` である |
  | G-02 | 要求グラフに違反がなく、v2 であり、`problem_id` が問題カードの `id` と一致する |
  | G-03 | 反証の記録があれば、違反がなく(R-03 を含む)、`problem_id` が問題カードの `id` と一致する |
  | G-04 | 反証の記録に `disposition` が `open` の指摘がない |

- **FR-005**: 判定の結果は、spec 059 の出力の欄に加えて、`decision`(`ready` か `blocked`)、`reasons`(満たさない規則ごとの `{rule_id, message}`)、`challenge`(`recorded` か `not_run`)を持つ。終了コードは `ready` で 0、`blocked` で 1、入力を解釈できなければ 2 とする。
- **FR-006**: `goal-refinement` の `SKILL.md` は、問題カードを書く、要求グラフへ分解する、必要なら反証役を起動する、判定を実行する、`blocked` の理由に応じて戻る、の手順を定める。同じ理由で3回続けて `blocked` になれば、自動の繰り返しを止めて人に判断を求める。反証役の指示文は、パッケージの `references/` に置く。
- **FR-007**: spec 059 の検査器、例、テストを `.claude/skills/goal-refinement/` へ移し、spec 059 の受け入れテストがすべて引き続き通る。`tests/run-refinement-checker.sh` は移した先を実行する。
- **FR-008**: `tests/run-config-pyramid.sh` の自作スキルの一覧と名前のパターンに `goal-refinement` を加え、README の索引と説明を更新する。`problem-definition` を含む既存のスキルの本文は変えない。
- **FR-009**: 問題カード、v2 の要求グラフ、反証の記録の例を1組、スキルの `examples/` に置き、判定が `ready` になる。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: User Story 1・2 の各負例が期待する規則で失敗し、正例が合格することを、実装の前に失敗するテストで確かめる。
- **SC-002**: spec 059 の受け入れテスト49件を含め、検査器のテストがすべて通り、既存のローカルの検査がすべて変更前と同じ件数か、`goal-refinement` を加えた分だけ増えた件数で通る。
- **SC-003**: 反証役の評価の4件について、期待する種類の指摘が出た件数、出なかった件数、誤検知を作業記録に残す。

## Assumptions

- 利用者の「順に実装」は、引き継ぎ書 §21.8 の各 Phase の着手前の確認を、利用者が省いたものと読む(確度: 中)。
