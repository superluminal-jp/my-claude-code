# 要件ドラフト: ドキュメンテーションの粒度階層と読者段階

**ステータス**: 確定・実装済み（2026-08-30。OQ-1〜OQ-4 はすべてデフォルト案を採用）

**作成日**: 2026-08-30

**入力**: ユーザー記述:「ドキュメンテーションやコメント付与において、コード内のコードブロック単位、ファイル単位、フォルダ単位、階層構造、レポジトリ単位などで段階的に情報を適切な粒度で書き示すようにしたい。内容的にもさまざまな読者レベルに対応できるように段階的に専門性・事前知識を高めていくような構造を取りたい。」

**成果物の配置先**: `.claude/rules/live-documentation.md` に **§ 7** を追記し、あわせて **§ 5 No Redundancy** に例外条項を追加する（本ドラフトは実装ではない）。

---

## 1. 目的

既存の `live-documentation.md` は「文書が嘘をつかないこと」（§1 Drift）と「コードの近くに置くこと」（§4 Proximity）を担保するが、**どの階層に、どの深さで、どういう順序で書くか**を規定していない。その結果、粒度の判断が毎回その場の裁量になり、同じ対象が場所によって過剰にも過少にも記述される。

§7 はこの欠落を埋め、(A) 粒度階層ごとの正本の所在と (B) 各文書内部の論理構造を規定する。

## 2. 用語

| 用語 | 定義 |
|---|---|
| **粒度層 (granularity layer)** | 文書が対象とする範囲の大きさ。本要件では 5 層（§4.1）。 |
| **正本 (canonical source)** | ある事実について、リポジトリ内で唯一の権威となる記述箇所。§4 Proximity により、対象コードに最も近い層に置かれる。 |
| **圧縮要約 (compression)** | 上位粒度層が下位粒度層の正本を要約したもの。§5 の重複には当たらない（§4.5 の条件を満たす場合に限る）。 |
| **ピラミッド構造** | 前提の共有 → 結論 → MECE な支持要素、という順序を持つ文書構造（Minto）。 |

## 3. スコープ

**対象内**
- `.claude/rules/live-documentation.md` への §7 追加と §5 への例外条項追加。
- 5 つの粒度層の定義、各層の正本種別、必須度の規定。
- 各 Documentation Artifact の内部構造要件（ピラミッド構造）。

**対象外**
- 機械的な強制（hooks / スクリプト）。ADR 0005・0007 により撤去済みで、復活させない。
- 既存文書の遡及的な書き直し（OQ-4 参照）。
- `docs/`、`specs/`、`.claude/skills/` 内の既存文書の再編。

## 4. 決定事項と要求

### 4.1 粒度層の定義

**FR-001** — §7 は次の 5 層と、各層の正本種別を定義する。ある事実の正本は、その事実が真である**最小の**層に置く。

| 層 | 対象範囲 | 正本となる Documentation Artifact |
|---|---|---|
| L1 `repository` | リポジトリ全体 | ルート `README.md` |
| L2 `subtree` | 複数フォルダにまたがる部分木（サブシステム） | 部分木のルートにある `README.md` |
| L3 `directory` | 単一フォルダ直下 | 同一フォルダの `README.md` |
| L4 `file` | 単一ファイル | ファイル冒頭の docstring / モジュールコメント |
| L5 `block` | 関数内の区画・非自明な分岐 | インラインコメント |

*根拠*: §4 Proximity の「最も近い場所」を、判断の余地なく層として離散化したもの。既存 §4 の優先順位（docstring > 同一ディレクトリ README > 隣接する仕様ファイル）と矛盾しない。

### 4.2 必須度

**FR-002** — 必須度は次のとおり（RFC 2119 の語法に準じる）。

- L1 `repository`: **MUST**（ルート README は常に存在し、§4.3 の構造要件を満たす）。
- L2〜L5: **SHOULD**（推奨）。存在しないこと自体は §7 違反としない。
- **ただし全層共通で MUST**: 文書を書く場合は §4.3 の構造要件に従う。「書かなくてよいが、書くなら形式に従う」。

*根拠*: ユーザー選択（「リポジトリ層のみ必須、他は推奨」）。全層一律必須は内容の薄い README を量産し §5 と正面衝突する。

**FR-002a** — 推奨に留めても実質的な担保は失われないことを §7 に明記する。既存 §1 Drift Detection は独立に作動し、公開契約が変わったのに対応する Documentation Artifact が同一差分で更新されていなければ、その文書が「推奨」層にあっても違反となる。

### 4.3 文書内部の構造要件（ピラミッド構造）

**FR-003** — 層を問わず、すべての Documentation Artifact は次の 4 条件を満たす。

1. **前提の共有が先** — 本題に入る前に、読者が既に知っている状況と、この文書が扱う対象・前提知識・用語を提示する。未定義の専門用語で書き出さない。
2. **結論が先** — 支持する詳細より前に、答え（この対象は何か／何をするか）を置く。
3. **兄弟は MECE** — 同一階層に並ぶ項目は、相互に重複せず、その階層で漏れがない。
4. **グループは演繹型か帰納型のいずれかに統一** — 一つのグループ内で、前提→前提→結論（演繹）と、同種の事実の列挙（帰納）を混在させない。

*根拠*: ユーザー指定。`rules/thinking-lenses.md` の Logic tree レンズ（演繹/帰納の区別、兄弟の MECE）および Parallel レンズ（兄弟の同種性）と同一の判断基準であり、新しい概念を導入していない。

### 4.4 段階的な専門性

**FR-004** — 「読者レベル」は固定のラベル（初級/中級/上級）としては定義しない。**ピラミッドを何段降りたかが、そのまま専門性の段階**である。これを検証可能にするため、次を規定する。

- 各層は、**一つ上の層の文書を読み終えた読者**を想定読者とする。
- したがって、ある層の文書は、上位層で既に導入された用語に依存してよいが、**下位層でしか定義されていない用語に依存してはならない**（依存の向きは常に上→下の一方向）。
- L1 `repository` は前提知識ゼロの読者を想定する。

*根拠*: FR-003-1（前提の共有が先）を層をまたいで適用した帰結。「段階的に専門性・事前知識を高めていく」という要求を、文書単位ではなく**層の連鎖**として実現する。

### 4.5 §5 No Redundancy の例外条項

**FR-005** — §5 に例外を追加する。上位粒度層における下位粒度層の要約は、重複ではなく**圧縮**として許可される。ただし次の 3 条件をすべて満たすこと。

- (a) 正本へのリンクを伴う。
- (b) 正本と矛盾しない。
- (c) 正本に存在しない事実を新たに導入しない。

*根拠*: ユーザー選択。FR-004 の段階構造は、同一対象を異なる深さで複数回述べることを必然的に要求するため、例外を明示しなければ §7 と §5 は矛盾する。

**FR-006** — 違反類型を 2 つ定義する。

- **Structure violation** — FR-003 の 4 条件のいずれかを満たさない（未定義用語での書き出し、結論の後置、兄弟の重複/漏れ、演繹と帰納の混在）。
- **Compression violation** — FR-005 の (a)(b)(c) のいずれかに反する。うち (b) 矛盾は既存の **Drift** 違反としても扱う（同一事実に対する二重の記述が食い違っている状態であり、§1 の趣旨そのもの）。

### 4.6 運用

**FR-007** — 既存の Override Handling をそのまま適用する。理由の明示がない黙示的なスキップは拒否する。§7 専用の免除規定は設けない。

**FR-008** — 機械的な強制は行わない。§7 は §1〜§6 と同列に、差分・コミット・PR のレビュー時および Documentation Artifact 作成時に適用されるチェックとする（ADR 0005・0007 の決定を維持）。

**FR-009** — 正本は本リポジトリの `.claude/rules/live-documentation.md` ただ一つとする。`~/.claude/rules/live-documentation.md` は `install.sh` が同期する（現時点で両者は同一であることを確認済み）。手動での二重編集は行わない。

**FR-010** — §7 の本文は、既存 `rules/` 配下の記述言語に合わせて**英語**で記述する。本要件ドラフト（`specs/` 配下）は既存の慣行に合わせ日本語とする。

## 5. 受け入れ基準

- **SC-001** — **Given** 公開契約を持つ関数を含むファイルが変更された、**When** そのファイルに docstring が存在しない、**Then** §7 単独では違反としない（L4 は SHOULD）。ただし既存の docstring が古いまま残っている場合は §1 Drift 違反となる。
- **SC-002** — **Given** 新規に作成されたルート `README.md`、**When** 冒頭が未定義の専門用語で始まり、結論より先に詳細が並んでいる、**Then** Structure violation として指摘される。
- **SC-003** — **Given** リポジトリ層 README がサブシステムの説明を 3 行で要約している、**When** その要約が部分木 README へのリンクを伴い、内容が矛盾せず、正本にない事実を含まない、**Then** §5 違反としない（圧縮として許可）。
- **SC-004** — **Given** 同じ状況で、要約が正本に存在しない設定項目に言及している、**Then** Compression violation (c) として指摘される。
- **SC-005** — **Given** 上位層の文書が、下位層の docstring でしか定義されていない用語を無定義で使用している、**Then** FR-004 の依存方向違反として指摘される。
- **SC-006** — **Given** ある README の箇条書きが、演繹的な論証 2 項目と並列事実 3 項目を同一階層に混在させている、**Then** Structure violation (FR-003-4) として指摘される。
- **SC-007** — **Given** §7 追加後の `live-documentation.md`、**When** `install.sh` を実行する、**Then** `~/.claude/rules/live-documentation.md` が同一内容に更新され、手動編集は不要である。
