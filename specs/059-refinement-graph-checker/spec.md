## 用語

- **引き継ぎ書**: 利用者が渡した Markdown の文書『AIコーディングのレビュー限界を突破するための設計・研究・実装引き継ぎ書』(2026-11-04 作成、2026-11-06 更新)。利用者の手元のファイルで、このリポジトリには含めない。本仕様の節番号(§20.4 など)は、この文書の節番号である。本仕様が使う節の内容は、各所で要約する。
- **Phase 1〜5**: 引き継ぎ書 §21 の段階。Phase 1 は宣言の形式と静的な検査、Phase 2 は問題定義と論理分解、Phase 3 は多層の独立した検証、Phase 4 はレビューの判断資料、Phase 5 は比較実験である。
- **T-01〜T-10**: 引き継ぎ書 §19.6 のテストの ID。本仕様に関わるのは、T-07(検証を担う役割、すなわち `auditor` と `checker` に、書き込みや配備の権限がある宣言を拒否する)、T-09(既存の一段の構成を、明示の互換の設定のもとで従来と同じ意味に読む)と、D14 の4つである。
- **要求の論理グラフ**: 要求をノードとし、親の要求から子の要求への分解をエッジとするグラフ。各ノードは、分解の型と受け入れ条件を持つ。
- **分解の型(AND、OR、LEAF)**: AND は、子のすべてが親に必要であることを表す。OR は、子のうちどれか一つを、条件に応じて選ぶ代替であることを表す。LEAF は、それ以上分解しない葉であることを表す。分解の型は宣言であり、子が親を満たすことの証明ではない。本仕様で「値の型」と書くときは、JSON の値の種類(文字列、配列など)を指し、分解の型とは別である。
- **根**: 要求の論理グラフで、どのノードの子にも挙げられていないノード。
- **受け入れ条件**: ノードが満たされたと判定するための検証の宣言。ID、説明、水準を持つ。宣言であって、検証を実行した結果ではない。
- **水準(L1、L2、L3)**: 引き継ぎ書 §6 の検証の層。L1 は葉の個別の検証、L2 は親の統合の検証、L3 はシステム全体の検証である。
- **スキル合成グラフ**: スキルをノードとし、親スキルから、それが適用できる子スキルへのエッジを持つグラフ。引き継ぎ書 §20.3 の例 B(例 A は要求の論理グラフ)がこの形である。エッジは、実行の順序や自動の起動を表さない。ただし親が子を適用すれば子の効果が生じるため、S-09 は監査役から届くスキルの権限も見る。
- **有向非巡回グラフ(DAG)**: 向きのあるエッジをたどっても、元のノードに戻れないグラフ。一つの子が複数の親を持ってよい。複数の親を持つ子を**共有子**と呼ぶ。
- **宣言ファイル**: 要求の論理グラフ、またはスキル合成グラフの一方を書いた JSON のファイル。
- **互換モード**: 宣言ファイルの代わりに、スキルを並べたディレクトリの各 `SKILL.md` にある「`## Child skills`」節からスキル合成グラフを作り、検査する動き方。
- **spec 058**: `specs/058-parent-skill-references/spec.md`。親スキルが `SKILL.md` の「`## Child skills`」節で子を宣言でき(FR-001)、宣言された子は自作スキルでなければならず、親は自分自身を宣言できず(FR-003)、子は自分の子を宣言できない(FR-004、一段の制限)と定めた。自作スキルとは、`tests/run-config-pyramid.sh` の配列 `authored_skills` に並ぶスキルである。
- **規則 ID(S-00〜S-11)**: 本仕様が定める検査の規則の名前。S-01〜S-10 は引き継ぎ書 §20.4 の番号と意味に合わせた。S-00(値の形式)と S-11(単一の根)は本仕様で加えた。
- **受け入れシナリオ ID(P1-01〜P1-12)**: 引き継ぎ書 §20.5 の受け入れテストの番号。本仕様の受け入れシナリオに、その番号を付ける。番号のないシナリオは本仕様で加えた。
- **検査器(`refinement-checker`)**: 本仕様で作る、読み取り専用のコマンド。宣言ファイルまたはスキルのディレクトリを読み、規則の違反を報告する。
- **終了コード**: 検査器のプロセスが終わるときに返す数値。呼び出した側(CI など)は、この数値で合否を判断する。

## 背景

本仕様が埋めると仮定する差分は、要求とスキルの関係を型付きで宣言し、機械的に照合する共通の形式がないことである。引き継ぎ書 §4 の問題カードの項目で、次に示す。

| 区分 | 内容 | 確度と根拠 |
|---|---|---|
| 現状 | このリポジトリでスキルどうしの関係を宣言する手段は、spec 058 の「`## Child skills`」節だけであり、一段に限られる。要求の AND/OR の分解、親自身の受け入れ条件、スキルの権限を記述し、機械的に照合する形式はない。現在、「`## Child skills`」節を持つスキルはない | 観測。`origin/main`(コミット 34708a5)の spec 058、`tests/run-config-pyramid.sh`、`.claude/skills/` を読んだ |
| 理想 | 要求とスキルの多段の関係を DAG として宣言でき、ID の重複と欠損、循環、分解の型の不整合、受け入れ条件の欠如、監査役の権限の逸脱を、既存の構成を変えずに機械的に検出できる | 引き継ぎ書 §20.1 の目標 |
| 差分 | 型付きで検査できる共通の宣言の形式と、その検査器がない | 仮説。この欠如による失敗はまだ観測していない(親スキルが1つもない)。後の Phase で多段の親スキルや要求の分解を加えたときに、形式の不整合を止める手段がなくなると予測する |
| 意義 | 親スキルや独立した監査役を増やす前に形式の不整合を止める。後の Phase で、要求・検証の証拠・レビューの判断資料を ID で結ぶ土台にする | 推論。レビュー時間を減らす効果は測っていない |
| 完了条件 | 受け入れシナリオ P1-01〜P1-12 と本仕様で加えたシナリオが再現できる形で通り、既存の検査の結果が変わらない | 引き継ぎ書 §20.5 |

Phase 1 を完了しても、引き継ぎ書の最上位の目標 G0 を達成したことにはならない。G0 は、元の要求1件あたりの人間の介入時間の中央値を、比較できる従来の方式(現在の Claude Code の構成と従来の PR レビュー)より 20% 以上減らすこと(OUT-1)と、業務・本番システムの品質と安全性を保つこと(OUT-2)の両方であり、Phase 5 の比較実験で判定する(引き継ぎ書 §16.2)。

## User Scenarios & Testing *(mandatory)*

3つの利用者の物語は、検査器が要求の分解の構造の誤り(User Story 1)とスキルの合成の構造の誤り(User Story 2)を見つけ、既存の一段の宣言の検査を崩さないこと(User Story 3)を、それぞれ独立に確かめる。

### User Story 1 - 要求の分解の構造の誤りを、実装へ進む前に機械的に見つけられる (Priority: P1)

保守者、または保守者の指示で作業する Claude が、要求の分解を宣言ファイルに書き、検査器にかける。ID の重複、存在しない子、循環、分解の型と子の数の不整合、OR の選択条件の欠如、受け入れ条件の欠如、水準の誤り、挙げ忘れた子は、規則 ID とノードの ID を添えた違反として報告され、終了コードは 1 になる。共有子を持つ正しい DAG は合格し、終了コードは 0 になる。

**Why this priority**: 引き継ぎ書 §19.9 は、この構造の検査器を最初の実験の対象とした。これがないと、後の Phase の分解や監査の結果を機械的に照合できない。

**Independent Test**: 負例と正例の宣言ファイルを検査器にかけ、終了コードと規則 ID を確かめる。負例ごとに、期待する規則の違反だけが出ることを確かめる。

**Acceptance Scenarios**:

1. **P1-01** **Given** 二つのノードが同じ `id` を持つ要求の論理グラフ、**When** 検査する、**Then** S-01 の違反として重複した ID が報告され、終了コードは 1 である。
2. **P1-02** **Given** 定義されていない ID を子に挙げるノード、**When** 検査する、**Then** S-02 の違反として、親の ID と不明な子の ID が報告される。
3. **P1-03** **Given** A、B、C の順に宣言し、A→B→C→A と循環するグラフ、**When** 検査する、**Then** S-03 の違反として、循環の経路 `A -> B -> C -> A` が報告される。
4. **P1-04** **Given** 子を持つ LEAF、または子が1件だけの AND、**When** 検査する、**Then** それぞれ S-04 の違反として、分解の型と子の数が報告される。
5. **P1-05** **Given** 子の一つに選択条件がない OR、**When** 検査する、**Then** S-05 の違反として、条件のない子の ID が報告される。
6. **P1-06** **Given** 受け入れ条件を持たない AND の親、**When** 検査する、**Then** S-06 の違反が報告される。
7. **P1-07** **Given** 親の受け入れ条件に L2、葉の受け入れ条件に L1、根の受け入れ条件に L3 を付けた正しいグラフ、**When** 検査する、**Then** 違反はなく、終了コードは 0 である。**Given** 水準が `L4` の受け入れ条件、**Then** S-07 の違反になる。
8. **P1-08** **Given** 二つの親が同じ子を参照し、循環はないグラフ、**When** 検査する、**Then** 違反はない(S-08)。
9. **P1-10** **Given** JSON として読めないファイル、または `schema_version` が 1 でないファイル、**When** 検査する、**Then** 終了コードは 2 で、読めない理由が表示される。
10. **Given** 定義していない欄(例: `acceptence`)を持つノード、**When** 検査する、**Then** S-00 の違反になる。
11. **Given** 同じオブジェクトに同じキーを二度持つ JSON、**When** 検査する、**Then** 終了コードは 2 である。
12. **Given** 二つのノードが同じ ID の受け入れ条件を持つグラフ、**When** 検査する、**Then** S-07 の違反になる。
13. **Given** `selection` を持つ AND のノード、**When** 検査する、**Then** S-05 の違反になる。
14. **Given** 親が子を挙げ忘れ、その子が2つ目の根になったグラフ、**When** 検査する、**Then** S-11 の違反として2つの根が報告される。
15. **Given** 10,000 ノードの直鎖の正しいグラフ、**When** 検査する、**Then** 異常終了せず、違反はない。**Given** 入れ子が 100,000 段の JSON の配列、**Then** 終了コードは 2 である。

### User Story 2 - スキル合成グラフの多段の DAG と、監査役の権限の宣言を検査できる (Priority: P1)

保守者が、引き継ぎ書 §20.3 の例 B のような多段のスキル合成グラフを宣言ファイルに書き、検査器にかける。二段以上の参照と共有子は合格する。循環、存在しない子、定義していない権限や役割、監査役や検査役が書き込みを宣言していること、監査役から書き込むスキルへ届くことは違反になる。

**Why this priority**: 引き継ぎ書 §19.3 は、spec 058 の一段の制限を意識的な設計の変更の対象とし、まず互換性のテストを置くとした。一段の制限を緩める前に、多段の構成が満たすべき条件を機械的に確かめる手段が要る。監査役の権限の逸脱は、T-07 が先に固定すべきとした検査である。

**Independent Test**: スキル合成グラフの負例と正例を検査器にかけ、終了コードと規則 ID を確かめる。

**Acceptance Scenarios**:

1. **Given** 引き継ぎ書 §20.3 の例 B(FR-009)に、`change-assurance` から `refinement-checker` へのエッジを加えたグラフ。`change-assurance` → `goal-refinement` → `refinement-checker` の二段の参照を持ち、`refinement-checker` は `change-assurance` と `goal-refinement` の共有子である。**When** 検査する、**Then** 違反はない。`change-assurance`、`goal-refinement`、`refinement-checker` は例 B にある架空のスキル名であり、スキルとしては存在しない。`problem-definition` は実在するスキルである。
2. **P1-09** **Given** 役割が `auditor` で、権限が `workspace_write` のスキル、**When** 検査する、**Then** S-09 の違反になる。この検査は宣言の照合であり、実行時の権限を制御しない。
3. **Given** 権限が `write` のような定義していない値のスキル、**When** 検査する、**Then** S-09 の違反になる。
4. **Given** 権限が `read_only` の `auditor` の子に、`workspace_write` のスキルがあるグラフ、**When** 検査する、**Then** S-09 の違反として、届いた先のスキルが報告される。
5. **Given** スキルどうしの循環、**When** 検査する、**Then** S-03 の違反になる。

### User Story 3 - 既存の一段の宣言を互換モードで検査でき、既存の検査とリポジトリの振る舞いは変わらない (Priority: P2)

保守者が、宣言ファイルを持たない現在のリポジトリで、スキルのディレクトリを互換モードの検査器にかける。spec 058 の構造の規則(子の存在、自分自身の宣言の禁止、一段の制限)が判定される。既存の検査スクリプトの件数と結果は、変更の前後で変わらない。

**Why this priority**: 新しい形式を入れても既存の構成の意味を黙って変えないことは、引き継ぎ書 §20.5 の完了条件である。ただし、現在のリポジトリには親スキルがないため、利用者が直ちに使う場面は User Story 1・2 より少ない。

**Independent Test**: 一時ディレクトリに、spec 058 の受け入れシナリオと同じ架空のスキルを作り、互換モードの判定を確かめる。あわせて、既存の検査スクリプトを変更の前後で実行し、結果を比べる。

**Acceptance Scenarios**:

1. **P1-11** **Given** 宣言ファイルのない現在の `.claude/skills/`、**When** 互換モードで検査する、**Then** 違反はなく、終了コードは 0 である。
2. **P1-11** **Given** 変更後のリポジトリ、**When** `tests/run-config-pyramid.sh` を手元で実行する、**Then** 変更前と同じ 57 件がすべて通る。このスクリプトは CI では実行されない。
3. **Given** 架空のスキル `parent`、`child-a`、`child-b`(`parent` が `child-a` と `child-b` を子として宣言し、どの子も子を宣言しない)、**When** 互換モードで検査する、**Then** 違反はない。**Given** 同じ構成を spec 058 の受け入れシナリオ5・6・8のように変えたもの(存在しない子 `ghost` の宣言、`child-a` による `child-b` の宣言、`parent` による自分自身の宣言)、**Then** それぞれ S-02、S-10、S-03 の違反になる。
4. **P1-12** **Given** 変更後のリポジトリ、**When** ネットワークを使わないローカルの検査をすべて実行する、**Then** 変更前に通っていた検査がすべて同じ件数で通る。

### Edge Cases

- **合格の意味**: 合格は、検査した規則に構造が合うことだけを意味する。検査器の出力は、検査した規則の一覧を示す。互換モードでは S-09 を検査しないため、その一覧に S-09 を含めない。
- **権限と役割は自己申告である**: `permission` と `role` は意図を記録する値であり、Claude Code の権限設定や実行環境の制約を変えない。書き込めるスキルが `role: worker` と申告すれば S-09 は通る。実際の書き込みの禁止は実行環境で強制する(引き継ぎ書 §20.4)。
- **深い入れ子と長い鎖**: JSON の読み込みが入れ子の深さの上限を超えた入力は、終了コード 2 にする。長い親子の鎖や大きなグラフでも、検査器は異常終了しない(User Story 1 のシナリオ15)。
- **互換モードのコードブロック**: コードブロックの中に書かれた「- `名前`」の行は、spec 058 の FR-001 と同じく宣言とみなさない。
- **互換モードと spec 058 の検査の違い**: `tests/run-config-pyramid.sh` は、宣言された子が配列 `authored_skills` にあることを求める。検査器はこの配列を知らず、子のディレクトリに `SKILL.md` があることだけを求める。たとえば、自作スキルでない `apple-notes` を宣言した親は、検査器には合格し、`tests/run-config-pyramid.sh` では違反になる。本文での名前による参照(spec 058 の FR-002、FR-005)も検査器の対象外である。これらは引き続き `tests/run-config-pyramid.sh` が判定する。spec 058 が自分自身の宣言として報告する違反を、検査器は循環(S-03)として報告する。同じ子の二度の宣言は、spec 058 では違反にならず、検査器では S-02 の違反になる(D11)。
- **例のファイルのスキル名**: スキル合成グラフの例は、まだ存在しないスキルの名前(`change-assurance`、`goal-refinement`、`refinement-checker`)を含む。宣言ファイルのスキル ID を実在の `SKILL.md` と照合するのは互換モードだけであり、宣言ファイルと実在のスキルの食い違いは Phase 1 では見つけない。
- **記号のリンク**: 互換モードは、`SKILL.md` が記号のリンクであっても、その先を読む。読むだけで、何も書かない。

## Requirements *(mandatory)*

要件は、入力の形式(FR-001、FR-002)、判定の規則(FR-003、FR-004)、出力と終了コードと読み取り専用の性質(FR-005〜FR-008、FR-013)、例・検査スクリプト・文書・変えないもの(FR-009〜FR-012)から成る。

### Functional Requirements

- **FR-001**: 検査器は、1つの宣言ファイル、または互換モードで1つのスキルのディレクトリを入力にとる。宣言ファイルは、最上位がオブジェクトで、`schema_version` が整数の 1 であり、`requirements` と `skills` のちょうど一方を配列として持ち、ほかの欄を持たない。
- **FR-002**: ノードの欄、欄の値の型、欄がないときや値が誤っているときにどの規則の違反になるかを、[data-model.md](data-model.md) の表で定める。要求のノードは `id`、`statement`、`decomposition`、`acceptance` を持たなければならず、`children`、`assumptions`、`counterexamples`、`selection` を持ってよい。受け入れ条件は `id`、`description`、`level` を持つ。スキルのノードは `id`、`permission`、`role` を持たなければならず、`children` を持ってよい。欄がないときは、その欄を判定する規則の違反とする(`id` は S-01、`decomposition` は S-04、`acceptance` は S-06、`permission` と `role` は S-09)。定義していない欄、値の型の誤り、`statement` や `description` の欠如は S-00 の違反とする。
- **FR-003**: 検査器は、次の規則で判定する。S-01〜S-10 は引き継ぎ書 §20.4 に対応する。

  | 規則 | 対象 | 合格の条件 |
  |---|---|---|
  | S-00 値の形式 | 宣言ファイル | 各ノードがオブジェクトで、各欄の値の型が正しく、定義していない欄を持たない |
  | S-01 ID の一意性 | 宣言ファイル | 各ノードの `id` が空でない文字列で、グラフの中で一意である |
  | S-02 参照先の存在 | すべて | 子に挙げた ID がグラフの中で定義されている。互換モードでは、子のディレクトリに `SKILL.md` がある。同じ子を二度挙げない(D11) |
  | S-03 非循環 | すべて | 子をたどって元のノードに戻れない。自分自身を子にすることを含む。違反は循環の経路を示す |
  | S-04 分解の型 | 要求 | `decomposition` が AND、OR、LEAF のいずれかである。LEAF は子を持たず、AND と OR は2件以上の子を持つ |
  | S-05 OR の選択条件 | 要求 | OR の `selection` が、すべての子の ID について空でない条件を持ち、子でない ID を持たない。OR でないノードは `selection` を持たない |
  | S-06 受け入れ条件の存在 | 要求 | すべてのノードが1件以上の受け入れ条件を持つ(D7) |
  | S-07 受け入れ条件の ID と水準 | 要求 | 受け入れ条件の `id` が空でない文字列で、グラフ全体で一意であり、`level` が L1、L2、L3 のいずれかである |
  | S-08 共有子 | すべて | 複数の親を持つ子は、循環がなければ合格する。違反を出さない規則であり、子の複製を求めない |
  | S-09 権限の宣言 | スキル(宣言ファイル) | `permission` と `role` が D6 の値のいずれかである。`auditor` と `checker` は、自分も、子をたどって届くすべてのノードも `read_only` である |
  | S-10 一段の互換 | 互換モード | 宣言された子が、自分の子を宣言しない(spec 058 の FR-004) |
  | S-11 単一の根 | 要求 | 親を持たないノードが2つ以上ない(D12)。1つもないときは必ず循環があり、S-03 として報告するため、S-11 では重ねて報告しない |

- **FR-004**: 互換モードは、ディレクトリの直下で `SKILL.md` を持つ各サブディレクトリを、その名前を ID とするスキルとして、名前の順に読む。「`## Child skills`」節の宣言は、spec 058 の FR-001 の文を正とし、その実装である `tests/run-config-pyramid.sh` の関数 `declared_children` と同じに読む。すなわち、行頭が「```」の行でコードブロックの内外を切り替え、コードブロックの外で行頭が「`## `」の行で節を切り替え、「`## Child skills`」節の中で行頭が「- `名前`」(名前は英数字、`_`、`-`)の行を子の宣言とする。互換モードは S-02、S-03、S-08、S-10 を判定する。
- **FR-005**: 検査器は、違反ごとに、規則 ID、ノードの ID(ノードに結び付かない違反では空)、理由を報告する。出力は、人が読む形式と、機械が読む JSON の形式を選べる。引数、JSON の欄(`input_file`、`status`、`rules_checked`、`violations` など)、人が読む形式は、[contracts/cli.md](contracts/cli.md) で固定する。
- **FR-006**: 終了コードは、違反がなければ 0、規則の違反があれば 1、入力を解釈できなければ 2 とする。解釈できない入力とは、引数の誤り、読めないファイルやディレクトリ、通常のファイルでない入力(FIFO やデバイス)、5 MiB を超える宣言ファイル(互換モードでは 5 MiB を超える `SKILL.md`)、UTF-8 でない入力、JSON の構文の誤り、同じキーの重複、JSON の読み込みが扱えない深い入れ子、FR-001 に合わない最上位、の各場合である。
- **FR-007**: 検査器は、入力を読む以外のことをしない。ファイルを書かず、ネットワークに接続せず、入力の内容をコードとして実行しない。
- **FR-008**: 同じ入力に対して、検査器は違反の順序を含めて同じ出力を返す。
- **FR-009**: 要求の論理グラフとスキル合成グラフの例を1つずつ、`tools/refinement-checker/examples/` に置く。要求の例は引き継ぎ書 §20.3 の例 A(根 `REQ-ROOT` が AND で、葉 `REQ-READ` と `REQ-EXPORT` を持つ)、スキルの例は例 B(`change-assurance` が `problem-definition` と `goal-refinement` を、`goal-refinement` が `refinement-checker` を子に持つ)のノードとエッジをそのまま使い、本仕様が求める欄(すべてのノードの受け入れ条件、スキルの `role`)を加える。どちらも検査に合格する。
- **FR-010**: 新しい検査スクリプト `tests/run-refinement-checker.sh` は、検査器の受け入れテスト、2つの例の検査、現在の `.claude/skills/` の互換モードの検査を実行する。あわせて、D14 の後の Phase へ送るテストを `NOT RUN` の行として表示し、合格の件数に数えない。CI の必須ジョブ `test` がこのスクリプトを実行する。
- **FR-011**: 検査器の用途、実行主体、配布先、使い方、宣言の形式、規則、終了コード、限界を、検査器の README(英語と日本語)に書く。`README.md` と `README.ja.md` のファイル構成、検証、CI の節を、変更後の内容に合わせる。
- **FR-012**: `.claude/` の下のファイル、`install.sh`、`tests/run-config-pyramid.sh` を変えない。
- **FR-013**: 人が読む形式の出力では、ID と理由の中の制御文字をエスケープする(D13)。JSON の形式では、JSON の文字列のエスケープに従う。

### Key Entities

- **要求のノード**: 1つの要求。ID、要求の文、分解の型、子の ID、前提、受け入れ条件、反例、OR の選択条件を持つ。
- **受け入れ条件**: 1つの検証の宣言。グラフ全体で一意な ID、説明、水準を持ち、それを並べた1つのノードに属する。
- **スキルのノード**: 1つのスキル。ID、子の ID、権限、役割を持つ。
- **違反**: 規則 ID、ノードの ID、理由の組。
- **検査結果**: 入力、グラフの種類、状態、検査した規則の一覧、違反の一覧、読めなかった理由。

## Out of Scope

引き継ぎ書 §20.2 の非対象に従い、次のものは作らない。新しいスキル、新しいサブエージェント、実行時の再帰的な委譲、既存のスキルの書き換え、検査器による自動修正、テストの実行結果や証拠の収集(引き継ぎ書 §19.1 の実行モデル `RUN` と保証モデル `CASE`。前者はスキルやジョブを実行する順序、後者は主張と証拠の対応である。Phase 3 で扱う)、OR の条件の排他と網羅の検査(Phase 2)、本番環境やクラウドへの接続、GitHub の設定の変更、`install.sh` による配布。
