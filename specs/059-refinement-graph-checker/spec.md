## 用語

- **引き継ぎ書**: 利用者が渡した Markdown の文書『AIコーディングのレビュー限界を突破するための設計・研究・実装引き継ぎ書』(2026-11-04 作成、2026-11-06 更新)。利用者の手元のファイルで、このリポジトリには含めない。本仕様の節番号(§20.4 など)は、この文書の節番号である。
- **Phase 1〜5**: 引き継ぎ書 §21 の段階。Phase 1 は宣言の形式と静的な検査、Phase 2 は問題定義と論理分解、Phase 3 は多層の独立した検証、Phase 4 はレビューの判断資料、Phase 5 は比較実験である。
- **要求の論理グラフ**: 要求をノードとし、親の要求から子の要求への分解をエッジとするグラフ。各ノードは、分解の型と受け入れ条件を持つ。
- **分解の型(AND、OR、LEAF)**: AND は、子のすべてが親に必要であることを表す。OR は、子のうちどれか一つを、条件に応じて選ぶ代替であることを表す。LEAF は、それ以上分解しない葉であることを表す。型は宣言であり、子が親を満たすことの証明ではない。
- **受け入れ条件**: ノードが満たされたと判定するための検証の宣言。ID、説明、水準を持つ。宣言であって、検証を実行した結果ではない。
- **水準(L1、L2、L3)**: 引き継ぎ書 §6 の検証の層。L1 は葉の個別の検証、L2 は親の統合の検証、L3 はシステム全体の検証である。
- **スキル合成グラフ**: スキルをノードとし、親スキルから、それが参照できる子スキルへのエッジを持つグラフ。エッジは静的な参照の関係であり、実行の順序、権限の委譲、自動の起動を意味しない(引き継ぎ書 §20.3 B)。
- **有向非巡回グラフ(DAG)**: 向きのあるエッジをたどっても、元のノードに戻れないグラフ。一つの子が複数の親を持ってよい。複数の親を持つ子を**共有子**と呼ぶ。
- **宣言ファイル**: 要求の論理グラフ、またはスキル合成グラフの一方を書いた JSON のファイル。
- **互換モード**: 宣言ファイルの代わりに、スキルを並べたディレクトリの各 `SKILL.md` にある「`## Child skills`」節からスキル合成グラフを作り、検査する動き方。
- **spec 058**: `specs/058-parent-skill-references/spec.md`。親スキルが `SKILL.md` の「`## Child skills`」節で子を宣言でき(FR-001)、宣言された子は自作スキルでなければならず(FR-003)、子は自分の子を宣言できない(FR-004、一段の制限)と定めた。
- **規則 ID(S-00〜S-10)**: 本仕様が定める検査の規則の名前。S-01〜S-10 は引き継ぎ書 §20.4 の番号と意味に合わせた。S-00(形式)は本仕様で加えた。
- **受け入れシナリオ ID(P1-01〜P1-12)**: 引き継ぎ書 §20.5 の受け入れテストの番号。本仕様の受け入れシナリオに、その番号を付ける。
- **検査器(`refinement-checker`)**: 本仕様で作る、読み取り専用のコマンド。宣言ファイルまたはスキルのディレクトリを読み、規則の違反を報告する。
- **終了コード**: 検査器のプロセスが終わるときに返す数値。呼び出した側(CI など)は、この数値で合否を判断する。

## 背景

本仕様が埋める差分は、要求とスキルの関係を型付きで宣言し、機械的に照合する共通の形式がないことである。引き継ぎ書 §4 の問題カードの項目で、次に示す。

| 区分 | 内容 | 確度と根拠 |
|---|---|---|
| 現状 | このリポジトリでスキルどうしの関係を宣言する手段は、spec 058 の「`## Child skills`」節だけであり、一段に限られる。要求の AND/OR の分解、親自身の受け入れ条件、スキルの権限を記述し、機械的に照合する形式はない | 観測。`origin/main`(コミット 34708a5)の spec 058 と `tests/run-config-pyramid.sh` を読んだ |
| 理想 | 要求とスキルの多段の関係を DAG として宣言でき、ID の重複と欠損、循環、分解の型の不整合、受け入れ条件の欠如、監査役の権限の逸脱を、既存の構成を変えずに機械的に検出できる | 引き継ぎ書 §20.1 の目標 |
| 差分 | 型付きで検査できる共通の宣言の形式と、その検査器がない | 観測と推論。既存の検査が本文の名前による参照と一段の宣言しか見ないことから推論した |
| 意義 | 親スキルや独立した監査役を増やす前に形式の不整合を止める。後の Phase で、要求・検証の証拠・レビューの判断資料を ID で結ぶ土台にする | 推論。レビュー時間を減らす効果は測っていない |
| 完了条件 | 受け入れシナリオ P1-01〜P1-12 が再現できる形で通り、既存の検査の結果が変わらない | 引き継ぎ書 §20.5 |

Phase 1 を完了しても、引き継ぎ書の最上位の目標 G0 を達成したことにはならない。G0 は、元の要求1件あたりの人間の介入時間の中央値を従来より 20% 以上減らすこと(OUT-1)と、業務・本番システムの品質と安全性を保つこと(OUT-2)の両方であり、Phase 5 の比較実験で判定する。

## User Scenarios & Testing *(mandatory)*

3つの利用者の物語は、検査器が要求の分解の構造の誤り(User Story 1)とスキルの合成の構造の誤り(User Story 2)を見つけ、既存の一段の宣言の意味を変えないこと(User Story 3)を、それぞれ独立に確かめる。

### User Story 1 - 要求の分解の構造の誤りを、実装へ進む前に機械的に見つけられる (Priority: P1)

保守者、または保守者の指示で作業する Claude が、要求の分解を宣言ファイルに書き、検査器にかける。ID の重複、存在しない子、循環、型と子の数の不整合、OR の選択条件の欠如、受け入れ条件の欠如、水準の誤りは、規則 ID とノードの ID を添えた違反として報告され、終了コードは 1 になる。共有子を持つ正しい DAG は合格し、終了コードは 0 になる。

**Why this priority**: 引き継ぎ書が最初の実験対象とした能力である(§19.9)。これがないと、後の Phase の分解や監査の結果を機械的に照合できない。

**Independent Test**: 負例と正例の宣言ファイルを検査器にかけ、終了コードと規則 ID を確かめる。負例ごとに、期待する規則の違反だけが出ることを確かめる。

**Acceptance Scenarios**:

1. **P1-01** **Given** 二つのノードが同じ `id` を持つ要求の論理グラフ、**When** 検査する、**Then** S-01 の違反として重複した ID が報告され、終了コードは 1 である。
2. **P1-02** **Given** 定義されていない ID を子に挙げるノード、**When** 検査する、**Then** S-02 の違反として、親の ID と不明な子の ID が報告される。
3. **P1-03** **Given** A→B→C→A の循環、**When** 検査する、**Then** S-03 の違反として、循環の経路 `A -> B -> C -> A` が報告される。
4. **P1-04** **Given** 子を持つ LEAF、または子が1件だけの AND、**When** 検査する、**Then** それぞれ S-04 の違反として、型と子の数が報告される。
5. **P1-05** **Given** 子の一つに選択条件がない OR、**When** 検査する、**Then** S-05 の違反として、条件のない子の ID が報告される。
6. **P1-06** **Given** 受け入れ条件を持たない AND の親、**When** 検査する、**Then** S-06 の違反が報告される。
7. **P1-07** **Given** 親の受け入れ条件に L2、葉の受け入れ条件に L1、根の受け入れ条件に L3 を付けた正しいグラフ、**When** 検査する、**Then** 違反はなく、終了コードは 0 である。**Given** 水準が `L4` の受け入れ条件、**Then** S-07 の違反になる。
8. **P1-08** **Given** 二つの親が同じ子を参照し、循環はないグラフ、**When** 検査する、**Then** 違反はない(S-08)。
9. **P1-10** **Given** JSON として読めないファイル、または `schema_version` が 1 でないファイル、**When** 検査する、**Then** 終了コードは 2 で、読めない理由が表示される。

### User Story 2 - スキル合成グラフの多段の DAG と、監査役の権限の宣言を検査できる (Priority: P1)

保守者が、引き継ぎ書 §20.3 B のような多段のスキル合成グラフを宣言ファイルに書き、検査器にかける。二段以上の参照と共有子は合格する。循環、存在しない子、定義していない権限や役割、監査役や検査役が書き込みを宣言していること、監査役から書き込むスキルへ届くことは違反になる。

**Why this priority**: spec 058 の一段の制限を緩める前に、多段の構成が満たすべき条件を機械的に確かめる手段が要る(引き継ぎ書 §19.3)。監査役の権限の逸脱は、引き継ぎ書 §19.6 の T-07 が先に固定すべきとした検査である。

**Independent Test**: スキル合成グラフの負例と正例を検査器にかけ、終了コードと規則 ID を確かめる。

**Acceptance Scenarios**:

1. **Given** `change-assurance` → `goal-refinement` → `refinement-checker` の二段の参照と、二つの親が同じ子を参照する共有子を持つグラフ、**When** 検査する、**Then** 違反はない。
2. **P1-09** **Given** 役割が `auditor` で、権限が `workspace_write` のスキル、**When** 検査する、**Then** S-09 の違反になる。この検査は宣言の照合であり、実行時の権限を制御しない。
3. **Given** 権限が `write` のような定義していない値のスキル、**When** 検査する、**Then** S-09 の違反になる。
4. **Given** 権限が `read_only` の `auditor` の子に、`workspace_write` のスキルがあるグラフ、**When** 検査する、**Then** S-09 の違反として、届いた先のスキルが報告される。
5. **Given** スキルどうしの循環、**When** 検査する、**Then** S-03 の違反になる。

### User Story 3 - 既存の一段の宣言を互換モードで検査でき、既存の検査とリポジトリの振る舞いは変わらない (Priority: P2)

保守者が、宣言ファイルを持たない現在のリポジトリで、スキルのディレクトリを互換モードの検査器にかける。spec 058 の一段の宣言は、spec 058 と同じ意味で検査される。既存の検査スクリプトの件数と結果は、変更の前後で変わらない。

**Why this priority**: 新しい形式を入れても既存の構成の意味を黙って変えないことは、引き継ぎ書 §20.5 の完了条件である。ただし、現在のリポジトリには親スキルがないため、利用者が直ちに使う場面は User Story 1・2 より少ない。

**Independent Test**: 一時ディレクトリに、spec 058 の受け入れシナリオと同じ架空のスキルを作り、互換モードの判定を確かめる。あわせて、既存の検査スクリプトを変更の前後で実行し、結果を比べる。

**Acceptance Scenarios**:

1. **P1-11** **Given** 宣言ファイルのない現在の `.claude/skills/`、**When** 互換モードで検査する、**Then** 違反はなく、終了コードは 0 である。
2. **P1-11** **Given** 変更後のリポジトリ、**When** `tests/run-config-pyramid.sh` を実行する、**Then** 変更前と同じ 57 件がすべて通る。
3. **Given** spec 058 の受け入れシナリオ5・6・8と同じ架空のスキル(存在しない子 `ghost` の宣言、子による孫の宣言、自分自身の宣言)、**When** 互換モードで検査する、**Then** それぞれ S-02、S-10、S-03 の違反になる。spec 058 の受け入れシナリオ1と同じ正しい宣言は合格する。
4. **P1-12** **Given** 変更後のリポジトリ、**When** ネットワークを使わないローカルの検査をすべて実行する、**Then** 変更前に通っていた検査がすべて通り、変更前から失敗していた検査を隠さない。

### Edge Cases

- **合格の意味**: 合格は、検査した規則に構造が合うことだけを意味する。検査器の出力は、検査した規則の一覧を示す。互換モードでは S-09 を検査しないため、その一覧に S-09 を含めない。
- **権限の宣言は強制ではない**: `permission: read_only` は意図を記録する値であり、Claude Code の権限設定や実行環境の制約を変えない。実際の書き込みの禁止は実行環境で強制する(引き継ぎ書 §20.4)。
- **同じキーを二度持つ JSON**: 後の値が前の値を黙って上書きし、内容を隠し得るため、読めない入力として終了コード 2 にする。
- **深い入れ子と長い鎖**: 入れ子が深すぎて読めない JSON は、終了コード 2 にする。長い親子の鎖や大きなグラフでも、検査器は異常終了しない。
- **互換モードのコードブロック**: コードブロックの中に書かれた「- `名前`」の行は、spec 058 の FR-001 と同じく宣言とみなさない。
- **互換モードと spec 058 の検査の違い**: `tests/run-config-pyramid.sh` は、宣言された子が配列 `authored_skills`(自作スキルの一覧)にあることを求める。検査器はこの配列を知らず、子のディレクトリに `SKILL.md` があることを求める。本文での名前による参照(spec 058 の受け入れシナリオ1〜4・7)は検査器の対象外であり、引き続き `tests/run-config-pyramid.sh` が検査する。spec 058 が自分自身の宣言として報告する違反を、検査器は循環(S-03)として報告する。
- **例のファイルの将来のスキル名**: スキル合成グラフの例は、まだ存在しないスキル(`change-assurance`、`goal-refinement`)を含む。宣言ファイルのスキル ID を実在の `SKILL.md` と照合するのは互換モードだけであり、宣言ファイルでは照合しない。
- **複数の根**: 親を持たないノードが複数あってもよい。各ノードは独立した根として扱う。

## Requirements *(mandatory)*

要件は、入力の形式(FR-001、FR-002)、判定の規則(FR-003、FR-004)、出力と終了コードと読み取り専用の性質(FR-005〜FR-008)、例・検査スクリプト・文書・変えないもの(FR-009〜FR-012)から成る。

### Functional Requirements

- **FR-001**: 検査器は、1つの宣言ファイル、または互換モードで1つのスキルのディレクトリを入力にとる。宣言ファイルは、最上位がオブジェクトで、`schema_version` が 1 であり、`requirements` と `skills` のちょうど一方を配列として持つ。
- **FR-002**: 要求のノードは、`id`(文字列)、`statement`(空でない文字列)、`decomposition`(AND、OR、LEAF)、`acceptance`(受け入れ条件の配列)を必ず持つ。`children`(ID の配列、省略時は空)、`assumptions` と `counterexamples`(文字列の配列)、`selection`(OR だけ)を持ってよい。受け入れ条件は `id`、`description`(空でない文字列)、`level` を持つ。スキルのノードは `id`、`permission`、`role` を必ず持ち、`children` を持ってよい。これ以外の欄と、型の誤りは S-00 の違反とする。
- **FR-003**: 検査器は、次の規則で判定する。S-01〜S-10 は引き継ぎ書 §20.4 に対応する。

  | 規則 | 対象 | 合格の条件 |
  |---|---|---|
  | S-00 形式 | 宣言ファイル | 各ノードがオブジェクトで、FR-002 の必須の欄を持ち、各欄の型が正しく、定義していない欄を持たない |
  | S-01 ID の一意性 | 宣言ファイル | 各ノードの `id` が空でない文字列で、グラフの中で一意である |
  | S-02 参照先の存在 | すべて | 子に挙げた ID がグラフの中で定義されている。互換モードでは、子のディレクトリに `SKILL.md` がある。同じ子を二度挙げない |
  | S-03 非循環 | すべて | 子をたどって元のノードに戻れない。自分自身を子にすることを含む。違反は循環の経路を示す |
  | S-04 分解の型 | 要求 | `decomposition` が AND、OR、LEAF のいずれかである。LEAF は子を持たず、AND と OR は2件以上の子を持つ |
  | S-05 OR の選択条件 | 要求 | OR の `selection` が、すべての子の ID について空でない条件を持ち、子でない ID を持たない。OR でないノードは `selection` を持たない |
  | S-06 受け入れ条件の存在 | 要求 | すべてのノードが1件以上の受け入れ条件を持つ(D7) |
  | S-07 受け入れ条件の ID と水準 | 要求 | 受け入れ条件の `id` が空でなく、グラフ全体で一意であり、`level` が L1、L2、L3 のいずれかである |
  | S-08 共有子 | すべて | 複数の親を持つ子は、循環がなければ合格する。違反を出さない規則であり、子の複製を求めない |
  | S-09 権限の宣言 | スキル(宣言ファイル) | `permission` と `role` が D6 の値のいずれかである。`auditor` と `checker` は、自分も、子をたどって届くすべてのノードも `read_only` である |
  | S-10 一段の互換 | 互換モード | 宣言された子が、自分の子を宣言しない(spec 058 の FR-004) |

- **FR-004**: 互換モードは、ディレクトリの直下で `SKILL.md` を持つ各サブディレクトリを、その名前を ID とするスキルとして読む。「`## Child skills`」節の宣言は spec 058 の FR-001 と同じに読む。すなわち、コードブロックの外で、節の見出しから次の `## ` 見出しまでの、「- `名前`」で始まる行を子の宣言とする。互換モードは S-02、S-03、S-08、S-10 を判定する。
- **FR-005**: 検査器は、違反ごとに、規則 ID、ノードの ID(ノードに結び付かない違反では空)、理由を報告する。出力は、人が読む形式と、機械が読む JSON の形式を選べる。JSON の結果は、出力形式の版、入力のパス、グラフの種類、状態(`passed`、`failed`、`error`)、検査した規則の一覧、違反の一覧、読めなかった理由を持つ。
- **FR-006**: 終了コードは、違反がなければ 0、規則の違反があれば 1、入力を解釈できなければ 2 とする。解釈できない入力とは、引数の誤り、読めないファイル、JSON の構文の誤り、同じキーの重複、深すぎる入れ子、最上位がオブジェクトでない、`schema_version` が 1 でない、`requirements` と `skills` のちょうど一方を持たない、の各場合である。
- **FR-007**: 検査器は、入力を読む以外のことをしない。ファイルを書かず、ネットワークに接続せず、入力の内容をコードとして実行しない。
- **FR-008**: 同じ入力に対して、検査器は違反の順序を含めて同じ出力を返す。
- **FR-009**: 要求の論理グラフとスキル合成グラフの例を1つずつ置く。どちらも引き継ぎ書 §20.3 の例と同じ構造で、検査に合格する。
- **FR-010**: 新しい検査スクリプト `tests/run-refinement-checker.sh` は、検査器の受け入れテスト、2つの例の検査、現在の `.claude/skills/` の互換モードの検査を実行する。CI の必須ジョブ `test` がこのスクリプトを実行する。
- **FR-011**: 検査器の用途、実行主体、配布先、使い方、宣言の形式、規則、終了コード、限界を、検査器の README に書く。`README.md` と `README.ja.md` のファイル構成、検証、CI の節を、変更後の内容に合わせる。
- **FR-012**: `.claude/` の下のファイル、`install.sh`、`tests/run-config-pyramid.sh` を変えない。

### Key Entities

- **要求のノード**: 1つの要求。ID、要求の文、分解の型、子の ID、前提、受け入れ条件、反例、OR の選択条件を持つ。
- **受け入れ条件**: 1つの検証の宣言。グラフ全体で一意な ID、説明、水準を持ち、1つのノードに属する。
- **スキルのノード**: 1つのスキル。ID、子の ID、権限、役割を持つ。
- **違反**: 規則 ID、ノードの ID、理由の組。
- **検査結果**: 入力、グラフの種類、状態、検査した規則の一覧、違反の一覧、読めなかった理由。

## Success Criteria *(mandatory)*

成功は、負例を期待どおりに拒否し、既存の検査を一つも崩さず、出力が決定論的で、CI が新しい検査を実行することで測る。

### Measurable Outcomes

- **SC-001**: 受け入れシナリオ P1-01〜P1-10 と User Story 2 の負例は、それぞれ期待する規則の違反だけで失敗し、期待しない違反を出さない。正例は違反なしで合格する。各負例のテストが、検査器を実装する前に失敗することを確かめる。
- **SC-002**: 変更前に通っていたローカルの検査がすべて、同じ件数で通る。変更前の件数は、`run-config-pyramid` 57件、`run-readme-skill-index` 29件、`run-removed-guardrails` 4件、`run-install` 成功、`run-package-safety-bundle` 21件、`run-secure-logging-skill` 40件、`run-digital-agency-frontend-skill` 74件、`pyramid-structure` スキルの単体テスト64件である(2026-11-06、コミット 34708a5 で測定)。
- **SC-003**: 同じ入力で検査器を2回実行すると、2回の出力が一致する。
- **SC-004**: CI の必須ジョブ `test` が `tests/run-refinement-checker.sh` を実行する。

## Assumptions

各項目の確度は、その仮定が利用者の意図に合っている見込みを高・中・低で示す。

- 引き継ぎ書の「push・PR作成は禁止」(§20.6)は、利用者の今回の指示で push に限って解除された(確度: 高)。PR の作成は指示にないため行わない。
- Phase 1 の検査器を使うのは、このリポジトリの保守者と Claude である。ほかのプロジェクトからは、このリポジトリの中の検査器のパスを指定して実行する(確度: 中)。
- 宣言ファイルを実際のプロジェクトのどこに置くかは、Phase 2 で決める。Phase 1 は形式、検査器、例だけを提供する(確度: 中)。
- spec 058 の一段の制限を緩めるかは、多段を要する親スキルが現れたとき(Phase 2)に決める(確度: 中)。

## Out of Scope

引き継ぎ書 §20.2 の非対象に従い、次のものは作らない。新しいスキル、新しいサブエージェント、実行時の再帰的な委譲、既存のスキルの書き換え、検査器による自動修正、テストの実行結果や証拠の収集(引き継ぎ書の実行モデルと保証モデル。Phase 3)、本番環境やクラウドへの接続、GitHub の設定の変更、`install.sh` による配布。
