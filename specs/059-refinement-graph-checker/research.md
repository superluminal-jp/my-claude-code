# Research: 要求とスキルのグラフ検査器の設計の判断

各判断は、spec の要件を満たす選択肢のうち、依存を増やさず、既存の慣例に合い、失敗を黙って成功にしないものを選んだ。

## R1. 実装の言語は Python 3 の標準ライブラリにする

- **Decision**: Python 3(構文は 3.9 以上)の標準ライブラリだけで書く。
- **Rationale**: リポジトリには、標準ライブラリだけで書いた Python の検査器の前例がある(`pyramid-structure` スキルの `scripts/check.py`)。CI の `ubuntu-latest` と macOS の両方に `python3` がある。
- **Alternatives considered**: Bash と `jq` は、DAG の循環の経路の復元と、JSON の重複キーの検出が難しい。Node.js は CI で準備の手順が増える。

## R2. 宣言ファイルは JSON にし、同じキーの重複を拒否する

- **Decision**: JSON を `json.loads` の `object_pairs_hook` で読み、同じオブジェクトに同じキーが二度あれば、読めない入力(終了コード 2)にする。
- **Rationale**: YAML の読み込みには標準ライブラリにない依存が要る(spec D3)。JSON の仕様(RFC 8259)はキーの重複を禁止せず、Python の既定は後の値で黙って上書きするため、宣言の一部が見えなくなり得る。
- **Alternatives considered**: YAML(依存が増える)。重複を許して最後の値を使う(内容を隠す)。

## R3. 循環は反復の深さ優先探索で見つけ、経路を正規化して報告する

- **Decision**: 宣言の順にノードをたどる反復の深さ優先探索で、探索中の経路に戻るエッジを見つけたら、その経路を循環として記録する。同じ循環を重ねて報告しないよう、宣言の順で最も早いノードから始まるように回転させてから、重複を除く。
- **Rationale**: 再帰を使うと、長い鎖で Python の再帰の上限に達する(spec Edge Cases)。回転の正規化により、`A -> B -> C -> A` のように、宣言の順に読める経路になる(P1-03)。
- **Alternatives considered**: 強連結成分だけを報告する方法(循環の経路が分からず、直す箇所を示せない)。

## R4. 違反の順序は規則 ID とノードの宣言の順で固定する

- **Decision**: すべての違反を集めてから、規則 ID、ノードの宣言の順、検出の順に並べる。検出の順は、ノードの中の宣言の順(受け入れ条件の #1、#2、…)に従う。理由の文字列で並べると `#10` が `#2` より前になるため、使わない(`/code-review` の指摘7)。
- **Rationale**: 同じ入力に同じ出力を返す(spec FR-008、SC-003)。辞書や集合の走査の順に頼らない。

## R5. 欄がないときの規則は、その欄を検査する規則にする

- **Decision**: `id` がなければ S-01、`decomposition` がなければ S-04、`acceptance` がないか空なら S-06、`permission` か `role` がなければ S-09 の違反とする。S-00 は、ノードがオブジェクトでない、定義していない欄がある、ある欄の型が誤っている、`statement` がない、の各場合だけを扱う。
- **Rationale**: 一つの欠落を二つの規則で重ねて報告しない。受け入れシナリオ P1-06(受け入れ条件のない親)が、欄を省いても空の配列にしても同じ S-06 になる。

## R6. 互換モードは spec 058 の `awk` と同じ読み方をする

- **Decision**: `tests/run-config-pyramid.sh` の関数 `declared_children` と同じ規則で「`## Child skills`」節を読む。行頭が「```」の行でコードブロックの内外を切り替え、行頭が「`## `」の行で節を切り替え、節の中で行頭が「- `名前`」(名前は英数字・`_`・`-`)の行を子の宣言とする。ディレクトリの直下のサブディレクトリを名前の順に読む。
- **Rationale**: spec D5。読み方が同じなら、互換モードの判定と spec 058 の判定の違いは、spec の Edge Cases に書いた点に限られる。
- **Alternatives considered**: Markdown の構文解析器を使う(依存が増え、spec 058 と読み方が変わり得る)。

## R7. 受け入れテストは、検査器をサブプロセスとして起動する

- **Decision**: テストは `sys.executable -B check_graph.py --format json <入力>` を起動し、終了コードと JSON の `status`・`violations` を確かめる。負例は、違反の規則 ID の集合が期待する集合と一致することを確かめる。
- **Rationale**: 利用者と CI が依存する外から見える契約(引数、出力、終了コード)そのものを確かめる。実装前のテストの失敗(Red)も、存在しないスクリプトの起動として観測できる。終了コード 2 を期待するテストは、JSON の `status` が `error` であることも確かめるため、スクリプトが存在しないことで偶然通ることはない。

## R8. 入力の大きさを 5 MiB に制限する

- **Decision**: 宣言ファイルと各 `SKILL.md` が 5 MiB を超えれば、読めない入力(終了コード 2)にする。
- **Rationale**: 検査器は、AI が生成した宣言など信頼できない入力を読む(引き継ぎ書 §19.5)。システムの境界で入力の大きさを制限し、メモリの枯渇を防ぐ(OWASP ASVS の入力の検証)。このリポジトリの宣言は数 KB である。

## R9. CI は既存のジョブに1ステップを加える

- **Decision**: `.github/workflows/ci.yml` のジョブ `test` に、`bash tests/run-refinement-checker.sh` のステップを加える。
- **Rationale**: `main` の必須チェックはジョブ `test` であり(`.github/rulesets/main-required-checks.json`)、別のジョブを作ると必須チェックの設定の変更が要る。`ubuntu-latest` には `python3` があるため、準備の手順は要らない。
