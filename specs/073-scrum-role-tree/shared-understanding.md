# 共有した理解: harness のスキルとエージェントを、Scrum の役割の木に再編する

**状態**: 合意済み（2026-11-15。問題文に合意し、ADR は「書く」を選んだ）
**記録**: 2026-11-15

## 依頼（利用者の言葉）

- 「綺麗な木構造になるように再整理できるか」
- 対象として「ハーネス自体を再編する」を選んだ。分類の軸には「Scrum の役割」を選び、補足として「Scrumの役割の下に 1 正しい作業を定める 2 統制の下で実行する 3 引き渡す といったさらなる構造を作って位置付ける」と書いた。
- 「A. 現状スキルとして組まれているものも、エージェントとした方が適切なものがあれば変更してよい。エージェントをスキルに変えるのも許可。スキル・エージェントの名称や内容を一覧したときに役割や目的がわかりやすくなるよう適切に調整するのも良い。」

## 理解

`harness/` のスキル（17件）とサブエージェント定義（5件）それぞれに、木の中の場所を1つだけ宣言させる。木は次の3段で、宣言は各ファイルの前付けに置く（方式 A）。

- 第1段: 役割（Product Owner の判断を支える、Developers、Scrum Master）
- 第2段: 枝（1 正しい作業を定める、2 統制の下で実行する、3 引き渡す）
- 第3段: 各要素

あわせて、次のことを行う。

- 宣言が欠けている、不正である、二重であるものを、契約の検査で拒む。
- 基準に照らして、形（スキルかエージェントか）、名前、description を必要なところだけ直す。一覧したときに、役割と目的が読み取れるようにするためである。
- 構成図（`docs/harness/skill-map/`）と、両方の README の目次を、木に合わせて作り直す。

## 範囲

- **含む**
  - 22件の要素の前付けへの場所の宣言と、その検査
  - 次の基準に当てはまる要素の、形の変更と改名
  - 一覧での見え方（description、README の目次）
  - 構成図と、関係する文書・テスト・評価の対応表の追従
- **含まない**
  - 頂点の指示（`harness/CLAUDE.md`）とルールの変更（どの役割にも共通で、汎用に保つ）
  - 基準が求めない手順の変更
  - Claude.ai 用の写しの作り直しと、再アップロード
  - `scrum/` の Product Goal と Definition of Done を埋めること（Product Goal は Product Owner、Definition of Done は組織の標準か、なければ Scrum Team が決める [SG20, pp.5-6, 12]。Scrum Master の所見 F-4 を受けて 2026-11-15 に直した）

## 基準

- **役割**: 要素の主な成果物が、Scrum Guide 2020 でだれのアカウンタビリティに属するかで決める [SG20, pp.5-7]。
- **枝**: `docs/harness/capability-map.json` が、その要素の主な段階に付けている枝で決める。
- **形**: 次の2つを両方満たすものはエージェントにし、それ以外はスキルにする（`harness/CLAUDE.md`:16 の委任の条件から導いた案）。
  - (a) 作者から独立した読み手が要る、または出力が長く結果だけが要る
  - (b) 人との対話も、完了の判定も要らない
- **改名**: 名前が、要素の実際の目的と違うことを述べている場合、または一覧の読み手が役割を取り違える場合にだけ改名する。改名1件ごとに6〜20ファイルの追従が要り、Claude.ai の写しとの対応も切れるためである。

## 前提（確度）

- **木の辺は「属する」関係だけにする（中）。** 従える関係、判断基準を重ねる関係、サブエージェントを起動させる関係は、木の外の関係として別の図に描く。
- **前回示した置き場所の例は、訂正がなかったので受け入れられたものとする（中）。**
- **`apply-scrum-guide` は分割しない（中）。** その主な成果物は、Developers のアカウンタビリティに属する。
- **エージェント定義の前付けの未知のキーは、Claude Code に無視される（高）。** 根拠は <https://code.claude.com/docs/en/sub-agents.md> の Frontmatter reference。ただし、このリポジトリの `tests/assert_reviewer_agent.py`:62 は前付けの欄を固定しているので、その検査を直す必要がある。
- **モデルに見える一覧に出るのは、スキルの `description` だけである（高）。** 根拠は <https://code.claude.com/docs/en/skills.md>。前付けの `metadata` は Claude Code の動作に影響しない。

## 完了の条件

- 22件の宣言がすべて検査に通る。検査は、宣言を欠いた写しを拒むことを先に確かめておく。
- 形と改名の基準を22件すべてに当てた結果が、要素ごとに記録されている。
- 木の図で、すべての節の親が1つであり、図の検査器が通る。木の外の関係は別の図にある。
- 既存のテスト（`tests/run-harness-skills.sh` ほか、このリポジトリの `tests/run-*.sh`）がすべて通る。
- 変更全体が `deliver-change` の手順を経ている。ゲートの判断とレビューカード、Scrum Master の所見が報告されている。

## 未決の点とリスク

- **問題文への合意**: 2026-11-15 に合意した（[problem.md](problem.md)）。
- **ADR**: 利用者は「書く」を選んだ。ADR-0026 を Proposed で書き、Accepted にするかは利用者が決める。
- **ADR-0025 の前提が現行の文書と食い違う。** ADR-0025 は「サブエージェントは別のサブエージェントを起動できない」ことを判断材料の1つにしている。一方、現行の公式文書は、3層まで起動できると述べている（<https://code.claude.com/docs/en/sub-agents.md>）。結論（判断はメインの会話に残す）は別の根拠でも成り立つ。それでも、この食い違いを記録する必要がある。
- **Claude.ai 用の写しが古いまま残る。** 改名やスキルからエージェントへの変更があれば、写しとの対応が切れる。

## 反証の後に利用者が決めたこと（2026-11-15）

- **役割の基準**: 要素の主な成果物が何を決めるかで分ける。Product Owner は何をなぜ作るか、Developers はどう作りどう確かめるか、Scrum Master は Scrum が成り立っているか。`manage-scrum-artifacts` は Scrum Master に置く。配置は Product Owner 3件、Developers 17件、Scrum Master 2件。
- **標識**: `description` の末尾に `[<役割> / <枝>]` を付ける。スキルの選ばれ方への影響は測らず、未検証のリスクとして受け入れる。
