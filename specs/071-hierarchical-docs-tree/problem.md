# Problem Statement: sync-docs では、リポジトリのルートから階層をたどって読み進められる文書の木を作ることも、検査することもできない

**Status**: Complete
**Generated**: 2026-11-14

この問題文の対象は、このリポジトリの `harness/skills/sync-docs/` である。2026-11-10〜14 の利用者とのやりとりから始まった。利用者は「living documentation の一環として、機能単位で作業したソースコードのフォルダの中に README や構成図を置きたいが、いずれ保守されなくなってコードと食い違い、AI が間違った情報をもとに答えるのではないか」と懸念し、そのうえで「レポのルートから階層的に構造をもった段階的なドキュメンテーションを構築できるように」と求めた。

用語:
- **階層**: README を置く単位になるフォルダの段のこと。リポジトリのルート、プロダクト（1つのリポジトリに複数のプロダクトがあるとき）、機能フォルダ（例 `src/features/<機能>/`）の3段を想定する。
- **文書の木**: 各階層の README を、親から子へのリンクと子から親へのリンクで結んだもの。

## 理想の状態

- 人も AI も、リポジトリのルートの README から1段ずつ下へ読み進め、目的の機能フォルダの README までたどり着ける。
- 各階層の README は、その範囲が何のためにあるかを書き、1つ下の階層の README すべてと1つ上の README にリンクする。下の階層の細かい内容は繰り返さない。
- 既存のリポジトリにも、頼まれればこの木を一度に作れる。その後はコードの変更に合わせて保てる。
- 機能フォルダが増えた・消えた・名前が変わったときに、README がないことや親子のリンクが欠けたことを機械的な検査で見つけ、エラーにする。
- 利用者のリポジトリの構成は、1リポジトリに1プロダクトのものと、1リポジトリに複数プロダクトのものがあり、どちらにも当てはまる。

## 現在の状態（このセッションで確認、2026-11-14）

- **README のひな形がどの階層にもない。** `templates/` にあるのは `adr.md`、`architecture.md`、`provenance.md`、`ci/github-actions.yml` だけである。
- **中間の階層と、親子をつなぐ決まりがない。** `references/practices.md` の「Layers, placement, and proximity」は、リポジトリのルートの README（目的と最短の手順を書き、先へリンクし、細部を持たない）と、フォルダごとの README（P1。この skill 独自の判断で出典はないと明記）を挙げる。プロダクトや機能フォルダという階層も、親が子にリンクし子が親へ戻るという決まりもない。同じ節は「No source reviewed presents a single hierarchy from the project README down to code comments」と書く。
- **上の階層の README が更新候補に挙がらない。** `scripts/find_related.py` は、変更されたファイルと同じフォルダの文書だけを P1 候補にする（`find_related.py:98-101`）。`src/features/foo/api/handler.ts` を変えても `src/features/foo/README.md` は P1 候補にならず、README の本文がそのファイル名を書いているときに P2（言及）として挙がるだけである。
- **木の形を検査しない。** `scripts/check_links.py` は、ローカルのリンク先があるかと見出しへのリンク（#fragment）を検査するだけである。ある階層に README があるか、ルートからたどり着けるか、子が親へ戻るリンクを持つかは検査しない。
- **階層を宣言する場所がない。** `.living-documentation.json` のキーは `enforcement`、`exclude_globs`、7種類の `*_globs`（ファイルの分類）、`related`（`max_candidates`、`min_name_length`）だけで、階層を表すキーはない。
- **既存リポジトリにまとめて作れない。** `SKILL.md` は「Create at most three new files per change and propose the rest in the report」とし、木を作る手順を持たない。
- 利用者のプロジェクトで、文書とコードの食い違いがどれだけ起きたかのデータはない。

## ギャップ

理想では、宣言した段のすべてに README があって親子のリンクでつながり、それが欠ければ検査がエラーにし、既存のリポジトリにも一度に作れる。実際には、sync-docs を当てたリポジトリでも README の無い段や親子のつながっていない README が何の報告もなく残り、機能フォルダの中を変えてもその機能フォルダの README は更新候補に挙がらず、既存のリポジトリに一度に作ることもできない。

## 重要性

- `harness/` の sync-docs は `install.sh` で `~/.claude/` に入り、利用者のすべてのプロジェクトで使われる。利用者は複数の構成のリポジトリを持ち、TypeScript・React・Python・AWS CDK・Terraform（Google Cloud）を使う。
- この問題で機械的に見つけられるようになるのは、README の欠けと親子のリンクの欠けという構造の欠けだけである。README の本文とコードの食い違いは見つけられない（含めないもの）。
- 木があると人と AI が正しい README にたどり着きやすくなり、利用者の懸念（文書とコードの食い違いをもとに AI が答えること）が減る、というのは検証していない仮説である。README の欠けやリンクの切れで実際に困った事例のデータはない。
- 機能フォルダの README のひな形（目的・扱わないこと・設計の理由・守るべき条件・最初に読むファイル）は、木の中の置き場所が決まって初めて使える。

## Identified solution (not part of the problem statement)

会話の中で提案したもの（2026-11-12〜13）。

- リポジトリ・プロダクト・機能フォルダの3階層の README のひな形を `templates/` に加える。
- `find_related.py` が、変更されたファイルより上の階層の README も候補に挙げるようにする。
- `practices.md` に階層と親子のリンクの決まりを書く。
- 木の形を検査するスクリプトを加える。

## 合意済みの決定（利用者の回答、2026-11-14）

- **まとめて作る機能を含める。** 人がはっきり頼んだときだけ、すべての階層の README の骨組みを一度に作る。中身は確かめられる事実だけにし、分からない所は「未記入」とはっきり書く。その後の変更では木を保つだけにする。
- **階層は設定で宣言する。** プロジェクトごとの `.living-documentation.json` に、階層ごとのパターン（例 `products/*`、`src/features/*`）を書く。宣言がないときは、`package.json` の workspaces や `pyproject.toml` などから候補を示すだけで、木の検査はしない。
- **構造の欠けはエラーにする。** 宣言した階層に README がないこと、親子のリンクが欠けていることは検査の失敗とし、sync-docs の完了条件に入れる。中身のずれは、今までどおり報告にとどめる。
- **複数のリポジトリで1つのサービスを作る場合は含めない。** 1つのリポジトリの中の階層に絞る。
- 利用者は、この問題文の案（2026-11-14 に会話で示したもの）について、上の4点に答えた。異論はなかった。
