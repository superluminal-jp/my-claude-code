# Phase 1 データモデル: `problem-definition` スキル

**機能**: 038-problem-definition-skill | **日付**: 2026-09-05 | **計画**: [plan.md](./plan.md)

本機能には実行時のデータストアは存在しない。「モデル」とは、本リポジトリが保持する設定エンティティ（スキル自体）と、本スキルが対象の文脈に生成する成果物（問題文）の構造、およびそれらに課される不変条件である。

---

## エンティティ: スキル（`problem-definition`）

| フィールド | 出所 | `problem-definition` での値 |
|---|---|---|
| `name` | `SKILL.md` フロントマター | `problem-definition` |
| `description` | `SKILL.md` フロントマター | トリガー条件と除外境界を1文で記述（FR-002、SKILL-03） |
| `when_to_use` | `SKILL.md` フロントマター | **存在しない**（SKILL-02） |
| `allowed-tools` | `SKILL.md` フロントマター | **存在しない**——追加のツール権限を要求しない |
| 本文 | `SKILL.md` | 4件の引用を含む本文。`references/` サブディレクトリなし |

**検証ルール**

- V1. `name` は格納ディレクトリ名（`.claude/skills/problem-definition/`）と一致しなければならない。
- V2. `description` は、トリガー語句と除外境界の両方を含まなければならない（FR-002、SKILL-03）。
- V3. 本文は `product-strategy`・`clarifier`・`adr` 等の他スキル名をそのまま埋め込んではならない（FR-016）。
- V4. 本文中のすべての引用は、[参考文献](./spec.md#参考文献) に列挙された4件のいずれかに紐づかなければならない（FR-003）。
- V5. 本文は原因分析・対応策の検討・実行計画の策定を行う手順を含んではならない（FR-005）。
- V6. 本文は自分自身の配置パス（`.claude/skills/problem-definition/`）をハードコードしてはならない（FR-017）。
- V7. 本文は `product-strategy` を含むいかなる他スキルの内容も参照・依存してはならない（FR-006）。

## エンティティ: 問題文（Problem Statement）

| フィールド | 必須/任意 | 説明 |
|---|---|---|
| ステータスマーカー | 必須 | `完成` または `ドラフト（未完成）`。後者は FR-009a に基づき、引き出しセッションが中断された場合に付与される |
| 未回答要素一覧 | ステータスが「ドラフト（未完成）」のときのみ必須 | 未回答の要素名を明示するリスト（FR-009a） |
| 現状 | 完成した問題文では必須 | BABOK/A3 に基づく、事実・データに根ざした記述（FR-007、FR-008） |
| あるべき姿 | 完成した問題文では必須 | Ishikawa/QC・BABOK・A3 に基づく、期待値・標準の記述（FR-007、FR-008） |
| ギャップ（問題文の核） | 完成した問題文では必須 | Kepner-Tregoe/A3 に基づく、現状とあるべき姿の対比としての問題の定式化（FR-007） |
| 重要性 | 完成した問題文では必須 | なぜ今取り組む必要があるかの記述（FR-007） |
| 識別された解決策の混入 | 該当があれば必須 | ユーザーが問題として提示したが実際には解決策である内容を、問題文から切り分けて記録（FR-010） |
| 識別された未検証の原因 | 該当があれば必須 | ユーザーが問題として提示したが実際には未検証の原因仮説である内容を、問題文から切り分けて記録（FR-011） |
| 対立するあるべき姿 | 該当があれば必須 | 関係者間で「あるべき姿」の見解が割れている場合、両論を併記（FR-012） |

**検証ルール**

- V8. `完成` ステータスの問題文は、上表の4必須要素（現状〜重要性）をすべて含まなければならない（FR-007、SC-003）。
- V9. `ドラフト（未完成）` ステータスの問題文は、必須要素の充足を問われない代わりに、未回答要素一覧を必ず含まなければならない（FR-009a、SC-003 の除外規定）。
- V10. いずれの値も、対象の文脈内に根拠が存在しない場合は前提として明示されなければならず、事実として断定してはならない（FR-009）。
- V11. 現状とあるべき姿の間に実質的な差が無いと判明した場合、問題文を生成せず、その旨を率直に伝えなければならない（FR-014）。
- V12. 複数の異なるギャップが1つの訴えに束ねられている場合、単一の問題文に統合せず、分解して別々の問題文候補として提示しなければならない（FR-013）。

**状態遷移**

問題文には2つの独立した状態軸がある:

1. **完成度**: `引き出し中` → `完成` または `引き出し中` → `ドラフト（未完成）`（中断時、FR-009a）。`ドラフト（未完成）` から `完成` への自動遷移はない——前提条件が明示するとおり、スキルは部分的な問題文を読み込んでセッションを再開することはしない。
2. **版数**: 同一の出力先に既存の問題文が見つかった場合、`上書き確認待ち` という一時状態を経て、ユーザーの回答に応じて `上書き` または `新バージョン作成` のいずれかに解決する（FR-015a）。サイレントな自動遷移は存在しない。

## エンティティ: 混入した非問題入力

ユーザーが問題として持ち込むが、実際には問題（ギャップ）そのものではない入力。識別し、問題文の本体から切り分けて別途記録する。

| 種別 | 識別方法 | 扱い |
|---|---|---|
| 解決策の混入 | 「〇〇すべきだ」のような処方的な文言（FR-010） | 解決策として明示し、その解決策が解消しようとしている現状とあるべき姿のギャップを別途引き出す |
| 未検証の原因 | 「原因は××のはずだ」のような、検証されていない因果の断定（FR-011） | 検証されていない仮説として明示し、原因分析へ進む前にギャップの記述そのものへ引き出しを戻す |

**検証ルール**

- V13. 解決策の混入・未検証の原因のいずれも、問題文の「ギャップ」フィールドへそのまま記載してはならない（FR-010、FR-011）。
