# Phase 1 クイックスタート: `problem-definition` スキルの検証

**機能**: 038-problem-definition-skill | **日付**: 2026-09-05 | **計画**: [plan.md](./plan.md)

実装（Phase 2 以降）が完了したことをエンドツーエンドで確認するための、実行可能な検証シナリオ。各シナリオの期待結果・満たすべき契約は [data-model.md](./data-model.md) と [contracts/problem-interface.md](./contracts/problem-interface.md) を参照し、ここでは重複させない。

## 前提条件

- Claude Code CLI がローカルで利用可能であること（`claude` コマンド）。
- 本リポジトリ（`my-claude-code`）がユーザースコープにインストール済み、または本リポジトリ内で直接検証する場合は `.claude/skills/problem-definition/SKILL.md` が存在すること。

## シナリオ1: 構造契約（オフライン、最速）

```bash
bash tests/run-config-pyramid.sh
```

**期待結果**: `problem-definition` を対象に含む `SKILL-01`〜`SKILL-06` と新規 `ROUTE` アサーションを含む、すべてのアサーションが `PASS` する。

## シナリオ2: 曖昧な訴えから問題文を生成する（ユーザーストーリー1）

**実行**: スキル名を出さずに次のように依頼する:

> 「なんとなくこのチームの動きがうまくいっていない気がする」

**期待結果**（spec.md 受け入れシナリオ1参照）:
- `problem-definition` スキルがロードされる。
- 現状・あるべき姿がそれぞれ引き出され、両者の対比としてギャップが明示される。
- 完了後、`## ステータス: 完成` のマーカーを持つ単一ファイルが生成され、契約Bの4必須要素をすべて含む。
- 途中で意図的に中断した場合、`ドラフト（未完成）` マーカーと未回答要素一覧を持つファイルが残ることを別途確認する（FR-009a）。
- 実行前後で対象の文脈内の他のファイルが一切変更されていないことを確認する（FR-015）。

## シナリオ3: 解決策・未検証の原因の混入を切り分ける（ユーザーストーリー2）

**実行**: 次のように依頼する:

> 「〇〇という機能を追加すべきだ、それが問題だ」

**期待結果**（spec.md 受け入れシナリオ2参照）:
- スキルはこれを解決策として識別し、問題文の「ギャップ」フィールドにそのまま記載しない。
- その解決策が解消しようとしている現状とあるべき姿のギャップを別途尋ねる。
- 契約Bの「識別された解決策」セクションが生成され、問題文本体とは分離される。

同様に、「原因は××のはずだ」という未検証の原因を持ち込んだ場合も、原因分析へ進まずギャップの記述に引き出しを戻すことを確認する。

## シナリオ4: 再実行時の上書き確認

**セットアップ**: シナリオ2で生成した問題文ファイルが既に存在する状態で、同じ対象について再度依頼する。

**期待結果**: スキルは既存ファイルの存在を検知し、上書きするか新しいバージョンを保存するかをユーザーに確認する（FR-015a）。サイレントにどちらかを選ばない。

## シナリオ5: ルーティング境界（隣接スキルとの非混同）

**実行**:

1. 「新規プロダクトの戦略を整理したい」 → `product-strategy` がロードされ、`problem-definition` はロードされないことを確認する（両スキルは意図的に独立であり、`problem-definition` が `product-strategy` の対象領域を奪わないことを検証する）。
2. 「この1機能の受け入れ基準を明確にしたい」（対象機能が既に合意済みである文脈で） → `clarifier` がロードされることを確認する。

**期待結果**: SC-002（既存のルーティング判断への回帰ゼロ）が壊れていないことを、この2件で代表的に確認する。
