# Feature Specification: 判定の結果と証拠を、1画面のレビューカードに表示する(引き継ぎ書 Phase 4)

**Feature Branch**: `feat/review-card`(`feat/change-assurance` から分岐)

**Created**: 2026-11-06

**Status**: Draft

**Input**: User description: "Phase 2 から先も順に実装"(2026-11-06)

**要旨**: `change-assurance` スキルの検査器に `card` の動き方を加え、問題カード、要求グラフ、検証の記録(と任意の反証の記録)から、人がレビューで最初に読む1画面の **レビューカード**(Markdown)を出す。カードの合否の表示は、Phase 3 の保証の判定をそのまま使い、カード自身は合否を決めない。必須の検査が1つでも合格でなければ、合格の印を出さない。未実行の検査と未解消の事項を隠さず、要求から検査と証拠の参照先までたどれるようにする。入力の文はすべて信頼できない文として、Markdown と Mermaid の中で無害にする。カードが人の判断の時間を減らすかは、ここでは測らない(Phase 5)。

## 用語

spec 059〜061 の用語(問題カード、要求グラフ、受け入れ条件、水準、反証の記録、検証の記録、保証の判定)は、そのまま使う。

- **レビューカード**: 1つの変更について、人が受け入れるか差し戻すかを決めるために最初に読む Markdown の文書。判定、問題、変更とリスク、水準ごとの合否、未解消の事項、人が決めること、要求の図、証拠の一覧を、この順に持つ。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 合否を判定のとおりに表示し、未実行と未解消を隠さない (Priority: P1)

**Acceptance Scenarios**:

1. **P4-02** **Given** L1 はすべて `passed`、親の L2 が `failed` の検証の記録、**When** カードを作る、**Then** 判定の欄は `fail` で合格の印がなく、水準の表で L1 の合格と L2 の不合格が別の行に出る。
2. **P4-03** **Given** 認可の負例の検査が `not_run` の検証の記録、**Then** カードは `not_run` の検査をその ID とともに示し、判定は `blocked` である。
3. **P4-04** **Given** リスクの理由の文に「すべての検査に合格した」と書かれているが、検査の1つが `failed` の検証の記録、**Then** カードの判定は `fail` である(文ではなく記録の状態に従う)。
4. **Given** `open` の指摘を持つ反証の記録、**Then** カードの未解消の事項にその指摘が出る。
5. **Given** すべて合格の記録、**Then** 判定の欄に合格の印が出る。

### User Story 2 - 要求から検査と証拠までたどれ、入力の文で表示が壊れない (Priority: P1)

**Acceptance Scenarios**:

1. **P4-05** **Given** 共有子を持つ4階層の要求グラフ、**Then** 図の中で各要求は1回だけ定義され、4階層目の要求は図の下の一覧に出る。すべての要求の ID がカードに現れる。
2. **P4-06** **Given** 証拠の参照先が URL の検査、**Then** 証拠の一覧で、要求の ID、検査の ID、水準、状態、参照先のリンクが同じ行に出る。
3. **Given** 要求の文に `|`、`<script>`、改行、引用符を含む入力、**Then** 表の列が崩れず、HTML のタグが文字として表示され、Mermaid のノードの文が閉じない。
4. **Given** 参照先が `javascript:` で始まる証拠、**Then** リンクにならない。
5. **Given** `--lang ja`、**Then** 見出しが日本語になる。

## Requirements *(mandatory)*

- **FR-001**: `assure.py card --problem CARD --graph GRAPH --manifest MANIFEST [--report REPORT] [--lang en|ja]` は、レビューカードを標準出力に書く。終了コードは判定と同じ(`pass` で 0、`fail` と `blocked` で 1、入力を解釈できなければ 2)とする。
- **FR-002**: カードの判定、水準ごとの件数、理由は、保証の判定(spec 061 の `gate`)の結果をそのまま使う。
- **FR-003**: カードは D5 の規則で入力の文を無害にする。
- **FR-004**: `SKILL.md` の手順の最後に、カードを作って人に示す手順を加える。`references/manifest.md` にカードの節を加える。

## Success Criteria *(mandatory)*

- **SC-001**: User Story 1・2 の各シナリオを、実装の前に失敗するテストで確かめる。
- **SC-002**: 既存の検査がすべて通る。

## Out of Scope

カードによるレビュー時間や判断の正確さの測定(Phase 5)、専用のビューア、GitHub の PR への自動の書き込み。
