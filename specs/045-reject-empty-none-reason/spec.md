# Feature Specification: 空の「不要」理由を弾く(スライス S3)

**Feature Branch**: `045-reject-empty-none-reason`

**Created**: 2026-10-17

**Status**: Draft

**Input**: User description: "specs/043-related-doc-discovery/meta-spec.md のスライス S3「空の『不要』理由を弾く」。`Documentation impact: none —` が理由なしで通る穴を塞ぐ。Stop ゲートが、理由が空または定型句だけの不要宣言を無効な報告とみなし、具体的な理由は受け付ける。実装系の変更があり文書の変更がゼロの場合は、`Updated:` 行か理由付きの `No change needed:` 行を必須にする。"

**Authority**: 範囲と契約 C2(報告の文法)は [meta-spec.md](../043-related-doc-discovery/meta-spec.md) に従う。S1([044](../044-unaddressed-readme-detection/spec.md))の「未処分の候補」の検査とは独立で、併用される。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 理由のない「不要」を通さない (Priority: P1)

スキルを導入したプロジェクトの利用者(開発者、および支援するエージェント)として、完了報告の `Documentation impact: none` に、空または定型句だけの理由しか付いていないときは、終了時に止めてほしい。具体的な理由が付いているときは通してほしい。

**Why this priority**: 「文書への影響なし」は最も楽に書ける逃げ道で、現在は理由が空でも通る。ここを塞がないと、更新の確認がすべて形骸化する。

**Independent Test**: 実装系の変更のある一時リポジトリで、最終メッセージだけを変えて終了処理を行う。`Documentation impact: none —`(理由なし)や `Documentation impact: none — n/a` は止まり、`Documentation impact: none — 内部の変数名のみの変更で、公開される挙動は不変` は通る。

**Acceptance Scenarios**:

1. **Given** 実装系の変更があり、最終メッセージが `Documentation impact: none —`(理由なし)、**When** 終了処理が走る、**Then** 理由が必要なことを伝えて止まる。
2. **Given** 理由が `n/a`、`none`、`no impact`、`nothing`、`なし`、`なし。`、`-`、記号のみ、またはテンプレートのまま `<reason>` のいずれか、**When** 終了処理が走る、**Then** 同様に止まる(大文字・小文字、全角・半角、末尾の句読点の違いは区別しない)。
3. **Given** 理由が具体的(上記の定型句ではない説明)、**When** 終了処理が走る、**Then** この検査では問題にしない。
4. **Given** 強制の度合いが「警告のみ」または「無効」、**When** 無効な不要宣言がある、**Then** 警告のみを表示するか、何も行わない。

### User Story 2 - 文書を変えていないなら、変えない理由を言わせる (Priority: P2)

利用者として、実装系の変更があるのに文書がまったく変更されていないとき、完了報告に「何を更新したか」または「なぜ変更不要か」が具体的に書かれていなければ、止めてほしい。

**Why this priority**: 見出しの `Documentation impact` だけを書いて中身が空の報告も、同じ逃げ道になる。ただし P1 より範囲が広く、既存の報告の書式への影響も大きいため、次に扱う。

**Independent Test**: 実装系の変更だけがある一時リポジトリで、`Documentation impact` の見出しのみ、あるいは `Checks:` 行のみの報告は止まり、`Updated: …` 行または理由付きの `No change needed: …` 行を含む報告は通る。

**Acceptance Scenarios**:

1. **Given** 実装系の変更があり文書は未変更、最終メッセージが見出し `Documentation impact` のみ、**When** 終了処理が走る、**Then** 更新内容または変更不要の理由が必要なことを伝えて止まる。
2. **Given** 同じ状況で、`Updated: <path> — <内容>` の行がある、**When** 終了処理が走る、**Then** 通る。
3. **Given** 同じ状況で、`No change needed: <対象> — <具体的な理由>` の行がある、**When** 終了処理が走る、**Then** 通る。
4. **Given** 同じ状況で、`No change needed: <対象> — n/a`(定型句の理由)、**When** 終了処理が走る、**Then** 止まる。
5. **Given** 実装系の変更があり、文書も変更されている、**When** 見出しのみの報告で終了処理が走る、**Then** この検査では問題にしない(現在と同じ)。
6. **Given** 複数行の報告書式(`Updated` / `No change needed` / `Unresolved` / `Proposed decision record` / `Checks`)、**When** 具体的な内容で書かれている、**Then** 現在と同じく通る。

---

### Edge Cases

- 先頭に箇条書きの記号(`-`、`*`)や強調記号が付いた行、行頭の空白、全角コロン、ダッシュの種類(`—`、`–`、`-`、`:`)の違いがあっても、同じ行として解釈する。
- 不要宣言が複数行あり、1 つでも無効なら、報告は無効とする。
- 区切り(ダッシュやコロン)が無い `Documentation impact: none` は、理由が空として扱う。
- 理由が日本語でも英語でも、定型句の判定は同じ規則で行う。具体的な理由の文字数に下限は設けない(短くても定型句でなければ有効)。
- `No change needed:` の行に区切りが無い場合は、行全体を理由として判定する(定型句でなければ有効)。
- 最終メッセージが取得できない場合は、この検査をしない(既存の方針)。
- 実装系の変更が無い(文書だけの変更など)場合は、報告自体が要求されないため、この検査をしない(現在と同じ)。
- ゲートは、同じ作業状態に対して既存の上限回数までしか止めず、ゲート自身の差し戻し直後の再入では止めない。S1 の「未処分の候補」の問題と同時に発生した場合は、問題を並べて 1 回のブロックで伝える。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Stop ゲートは、`Documentation impact: none` 形式の行(区切りの種類、行頭の記号、大文字小文字を問わない)の理由が、空、または定型句のみ、または記号のみ、または未記入のテンプレート(`<reason>` など)であるとき、その報告を無効として問題にしなければならない。
- **FR-002**: 定型句の判定は、前後の空白、末尾の句読点、全角・半角、大文字小文字を正規化したうえで、固定の一覧と照合して行わなければならない。一覧には少なくとも `n/a`、`na`、`none`、`nil`、`no`、`nothing`、`no impact`、`no change`、`no changes`、`not applicable`、`なし`、`無し`、`該当なし`、`変更なし`、`影響なし`、`-` を含める。
- **FR-003**: 具体的な理由(定型句ではない説明)は、長さにかかわらず有効としなければならない。
- **FR-004**: 完了報告が必要な変更(既存の判定: 実装、仕様、設定、インフラ、決定の各分類のいずれかが変更されたとき)があり、かつ文書の変更が 1 つも無い場合、ゲートは、最終メッセージに次のいずれかが無ければ問題にしなければならない: `Updated:` 行(内容が空でない)、定型句でない理由を持つ `No change needed:` 行、または有効な `Documentation impact: none — <理由>` 行。
- **FR-005**: 文書の変更がある場合は、FR-004 の検査をしてはならない(FR-001 の無効な不要宣言の検査は、文書の変更の有無にかかわらず行う)。
- **FR-006**: 問題の文面は、何が不足しているか(理由が空・定型句、更新内容または変更不要の理由の欠落)と、どう直すか(具体的な理由、または `Updated:` / `No change needed:` 行を書く)を伝えなければならない。
- **FR-007**: 既存の挙動をすべて維持しなければならない。強制の度合い(block / warn / off)、同じ作業状態に対する最大 2 回のブロック、再入でブロックしないこと、内部エラー時の通過、変更が無い場合の無動作、S1 の「未処分の候補」の検査。
- **FR-008**: 既存の単体テスト 90 件は、変更後もすべて通らなければならない。新しい挙動には、実装より先に書かれた(失敗することを確認した)テストがなければならない。
- **FR-009**: このスライスは、`related.*` の設定キー、候補数の上限、文書の作成規則、`SKILL.md` の処分に関する文言(ゲートの文面が必要とする範囲を超えるもの)、README・eval の更新を含まない。

### Key Entities

- **不要宣言(None declaration)**: 最終メッセージ中の `Documentation impact: none` 形式の行。理由を持つ。
- **理由(Reason)**: 不要宣言や `No change needed:` 行の、区切りより後ろの説明。有効か無効(空・定型句・記号のみ・未記入のテンプレート)かを持つ。
- **有効な報告(Valid report)**: 見出しがあり、無効な不要宣言を含まず、必要な場合は更新内容または変更不要の理由を含む最終メッセージ。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: FR-002 に挙げた定型句、空、記号のみ、`<reason>` のすべてが、不要宣言で 100% 無効と判定され、具体的な理由の見本は 100% 有効と判定される(表形式のテストで確認)。
- **SC-002**: 実装系の変更があり文書が未変更のとき、見出しのみの報告は止まり、`Updated:` 行、理由付きの `No change needed:` 行、有効な不要宣言のいずれかがあれば通る(テストで確認)。
- **SC-003**: 既存の単体テスト 90 件がすべて通り、追加したテストにより合計が増える。
- **SC-004**: 無効な報告に対するブロックは、同じ作業状態につき既存の上限回数を超えない(テストで確認)。
- **SC-005**: 問題の文面から、利用者が 1 回の読みで、何を書けばよいかを特定できる(文面に直し方が含まれていることをテストで確認)。

## Assumptions

- 「実装系の変更」は、既存の「完了報告が必要な変更」の分類(実装、仕様、設定、インフラ、決定)と同じ範囲とする。二つ目の一覧を作らず、判定を一貫させるため。
- 有効な `Documentation impact: none — <理由>` 行は、FR-004 の「変更不要の理由」の 1 つの書き方として認める。既存の単一行の書式を壊さないため。
- 定型句の一覧は固定とし、設定で拡張できない(設定キーは範囲外)。足りない定型句は、運用で見つかり次第、一覧に追加する。
- 日本語の定型句は、上記の一覧のほか、否定語だけの短い語を対象とする。理由の意味の妥当性(具体的に見えて実は無意味な文章)は機械的に判定できず、検査の対象外とする。限界として README に記載する(S6)。
- 正規化は、Unicode の互換正規化(全角・半角)と大文字小文字の畳み込みで足りるとする。
- 報告の書式の変更(`Created:` 行など)は S4 の範囲で、本スライスは既存の行の名前(`Updated:`、`No change needed:`、`Documentation impact: none`)だけを扱う。
