# Feature Specification: 未処分の兄弟 README の検出(スライス S1)

**Feature Branch**: `044-unaddressed-readme-detection`

**Created**: 2026-10-17

**Status**: Draft

**Input**: User description: "specs/043-related-doc-discovery/meta-spec.md のスライス S1「未処分の兄弟 README を検出する(ウォーキングスケルトン)」。maintaining-living-documentation スキルに、変更に対する近接文書の候補を読み取り専用で列挙する仕組みと、その候補が更新も言及もされないまま作業が終わろうとしたときに止める仕組みを、最小の端から端までの経路として加える。"

**Authority**: このスライスの範囲、契約 C1・C2、分岐 B2・B3 は [meta-spec.md](../043-related-doc-discovery/meta-spec.md) に従う。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 隣の README を更新し忘れたまま終わらせない (Priority: P1)

スキルを導入したプロジェクトの利用者(開発者、および開発を支援するエージェント)が、あるディレクトリのコードを変更したとき、同じディレクトリにある README や Markdown 文書が更新も言及もされないまま作業が終わることを、終了時に検出して止めてほしい。

**Why this priority**: 近接文書の更新漏れが、生きた文書を保つうえで最も頻繁で、しかも検出されにくい穴だから。以降のスライスは、この経路を広げたり補強したりするだけで、最小の価値はここで成立する。

**Independent Test**: 一時的な Git リポジトリを作り、`src/x.py` を変更し、隣の `src/README.md` を触らず言及もしない状態で終了処理を行うと止まり、README を更新するか、最終メッセージでそのパスを挙げると通る。他のスライスに依存せず検証できる。

**Acceptance Scenarios**:

1. **Given** `src/x.py` が変更され、`src/README.md` が未変更で最終メッセージにも現れない、**When** 作業の終了処理が走る、**Then** 未処分の候補として `src/README.md` が報告され、終了が(既存の挙動どおり)制限付きで止められる。
2. **Given** 同じ状況で `src/README.md` も更新されている、**When** 終了処理が走る、**Then** 候補に関する問題は報告されない。
3. **Given** 同じ状況で `src/README.md` は未変更だが、最終メッセージにそのパスが理由付きで書かれている、**When** 終了処理が走る、**Then** 候補に関する問題は報告されない。
4. **Given** 設定または環境で強制の度合いが「警告のみ」または「無効」になっている、**When** 未処分の候補がある、**Then** 警告のみを表示するか、何も行わない(既存の仕組みと同じ)。

---

### User Story 2 - 候補を機械可読な形で確認する (Priority: P2)

利用者(および手順を実行するエージェント)が、現在の変更に対する近接文書の候補を、判断を始める前に一覧として確認したい。

**Why this priority**: 候補の発見を決定的にし、エージェントが「どこを見るべきか」を推測に頼らず判断できるようにする。ゲートの前提でもあるが、単独でも手順上の価値がある。

**Independent Test**: 変更のある Git リポジトリでコマンドを実行し、変更ファイルの一覧と候補(元の変更ファイル、候補のパス、種別、近接度、理由)を含む機械可読な出力を得る。何も書き換えられない。

**Acceptance Scenarios**:

1. **Given** `src/x.py` が変更され、`src/README.md` と `src/design.md` が存在し未変更、**When** 候補の一覧を求める、**Then** 両方が「同じディレクトリ」の候補として、元のファイルと理由付きで出力される。
2. **Given** 候補になり得る文書が変更済みである、**When** 一覧を求める、**Then** その文書は候補に含まれない。
3. **Given** 比較の基点(ブランチ)が指定された、**When** 一覧を求める、**Then** 基点からの変更を含めて候補を求める。
4. **Given** Git リポジトリではない場所、**When** 一覧を求める、**Then** 原因と代替手段を示す明確なエラーで終わり、何も書き換えない。

---

### User Story 3 - 手順書に新しい確認手順が載っている (Priority: P3)

スキルの手順書(SKILL.md)を読んだエージェントが、変更の影響を評価する段階で、候補の一覧を求める手順と、候補の処分の最小限の約束(更新する、または最終メッセージで理由とともにパスを挙げる)を知っている。

**Why this priority**: 機械が検出しても、エージェントがその扱いを知らなければ、止められてから初めて知ることになる。ただし、挙動の核は P1 と P2 にある。

**Independent Test**: SKILL.md の影響評価の手順に、候補の一覧を求めるコマンドと、処分の最小限の約束が含まれ、SKILL.md は 500 行未満のまま、既存の定義検査が通る。

**Acceptance Scenarios**:

1. **Given** 更新後の SKILL.md、**When** 影響評価の手順を読む、**Then** 候補の一覧を求めるコマンドと、候補の処分の最小限の約束が書かれている。
2. **Given** 更新後の SKILL.md と rule、**When** 既存の定義検査を実行する、**Then** すべて通る。

---

### Edge Cases

- 変更ファイルが文書自身(Markdown など)である場合は、候補の元にしない(文書の変更が別の文書の候補を生まない)。
- 変更ファイルがルート直下にある場合は、ルート直下の README 系文書が同じディレクトリの候補になる。
- 同じ文書が複数の変更ファイルの候補になる場合は、契約 C1 の形を保つため、元の変更ファイルごとに別のレコードとして出力する。ゲートは文書のパス単位で 1 つの問題として扱い、元の変更ファイルをすべて示す。
- 除外設定の対象のパス、およびバージョン管理から外れたパスは、候補にしない。
- 候補の文書が削除された場合や、名前だけが変わった場合は、その変更自体を「処分済み」とみなす(変更集合に含まれる)。
- 変更前から存在した未コミットの変更は、既存の基準(セッション開始時・ターン開始時)に従い、このゲートの対象にしない。
- 最終メッセージが取得できない場合は、候補に関する問題を報告しない(既存の報告必須の判定と同じ方針)。
- ゲートは、同じ作業状態に対して既存の上限回数までしか止めず、ゲート自身の差し戻し直後の再入では止めない。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: スキルは、Git の作業ツリー(任意で比較の基点を指定)について、変更されたファイルのうち文書ではないものそれぞれに対し、同じディレクトリにある README 系文書と Markdown 文書を近接候補として列挙する読み取り専用のコマンドを提供しなければならない。
- **FR-002**: 候補の出力は、契約 C1 の形でなければならない。すなわち、変更されたパスの一覧、候補の配列(各候補は元の変更ファイル、候補のパス、種別、近接度、理由)、切り捨て件数を含む。このスライスの種別は「同じディレクトリ」、近接度は P1 のみである。
- **FR-003**: 候補から、すでに変更された文書、除外設定の対象のパス、および変更ファイル自身を除かなければならない。
- **FR-004**: コマンドは、プロジェクトのファイルを書き換えず、ネットワークに接続せず、読み取り専用の Git 操作のみを行わなければならない。Git リポジトリでない場合は、原因と代替手段を示すエラーで終了しなければならない。
- **FR-005**: 作業の終了処理(Stop ゲート)は、P1 の候補が、作業ツリーで変更されておらず、かつ最終メッセージにパスが現れない場合、その候補を問題として報告しなければならない。契約 C2 の「処分済み」の定義に従う。
- **FR-006**: ゲートは、既存の挙動をすべて維持しなければならない。すなわち、強制の度合い(block / warn / off)、同じ作業状態に対する最大 2 回のブロック、ゲート自身の差し戻し直後の再入でブロックしないこと、ゲート内部のエラーでは通過すること、変更が無い場合やセッション開始前からの変更では動作しないこと。
- **FR-007**: 候補に関する問題は、既存の問題(リンク切れ、完了報告の欠落)と同じ形式で、利用者に何を直すべきかが伝わる文面で報告されなければならない。
- **FR-008**: SKILL.md は、影響評価の手順に候補の一覧を求めるコマンドを加え、C2 に基づく処分の最小限の約束(更新する、または最終メッセージで理由とともにパスを挙げる)を示さなければならない。SKILL.md は 500 行未満を保たなければならない。
- **FR-009**: 既存の単体テスト 67 件は、変更後もすべて通らなければならない。新しい挙動には、実装より先に書かれた(失敗することを確認した)テストがなければならない。
- **FR-010**: このスライスは、P0・P2・変更履歴の候補、`related.*` の設定キー、候補数の上限、空の「不要」理由の拒否、文書の作成規則、README・eval の更新を含まない。

### Key Entities

- **候補(Candidate)**: ある変更ファイルに近接する、更新すべきか判断される文書。元の変更ファイル、候補のパス、種別、近接度、理由を持つ。
- **処分済み(Addressed)**: 候補が、作業ツリーで変更されている、または最終メッセージにパスが現れている状態。このスライスでは、この 2 つの条件のみで判定する。
- **変更集合(Changed set)**: 作業ツリー(基点の指定があれば基点からの差分を含む)で変更されたパスの集まり。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 隣の README が未変更・未言及のとき、ゲートは差し戻しの回数の上限内で必ず止まり、README の更新または言及があれば 100% 通る(テストで確認)。
- **SC-002**: 候補の出力は、同じ変更に対して常に同じ内容と順序になる(再現性、テストで確認)。
- **SC-003**: コマンドとゲートの実行後、作業ツリーの内容は実行前と一致する(書き換えが 0 件、テストで確認)。
- **SC-004**: 既存の単体テスト 67 件がすべて通り、追加したテストにより合計が増える。
- **SC-005**: SKILL.md の手順を読んだ利用者が、追加のコマンドとその扱いを、1 回の読みで見つけられる(手順書の影響評価の段落に収まっている)。

## Assumptions

- 近接度 P1 は「同じディレクトリ」を指す。親ディレクトリや子ディレクトリは対象外とする(meta-spec の定義による)。
- 「README 系文書」は、名前が README で始まる Markdown を指す。それ以外の Markdown 文書も、同じディレクトリにあれば候補とする。
- 「文書」の判定は、既存の分類(文書として分類されるパス)に従う。設定で上書きされた分類も尊重する。
- `common.py` の既存関数を変更せずに再利用できる(meta-spec の仮定 A3、確度 Medium)。偽の場合は、再計画として扱う。
- 「最終メッセージにパスが現れる」ことは、処分の十分な代理指標とは限らない(meta-spec の仮定 A2、確度 Medium)。形式的な言及でも通ることを、既知の限界として扱う。偽の場合は、C2 の再仕様として扱う。
- 実行環境は、既存のスキルと同じく Python 3.9 以上の標準ライブラリのみとする。
- 候補の列挙に上限は設けない(上限は S2 の範囲)。このリポジトリのように、1 ディレクトリの Markdown が少数の場合を前提にする。
- 文書の作成・更新そのものは、このスライスの範囲外で、エージェントの判断で行われる。
