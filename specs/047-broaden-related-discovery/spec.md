# Feature Specification: 近接候補の発見を広げる(スライス S2)

**Feature Branch**: `047-broaden-related-discovery`

**Created**: 2026-10-17

**Status**: Draft

**Input**: User description: "specs/043-related-doc-discovery/meta-spec.md のスライス S2。宣言なしに、名前参照(P2)、変更履歴、ファイル内コメント(P0、助言のみ)まで候補を拾い、`related.*` の設定キーと候補数の上限を加える。"

**Authority**: 範囲と契約 C1(拡張)・C3 は [meta-spec.md](../043-related-doc-discovery/meta-spec.md) に従う。S1([044](../044-unaddressed-readme-detection/spec.md))の候補の列挙とゲートを拡張する。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 離れた場所の文書も、変更したファイルを名指していれば候補になる (Priority: P1)

スキルを導入したプロジェクトの利用者(開発者、および支援するエージェント)が、あるファイルを変更したとき、別のディレクトリの文書(例: `docs/` の手順書)がそのファイルのパスまたは名前を本文で挙げていれば、更新の候補として列挙され、更新も言及もされないまま終わろうとすれば止められてほしい。

**Why this priority**: 同じディレクトリに文書がない変更が大多数で、宣言なしに「名指しされている文書」を拾えることが、この仕組みの価値の中心。

**Independent Test**: 一時リポジトリで `scripts/install.sh` を変更し、`docs/setup.md` が本文で `scripts/install.sh` を挙げているとき、候補一覧に `docs/setup.md` が名前参照(P2)として出る。ゲートは、更新も言及もなければ止め、更新または言及すれば通す。

**Acceptance Scenarios**:

1. **Given** 変更ファイルのパスを本文で挙げている未変更の文書、**When** 候補を求める、**Then** その文書が種別「名前参照」、近接度 P2、理由付きで出る。
2. **Given** 変更ファイルの名前(ファイル名)だけを挙げている文書で、名前が設定の最小長以上、**When** 候補を求める、**Then** 候補になる。最小長より短い名前は、パス全体の一致のときだけ候補になる。
3. **Given** 名前を含むが単語の一部にすぎない文面(例: `reinstall.sh`、`install.shx`)、**When** 候補を求める、**Then** 候補にならない。
4. **Given** 同じディレクトリにあり、名前も挙げている文書、**When** 候補を求める、**Then** 同じ組(元ファイルと文書)は 1 件(種別「同じディレクトリ」)のみで、重複しない。
5. **Given** 未処分の名前参照の候補、**When** ゲートが走る、**Then** S1 と同様に問題として報告され、更新または最終メッセージでのパスの言及で解消する。

---

### User Story 2 - 利用者に見える変更なら、変更履歴も候補になる (Priority: P2)

利用者として、プロジェクトが変更履歴(CHANGELOG など)を持っていて、利用者に見える変更(実装、仕様、設定、インフラ)をしたのに変更履歴が更新されていないとき、変更履歴を更新候補として列挙してほしい。持っていないプロジェクトには何も言わないでほしい。

**Why this priority**: 変更履歴の更新漏れは典型的な漏れだが、対象を持つプロジェクトに限られるため、P1 の次とする。

**Independent Test**: `CHANGELOG.md` のあるリポジトリで `src/x.py` を変更すると、`CHANGELOG.md` が「変更履歴」候補(近接度 P3)として出る。`CHANGELOG.md` も変更されれば出ない。変更履歴が無いリポジトリ、テストだけの変更、文書だけの変更では出ない。

**Acceptance Scenarios**:

1. **Given** 変更履歴ファイルがあり未変更、利用者に見える変更がある、**When** 候補を求める、**Then** 変更履歴が種別「変更履歴」、近接度 P3、理由付きで 1 件出る。
2. **Given** 変更履歴ファイルも変更されている、**When** 候補を求める、**Then** 変更履歴の候補は出ない。
3. **Given** 変更履歴ファイルが無い、または変更がテスト・文書のみ、**When** 候補を求める、**Then** 変更履歴の候補は出ない(変更履歴を新設するよう促さない)。

---

### User Story 3 - コメントは助言として示し、設定で調整できる (Priority: P3)

利用者として、変更した実装ファイル自身のコメントも更新の確認対象として一覧で見たい(ただし終了時に強制はしない)。また、候補の数の上限と、名前参照の最小長を設定で調整し、上限で切り捨てられた件数も知りたい。

**Why this priority**: コメントの確認は助言にとどまり、設定と上限は運用の調整であるため、価値の中心(P1・P2)の後でよい。

**Independent Test**: 実装ファイルを変更すると、そのファイル自身が種別「コメント」、近接度 P0 の助言として一覧に出るが、ゲートは問題にしない。`related.max_candidates` を小さくすると、近接度の高いものから残り、切り捨て件数が出力される。不正な設定値は明確なエラーで拒否される。

**Acceptance Scenarios**:

1. **Given** 変更された実装ファイル、**When** 候補を求める、**Then** そのファイル自身が P0(種別「コメント」、助言)として出る。設定・テスト・生成物・文書のみの変更では出ない。
2. **Given** P0 の候補だけが残っている、**When** ゲートが走る、**Then** 問題にしない。
3. **Given** `related.max_candidates` が候補の文書数より小さい、**When** 候補を求める、**Then** 近接度が高い順(P1、P2、P3)に、異なる文書で数えて上限まで残り、切り捨てた文書数が出力される。P0 は上限に数えない。
4. **Given** 切り捨てがあった、**When** ゲートが問題を報告する、**Then** 文面に、上限で省かれた件数が示される。
5. **Given** `related` に不正な値(数値でない、0 以下、真偽値、未知のキー、オブジェクトでない)、**When** 設定を読む、**Then** どのキーがなぜ不正かを示すエラーになる。

---

### Edge Cases

- 削除されたファイルの名前を本文で挙げている文書は、そのパスまたは名前の参照として候補になる(削除は文書の更新を要する変更)。
- 読み取れない文書(文字コードが不正、巨大なファイル)は、エラーにせず候補の探索から外す。
- 変更済みの文書、除外設定の対象、決定記録、変更履歴ファイルは、名前参照の対象にしない(変更履歴は専用の規則で扱う)。
- 元ファイルが複数あり同じ文書を挙げている場合、元ファイルごとに別のレコードになり、ゲートは文書のパス単位で 1 つの問題として扱う(S1 と同じ)。
- 変更履歴の候補は、文書ごとに 1 件で、元ファイルは利用者に見える変更の先頭の 1 件を示し、理由に件数を含む。
- 名前参照の判定は、単純な文字列の一致(大文字小文字を区別する、単語境界つき)とし、意味の解析はしない。
- 設定が無ければ既定値を使う。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 候補の列挙は、S1 の同じディレクトリの候補(P1)に加えて、次を返さなければならない: 名前参照(種別 `mention`、近接度 P2)、変更履歴(種別 `changelog`、近接度 P3)、ファイル内コメント(種別 `comment`、近接度 P0、助言)。契約 C1 の形(`source`、`path`、`kind`、`proximity`、`reason`、`changed`、`truncated`)を保つ。
- **FR-002**: 名前参照は、変更された文書でないファイル(削除を含む)のパス全体、または名前がその最小長以上であればファイル名を、未変更の文書の本文に単語境界つきで含む場合に成立しなければならない。同じ組が同じディレクトリの候補でもある場合は、種別「同じディレクトリ」の 1 件にする。
- **FR-003**: 名前参照の対象は、文書として判定される Markdown 系のファイルのうち、変更されておらず、除外設定の対象でなく、決定記録でも変更履歴でもないものでなければならない。読み取れない文書、1 MiB を超える文書は、エラーにせず対象から外さなければならない。
- **FR-004**: 変更履歴の候補は、プロジェクトに変更履歴のファイルがあり、そのファイルがどれも変更されておらず、利用者に見える変更(実装、仕様、設定、インフラの各分類)が 1 件以上あるときに限り、変更履歴のファイルごとに 1 件を返さなければならない。変更履歴が無いプロジェクトに、変更履歴を新設するよう促してはならない。
- **FR-005**: コメントの候補(P0)は、変更された実装ファイル(分類が実装のみのもの)自身を指し、助言とする。設定、テスト、生成物、文書のみの変更では返してはならない。
- **FR-006**: 設定ファイルは `related` オブジェクトを受け付け、`max_candidates`(1 以上の整数、既定 10)と `min_name_length`(1 以上の整数、既定 6)を持たなければならない。スキーマ(`schemas/config.schema.json`)がこれらの唯一の定義であり、不正な型・範囲外の値・未知の入れ子のキーは、キー名と理由を示すエラーで拒否されなければならない。
- **FR-007**: 候補の数は、`max_candidates` を上限に、近接度が高い順(P1、P2、P3)、次にパス順で、異なる文書の数で数えて残さなければならない。省かれた文書の数を `truncated` に返さなければならない。P0 は上限に数えない。
- **FR-008**: Stop ゲートは、P1・P2・P3 の候補(コメント以外)を S1 と同じ規則(変更されたか、最終メッセージにパスが現れれば処分済み)で強制し、P0(コメント)は問題にしてはならない。問題の文面は候補の種別(同じディレクトリ、名前参照、変更履歴)を示し、`truncated` が 0 より大きいときは省かれた件数を示さなければならない。S1・S3 の既存の挙動(強制の度合い、ブロック回数、再入、報告の質の検査)は変えない。
- **FR-009**: 設定値の検証を実現するために、`scripts/common.py` の検証処理を、整数(下限つき、真偽値を除く)と入れ子のオブジェクト(未知のキーを拒否)に対応させてよい。これは加算的な拡張に限り、既存の関数の契約と既存の挙動を変えてはならない。それ以外の `common.py` の変更が必要になった場合は、停止して報告しなければならない。
- **FR-010**: 既存の単体テスト 112 件は、変更後もすべて通らなければならない。ただし、S1 のテストが「P1 の候補だけ」を比較している補助(候補の組の取り出し)は、P0 の追加に合わせて、種別が `comment` でないものだけを対象にするよう更新してよい。新しい挙動には、実装より先に書かれた(失敗することを確認した)テストがなければならない。
- **FR-011**: このスライスは、`SKILL.md`・README の文言の更新(S4・S6)、文書の作成規則(S4)、eval(S6)、所有者・鮮度の機能を含まない。

### Key Entities

- **候補の種別(Kind)**: `sibling`(P1、S1)、`mention`(P2)、`changelog`(P3)、`comment`(P0、助言)。
- **名前参照(Mention)**: 変更ファイルのパスまたは名前を本文に含む文書。理由に一致した文字列を示す。
- **関連設定(related)**: `max_candidates` と `min_name_length`。
- **切り捨て件数(truncated)**: 上限により候補から省かれた異なる文書の数。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 変更ファイルのパスを挙げる未変更の文書は、探索の対象のうち 100% が名前参照として列挙される(テストで確認)。単語の一部に過ぎない一致は 0%(テストで確認)。
- **SC-002**: 変更履歴の候補は、変更履歴を持たないプロジェクト、変更履歴が更新済みのプロジェクト、テスト・文書のみの変更では 0 件(テストで確認)。
- **SC-003**: 上限の指定時、返る候補の異なる文書数は上限以下で、`truncated` と合わせて全体の文書数に一致する(テストで確認)。出力は再実行しても同一。
- **SC-004**: 不正な `related` の設定は、キー名と理由を示すエラーで 100% 拒否される(テストで確認)。
- **SC-005**: 既存の単体テスト 112 件(補助の更新を除く)がすべて通り、追加したテストにより合計が増える。

## Assumptions

- 名前参照の既定の最小長は 6 文字。短い名前は誤一致が多いため、パス全体の一致に限る(仮定 A1。実測は後続で行う。偽の場合は設定で調整でき、方針の見直しは再計画または再仕様)。
- 1 MiB を超える文書は読まない。実用上の文書の大半は下回る。
- 「利用者に見える変更」は、既存の分類の実装、仕様、設定、インフラのいずれかを含む変更とする。
- 変更履歴ファイルの判定は既存の `is_changelog` の判定(ファイル名の語幹)に従い、断片ディレクトリは扱わない。
- 検証処理の拡張(FR-009)は、メタスペックの仮定 A3 が偽になった場合の分岐 B3(再計画)にあたる。再計画の範囲は、加算的な拡張と回帰テストの追加に限る。
