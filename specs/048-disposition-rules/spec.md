# Feature Specification: 処分規則と作成条件を手順に入れる(スライス S4)

**Feature Branch**: `048-disposition-rules`

**Created**: 2026-10-17

**Status**: Draft

**Input**: User description: "specs/043-related-doc-discovery/meta-spec.md のスライス S4。SKILL.md と hooks/rule.md に、関連文書の処分(更新、不要の理由、作成、提案)の規則と作成条件を明文化し、完了報告に `Created:` 行を加える。"

**Authority**: 範囲と契約 C2(報告の文法)、C4(配置規則の所在)は [meta-spec.md](../043-related-doc-discovery/meta-spec.md) に従う。S1(候補の列挙とゲート)、S3(報告の質の検査)、S5(配置規則 [practices.md](../../.claude/skills/maintaining-living-documentation/references/practices.md))を前提とする。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 関連文書をどう扱えばよいかが手順に書かれている (Priority: P1)

スキルの手順を読むエージェントが、`find_related.py` が挙げた関連文書のそれぞれについて、更新する、変更不要の理由とともにパスを挙げる、のどちらかをすることを、手順から読み取れる。

**Why this priority**: S1・S2 のゲートが止める対象を、止められる前にエージェントが知っている状態にする。挙動の核。

**Independent Test**: `SKILL.md` に、関連文書の処分(更新、または最終メッセージでパスと理由を挙げる)の規則があり、`hooks/rule.md` にも同じ趣旨が短く書かれている。

**Acceptance Scenarios**:

1. **Given** 更新後の `SKILL.md`、**When** 手順を読む、**Then** 関連文書のそれぞれを更新するか、パスを挙げて変更不要の理由を述べる、という規則がある。
2. **Given** 更新後の `hooks/rule.md`、**When** 読む、**Then** 同じ規則が短く書かれ、セッション開始時にエージェントの文脈に入る。

---

### User Story 2 - 文書を作成してよい条件と、してはいけないことが明確である (Priority: P2)

エージェントが、関連文書が無いときに、新しい文書を作成するか、作成せずに提案するかを、手順から判断できる。作成は、新しい公開契約が増え、それを扱う文書が無いときに限り、配置は配置規則に従う。1 回の変更で作成するのは最大 3 ファイルとし、超える分は提案にする。決定記録は作成せず、変更履歴を持たないプロジェクトに変更履歴を新設しない。

**Why this priority**: 「無ければ作成」の過剰な適用(文書の増えすぎ)を防ぐ歯止め。P1 の後でよいが、同時に入れないと無制限の作成を誘発する。

**Independent Test**: `SKILL.md` に、作成の条件、配置規則への参照(`practices.md` の該当節)、上限(1 回の変更で最大 3 ファイル)、決定記録と変更履歴の禁止が書かれている。

**Acceptance Scenarios**:

1. **Given** 更新後の `SKILL.md`、**When** 作成の規則を読む、**Then** 新しい公開契約(コマンド、オプション、設定、API、モジュール)が増え、それを扱う文書が無いときに限り作成する、と書かれている。
2. **Given** 同じ規則、**When** 配置を読む、**Then** `references/practices.md` の「Layers, placement, and proximity」の節に従うことが、そのリンク(アンカー)つきで書かれている。
3. **Given** 同じ規則、**When** 上限を読む、**Then** 最大 3 ファイルで、超える分は報告で提案する、と書かれている。
4. **Given** 同じ規則、**When** 禁止を読む、**Then** 決定記録をユーザーの依頼なしに作成しない、変更履歴を持たないプロジェクトに新設しない、と書かれている。

---

### User Story 3 - 作成した文書を完了報告に記録できる (Priority: P3)

エージェントが、作成した文書を、完了報告の `Created:` 行(何を記録するために新しく作ったか)として報告できる。

**Why this priority**: 作成が起きたことの透明性のため。報告の書式の整合に必要だが、挙動の核ではない。

**Independent Test**: `SKILL.md` の完了報告の書式に `Created:` 行があり、ゲートがこの行を含む報告を従来どおり受け付ける。

**Acceptance Scenarios**:

1. **Given** 更新後の `SKILL.md`、**When** 完了報告の書式を読む、**Then** `Updated:` の次に `Created: <file> — <何を記録し、なぜ新しいファイルが必要だったか>` の行がある。
2. **Given** `Created:` 行を含む報告、**When** ゲートが走る、**Then** 従来どおりに評価される(新しい行が原因で問題にならない)。

---

### Edge Cases

- 作成した文書が、関連文書の候補として後から列挙された場合(同じ変更で作成したため、変更された文書になる)は、処分済みとして扱われる(既存の挙動)。
- 作成の上限を超える場合は、超えた分を `Proposed` として報告で提案する。専用の行は設けず、既存の `Unresolved:` または報告の文で述べる。
- 配置規則の節が無いプロジェクト(スキルの参照が読めない環境)では、プロジェクトの既存の構造に従う(スキルの既存の方針)。
- `SKILL.md` は 500 行未満を保つ。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `SKILL.md` は、関連文書(`find_related.py` が挙げるもの)のそれぞれを、更新するか、最終メッセージでパスと変更不要の理由を述べることを、手順に定めなければならない。
- **FR-002**: `SKILL.md` は、新しい文書を作成してよい条件を、「新しい公開契約(コマンド、オプション、設定、API、モジュール)が増え、それを扱う関連文書が無い」ときに限ると定めなければならない。
- **FR-003**: `SKILL.md` は、作成する文書の配置と形が `references/practices.md` の「Layers, placement, and proximity」の節に従うことを、その節へのリンクで示さなければならない。
- **FR-004**: `SKILL.md` は、1 回の変更で作成する文書は最大 3 ファイル(原文: at most three new files)とし、超える分は報告で提案することを定めなければならない。
- **FR-005**: `SKILL.md` は、決定記録をユーザーの依頼なしに作成しないこと(既存の規則)と、変更履歴を持たないプロジェクトに変更履歴を新設しないことを、作成の規則の一部として明記しなければならない。
- **FR-006**: `SKILL.md` の完了報告の書式は、`Updated:` の次に `Created: <file> — <what it documents and why no existing document fit>` の行を持たなければならない。他の行の意味と順序は変えない。
- **FR-007**: `hooks/rule.md` は、関連文書の処分と、作成の条件(新しい公開契約に限る)を、既存の箇条書きの形で短く加えなければならない。既存の箇条書きの意味は変えない。
- **FR-008**: 次を自動テストにしなければならない(実装より先に書き、失敗を確認する): (a) `SKILL.md` に処分の規則(更新、またはパスと理由)がある、(b) 作成の条件、配置規則へのアンカー付きリンク、上限 `at most three new files`、(c) 完了報告の書式に `Created:` 行がある、(d) `rule.md` に処分と作成の条件の趣旨がある。
- **FR-009**: `SKILL.md` は 500 行未満のままで、既存の定義検査(規則とスキルの一致、決定記録の規則、MADR4 など)がすべて通らなければならない。リンク検査(`check_links.py --changed`)はエラー 0 でなければならない。
- **FR-010**: 既存の単体テスト 132 件は、変更後もすべて通らなければならない。スクリプト(`*.py`)、スキーマ、README、eval は変更しない。

### Key Entities

- **処分(Disposition)**: 関連文書に対する、更新、変更不要の理由つきのパスの言及、作成、提案のいずれか。
- **新しい公開契約(New public contract)**: 利用者や他のコードが依存する、新しいコマンド、オプション、設定、API、モジュール。
- **作成の上限(Creation cap)**: 1 回の変更で作成する新規ファイルの数の上限(3)。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: `SKILL.md` と `rule.md` に、処分・作成の条件・上限・禁止・配置規則へのリンクのすべてが含まれる(テストで確認、必須の語句と anchor が 100% 存在)。
- **SC-002**: 完了報告の書式に `Created:` 行があり、他の行の順序と意味が変わっていない(テストで確認)。
- **SC-003**: 既存の単体テスト 132 件がすべて通り、追加したテストにより合計が増える。`SKILL.md` は 500 行未満。
- **SC-004**: `check_links.py --changed` のエラーが 0 である(配置規則へのリンクのアンカーを含む)。

## Assumptions

- 実際の LLM の振る舞い(規則に従って更新・作成・提案をするか)は、このスライスでは測定しない。仮定 A4(規則に効果がある)の検証は、S6 の eval を、費用の承認の後に実行して行う。
- 「新しい公開契約」の判断は、エージェントの判断に委ねる。機械的な検出は行わない。
- 上限の 3 は、メタスペックの設計判断で、設定では変更できない。
- `hooks/rule.md` は、セッション開始時に注入される短い規則であり、`SKILL.md` の詳細を繰り返さない。
