# Feature Specification: 介入時間の削減と品質の維持を、事前に固定した基準で判定する(引き継ぎ書 Phase 5)

**Feature Branch**: `feat/pilot-metrics`(`feat/review-card` から分岐)

**Created**: 2026-11-06

**Status**: Draft

**Input**: User description: "Phase 2 から先も順に実装"(2026-11-06)

**要旨**: `change-assurance` スキルに、比較実験の判定器 `scripts/pilot.py` と実験の手順書 `references/pilot.md` を加える。判定器は、実験の前に固定した**事前登録**と、案件ごとの人の作業時間と品質の**案件の記録**を読み、従来の方式(A)と新しい方式(B)の、元の要求1件あたりの人の介入時間の中央値の削減率を計算する。削減率が目標(既定は利用者が選んだ 20%)以上で、かつ事前登録した品質の条件をすべて満たすときだけ `adopt`(採用)と判定する。時間が短くても品質の条件を1つでも破れば採用しない。事前登録が案件より後なら、基準を結果の後に変えた疑いがあるため判定しない。実験そのもの(実案件の選定、人の作業時間の計測)は、利用者と関係者が行う。本仕様は、その実行も結果も含まない。

## 用語

- **方式 A・B**: A は従来の方式(既存のハーネスと従来の PR レビュー)、B は新しい方式(spec 059〜062 の仕組み)。
- **介入時間**: 1つの元の要求について、人が実際に作業した分数の合計。要求の確認、問題の再理解、AI への再指示、ログや差分の読解、レビュー、差し戻し、修正の再確認、承認の各項目を記録し、その和とする。AI の待ち時間は含めない。
- **削減率**: `1 - median(B) / median(A)`。
- **事前登録**: 実験の前に固定する、目標の削減率、方式ごとの最小の件数、品質の条件の名前、時間の項目、登録の日付の JSON。
- **案件の記録**: 案件ごとに、案件の ID、元の要求の ID、方式、層、完了したか、項目ごとの分数、品質の条件ごとの合否、開始の日付を書いた JSON。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 事前登録した基準で、採用するかを判定する (Priority: P1)

**Acceptance Scenarios**:

1. **P5-02** **Given** A の中央値が 50 分、B の中央値が 35 分(削減率 30%)、目標 20%、品質の条件をすべて満たす記録、**When** 判定する、**Then** `adopt` で、削減率 0.30 が示される。
2. **Given** 削減率が 10%、**Then** `not_adopted` である。
3. **P5-03** **Given** 削減率が 30% だが、B の案件の1つが品質の条件を破った記録、**Then** `not_adopted` で、破った条件と案件が示される。
4. **Given** 事前登録の日付が最初の案件の開始より後、**Then** `insufficient` である。
5. **Given** B の完了した案件が事前登録の最小の件数に足りない、**Then** `insufficient` である。

### User Story 2 - 標本の偏りと欠測を隠さない (Priority: P1)

**Acceptance Scenarios**:

1. **P5-01** **Given** 同じ方式に同じ `request_id` が2件ある、または時間の項目が事前登録と異なる案件、**Then** 形式の違反として判定しない(`insufficient` ではなく、終了コード 1 の違反)。
2. **P5-04** **Given** 層ごとに A と B がある記録、**Then** 層ごとの中央値と削減率が示され、B が A より長い層が示される。
3. **P5-05** **Given** ある層が B にしかない記録、**Then** `insufficient` で、その層が示される。
4. **P5-06** **Given** 未完了の案件を含む記録、**Then** 方式ごとの未完了の件数と、未完了を含めた中央値が示される。

## Requirements *(mandatory)*

- **FR-001**: `pilot.py [--format text|json] PREREG CASES` は判定の結果を出す。終了コードは、`adopt` で 0、`not_adopted` と `insufficient` と形式の違反で 1、入力を解釈できなければ 2 とする。形式と規則の詳細は `references/pilot.md` にある。
- **FR-002**: 判定器は読み取りだけを行い、ネットワークに接続しない。入力の読み込みは `assure.py` と同じ関数を使う。
- **FR-003**: 手順書は、事前登録の作り方、時間の測り方、割り当て、品質の条件、判定の読み方、判定器が保証しないことを書く。

## Success Criteria *(mandatory)*

- **SC-001**: User Story 1・2 の各シナリオを、実装の前に失敗するテストで確かめる。テストのデータは合成であり、実験の結果ではない。
- **SC-002**: 既存の検査がすべて通る。

## Out of Scope

実案件での実験の実施とその結果、統計的な検定、時間の自動計測、人の割り当ての自動化。
