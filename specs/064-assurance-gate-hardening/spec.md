# Feature Specification: 工程を飛ばしても、保証の判定が合格を出さないようにする

**Feature Branch**: `feat/assurance-gate-hardening`

**Created**: 2026-11-06

**Status**: Draft

**Input**: User description: PR #116 の実装に対する外部レビュー(「独立レビューを最終ゲートに組み込む」「工程の実行を検証可能にする」「証拠の出所を確認する」「失敗注入テストを追加する」)を検証した結果を受けて、"改善"(2026-11-06)

**要旨**: `change-assurance` の保証の判定(`assure.py gate`)は、前の工程が正しく終わっていることを前提にしていた。そのため、`goal-refinement` の判定を飛ばした要求グラフ(循環、存在しない子、子が1つの AND)、片付いていない反証の指摘(`"Open"`、定義にない状態、`resolution` のない `rejected`)、手順6の保証レビューを行っていない中・高リスクの変更を、`pass` と判定した。本仕様は、判定が自分の頼る記録を自分で検査し直すようにする。要求グラフの構造(規則 A-09)、反証の記録の指摘が答えられていること(A-08 の変更)、保証レビューの記録とその指摘が答えられていること(A-10)である。あわせて、親要求が自分の統合の検査(`L2` か `L3`)を持つことを、`goal-refinement` の検査器の新しい規則 S-12 と A-09 の両方で求める。

**利用者の指示と、決めた事項**:

**Authority**: 本仕様が正である。spec 061(保証の判定)、spec 062(レビューカード)、spec 059 と spec 060(要求グラフと反証の記録の形式)を、ここに書いた範囲で変える。それらの文書は書き換えない。

## 用語

spec 059〜063 の用語(要求グラフ、受け入れ条件、水準 L1〜L3、反証の記録、保証レビュー役、検証の記録、保証の判定、レビューカード)は、そのまま使う。

- **保証レビューの記録**: 保証レビュー役(要求グラフ、差分、生の証拠だけを読む読み取り専用のサブエージェント)の指摘と、その一つ一つへの答えを書いた JSON。`assurance-review.json`。
- **答えられた指摘**: D3 の条件を満たす指摘。
- **規則 S-12、A-09、A-10**: 本仕様で加える規則。S は `goal-refinement` の検査器、A は保証の判定の規則である。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 要求グラフの構造を検査していなくても、判定は壊れたグラフを合格させない (Priority: P1)

**Independent Test**: すべての受け入れ条件が合格した検証の記録と、構造を1か所だけ壊した要求グラフを、判定にかける。

**Acceptance Scenarios**:

1. **Given** 子に循環がある要求グラフ、**When** 判定する、**Then** `blocked` で、理由は A-09 である。
2. **Given** 定義されていない子を挙げる親、**Then** `blocked`(A-09)である。
3. **Given** 子が1つの `AND`、または子を持つ `LEAF`、**Then** `blocked`(A-09)である。
4. **Given** 親を持たない要求が2つあるグラフ、**Then** `blocked`(A-09)である。
5. **Given** ID が重なる2つの要求、または受け入れ条件が空の要求、**Then** `blocked`(A-09)である。
6. **Given** 受け入れ条件が `L1` だけの `AND` の親、**Then** 判定は `blocked`(A-09)、`goal-refinement` の検査器は S-12 の違反である。
7. **Given** `goal-refinement` の検査器のテストの要求グラフのうち、A-09 が検査し直す規則(S-01〜S-04、S-06、S-11、S-12)か、判定が終了コード 2 で拒む S-07(定義にない水準、2つの条件で使われた受け入れ条件の ID)に違反するもの、**When** すべての受け入れ条件が合格した検証の記録とともに判定する、**Then** どれも `pass` にならない。違反のないものは `pass` である。

### User Story 2 - 片付いていない指摘は、どう書かれていても判定を止める (Priority: P1)

**Acceptance Scenarios**:

1. **Given** 承認のある `high` の変更と、指摘の状態が `"Open"`(大文字)、`"closed"`(定義にない値)、`resolution` のない `rejected` のいずれかの反証の記録、**When** 判定する、**Then** `blocked`(A-08)である。
2. **Given** ID が重なる指摘、または対象が要求グラフにも問題にもない指摘を持つ反証の記録、**Then** `blocked`(A-08)である。
3. **Given** すべての指摘が `accepted` か `rejected` で `resolution` を持つ反証の記録、**Then** A-08 を満たす。

### User Story 3 - 中・高リスクの変更は、保証レビューの指摘に答えるまで合格しない (Priority: P1)

**Acceptance Scenarios**:

1. **Given** すべての検査が合格した `medium` の変更、**When** 保証レビューの記録を渡さずに判定する、**Then** `blocked`(A-10)である。`high` も同じである。
2. **Given** 審査の対象のコミットに対し、指摘がない、またはすべて答えられた保証レビューの記録、**Then** `pass` である。
3. **Given** 答えられていない指摘を持つ保証レビューの記録、**Then** リスクにかかわらず `blocked`(A-10)である。
4. **Given** `reviewed_commit` が検証の記録と異なる保証レビューの記録、**Then** `blocked`(A-10)で、理由は古いレビューである。
5. **Given** 別の `change_id` の保証レビューの記録、**Then** 終了コード 2 である。
6. **Given** `low` の変更、**When** 保証レビューの記録を渡さずに判定する、**Then** A-10 は判定を止めない。
7. **Given** 同じ入力、**When** レビューカードを作る(`card --review`)、**Then** 判定は `gate` と同じで、答えられていない指摘を未解消の事項に並べる。

### Edge Cases

- **判定が検査し直さない規則**: 欄の形式(S-00)と `OR` の選択条件(S-05)は検査し直さない。判定は、`OR` のどの選択肢についても、受け入れ条件ごとの検査を求めるため、選択条件が欠けても検証されない受け入れ条件は生じない。
- **合格の意味**: 判定の `pass` は、引き続き記録どうしの整合だけを示す。保証レビュー役の同意は証拠ではなく、反証役と同じく同じ系統のモデルによる意見である。

## Requirements *(mandatory)*

- **FR-001**: `goal-refinement` の検査器は、要求グラフに規則 S-12「`AND` と `OR` の要求は、`L2` か `L3` の受け入れ条件を1つ以上持つ」を加える。
- **FR-002**: 保証の判定は、規則 A-09「要求の ID が空でなく重ならない。挙げた子はすべて定義され、一度だけ挙げられる。子をたどって元に戻らない。`LEAF` は子を持たず、`AND` と `OR` は子を2つ以上持つ。親を持たない要求はちょうど1つである。どの要求も受け入れ条件を1つ以上持つ。`AND` と `OR` は `L2` か `L3` の受け入れ条件を持つ」を判定し、満たさなければ `blocked` とする。
- **FR-003**: 規則 A-08 を「`high` の変更は、その問題の反証の記録を伴う。渡した記録の指摘は、すべて答えられている(D3。対象は要求グラフの要求か問題)」に改める。
- **FR-004**: 保証の判定とレビューカードは、`--review REVIEW` で保証レビューの記録を受け取り、規則 A-10「`medium` と `high` の変更は、審査の対象のコミットに対する保証レビューの記録を伴う。渡した記録の指摘は、すべて答えられている(対象は要求、受け入れ条件、変更のいずれか)」を判定する。満たさなければ `blocked` とする。別の変更の記録と、形式が読めない記録は終了コード 2 とする。
- **FR-005**: 保証レビュー役の指示文は、記録に写せる形(指摘ごとに `id`、`kind`、`target`、`severity`、`statement`、状態 `open`)で答えを求める。
- **FR-006**: `change-assurance` の SKILL.md、`references/manifest.md`、`references/reviewer.md`、`goal-refinement` の `references/checker.md`、README の英日を、変更後の動作に合わせる。
- **FR-007**: リポジトリの検査 `tests/run-change-assurance-skill.sh` は、User Story 1 の受け入れシナリオ7を確かめる。

## Success Criteria *(mandatory)*

- **SC-001**: User Story 1〜3 の各シナリオを、実装の前に失敗するテストとして書き、失敗を確かめてから実装する。
- **SC-002**: 会話で示した失敗注入の8件(中リスクの変更が保証レビューなしで `pass`、`"Open"`・`"closed"`・`resolution` のない `rejected` で高リスクの変更が `pass`、循環・存在しない子・子が1つの AND・`L1` だけの親を判定が `pass`)が、すべて `pass` でなくなる。
- **SC-003**: 既存の検査がすべて通る。既存のテストの意図(1つの規則だけを確かめる)を保つため、`medium` か `high` の変更で別の規則を確かめるテストには、答えられた保証レビューの記録を渡す。

## Assumptions

- 保証レビュー役を、中・高リスクの変更のたびに、審査の対象のコミットに対して実行し直せる(確度: 中)。直すたびに実行し直す手間は、比較実験(spec 063)の作業時間に表れる。
- 判定が検査し直す規則と `goal-refinement` の検査器の規則は、FR-007 の検査でずれを見つけられる(確度: 中)。その検査が使う要求グラフは、`goal-refinement` のテストの入力に限られる。

## Out of Scope

証拠の出所の確認(CI のジョブの結果や承認者の本人確認)、Claude Code の実行の観測(スキルやサブエージェントが実際に起動したか)、多段の親スキル(spec 058 の D4)、比較実験の実施、問題カードの規則の判定での検査し直し。
