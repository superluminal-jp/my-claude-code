## シナリオ2: 新規プロジェクトでの戦略整理（ユーザーストーリー1）

**セットアップ**:

```bash
mkdir -p /tmp/product-strategy-quickstart/greenfield && cd /tmp/product-strategy-quickstart/greenfield
# README も specs/ も置かない、ほぼ空のディレクトリ
```

**実行**: このディレクトリで Claude Code セッションを開始し、スキル名を出さずに次のように依頼する:

> 「この新規プロダクトの戦略を整理したい」

**期待結果**（[spec.md](./spec.md) 受け入れシナリオ1参照）:
- `product-strategy` スキルがロードされる（他のスキルではない）。
- ビジョン・ターゲットユーザー・提供価値・成功指標・スコープの優先順位が、いきなり技術計画に入ることなく引き出される。
- 完了後、`## ステータス: 完成` のマーカーを持つ単一ファイルが生成され、契約Bの6必須セクションをすべて含む。
- 実行前後で `git status`（または同等の差分確認）を取り、生成されたブリーフファイル以外に変更されたファイルが無いことを確認する——スキルが自らの成果物以外に一切書き込まないという制約（FR-011）を実地で検証する。
- 途中でセッションを意図的に中断した場合、`ドラフト（未完成）` マーカーと未回答セクション一覧を持つファイルが残ることを別途確認する（FR-007a）。

## シナリオ3: 既存プロジェクトでの戦略整理（ユーザーストーリー2）

**セットアップ**: 整備された `README.md` と `CLAUDE.md`、および少なくとも1つの `specs/<N>-*` ディレクトリを持つプロジェクトを使う（本リポジトリ自身で検証してよい）。

**実行**: 同様にスキル名を出さずに依頼する:

> 「既存プロダクトに新機能を足す前に戦略を整理したい」

**期待結果**（spec.md 受け入れシナリオ2参照）:
- スキルが `README.md`/`CLAUDE.md`/過去の `specs/` をまず読み込み、そこに既に書かれている事実（プロダクト名、既存の目的など）を聞き直さない。
- 新しい戦略が既存の文脈と矛盾・縮小する場合、契約Bの「既存の戦略との関係」セクションが生成され、サイレントに統合されない。
- 既に同じ場所に戦略ブリーフが存在する状態でもう一度実行すると、上書きか新バージョンかをスキルが確認する（FR-011a、契約B）。

**期待結果**: SC-002（既存のルーティング判断への回帰ゼロ）が壊れていないことを、この2件で代表的に確認する。
