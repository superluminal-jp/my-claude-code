# 機能仕様書: 開発着手前の戦略整理を支援する `product-strategy` スキルの追加

**機能ブランチ**: `037-product-strategy-skill`

**作成日**: 2026-09-04

**ステータス**: ドラフト

**入力**: ユーザー記述: 「プロダクト開発における戦略をSpeckitなどを使って開発するに先立って整理するスキルを作りたい。既存のプロジェクトにも新規プロジェクトにも対応できるように。」

## 明確化の決定

本ドラフトが定まるまでに、2 ラウンドにわたってユーザーと重要な論点を解消した。

1. **「戦略」の範囲**: プロダクト/事業戦略——ビジョン、ターゲットユーザー、課題と提供価値、成功指標、優先順位とスコープの境界。アーキテクチャや技術選定の意思決定はスコープ外とする。
2. **下流ツールとの関係**: 単体で完結する。ユーザーの追加発言（「speckitに引き継ぐことは考えなくて良い。戦略立案を手助けする単体のスキルを作成したい」）により、当初の枠組みは上書きされた。本スキルは Speckit や他の特定の下流ツールに先行・供給・整合させることを目的とせず、それ自体としてプロダクト戦略の整理を助けるために存在する。他ツールの管理ファイルへ書き込まない点は変わらないが、これは Speckit 向けの特別な配慮ではなく、「自分自身の成果物のみを生成する」という一般原則として位置づけ直す。

残る未解決点は、ブロッキングな質問としてではなく [前提条件](#前提条件) と [リスク / 未解決の論点](#リスク--未解決の論点) に記録する。これは clarifier プロセスの「ブロッキングな論点はまとめて解消し、その後は進める」という原則に従うものだが、実装に昇格させる前にレビューすべきである。

## 明確化

### セッション 2026-09-04

- Q: 既にプロダクト戦略ブリーフが存在するプロジェクトに対して本スキルを再度実行した場合、既存ファイルをどう扱うべきか？ → A: 既存ブリーフの有無を検知し、上書きするか新しいバージョンを作るかをユーザーに確認する——サイレントに決定しない。
- Q: 引き出し（エリシテーション)の途中で会話が中断された場合、それまでの内容を未完成のドラフトとして保存すべきか、それとも破棄してやり直すべきか？ → A: 未完成である旨を明示した上で、途中経過をドラフトブリーフとして保存する——中断によってセッションが失われないようにする。

## ユーザーシナリオとテスト *(必須)*

### ユーザーストーリー1 - 新規プロダクトにおける戦略整理 (優先度: P1)

グリーンフィールドのプロジェクトを始めようとしている人が、何を・なぜ作るのかを整理する手助けを求める——「この新規プロダクトの戦略を整理したい」「実装に入る前にプロダクト戦略を一緒に考えてほしい」。スキルがロードされ、構造化された引き出し（ビジョン、ターゲットユーザー/JTBD、課題と提供価値、成功指標、MoSCoW によるスコープの優先順位付け、制約）を実行し、単体のドキュメントとして戦略ブリーフを生成する。

**この優先度の理由**: 依頼で名指しされた主要ケース（「新規プロジェクト」）そのものである。これがなければ本スキルは存在意義を持たない。

**独立したテスト**: 既存コード・ドキュメント・`specs/` の無いディレクトリでセッションを開始し、スキル名を出さずに戦略整理を求める質問をして、`product-strategy` がロードされ、事実を捏造することなく（不明点はフラグを立てる、でっち上げない）必須セクションを網羅したブリーフを生成することを確認する。

**受け入れシナリオ**:

1. **Given** ほぼ空のプロジェクトディレクトリ、**When** ユーザーが開発着手前にプロダクト戦略を整理したいと依頼する、**Then** `product-strategy` スキルがロードされ、技術的な計画にいきなり入るのではなく、ビジョン・ターゲットユーザー・課題/提供価値・成功指標・スコープの優先順位を引き出す。
2. **Given** 引き出しが完了した、**When** スキルが出力を生成する、**Then** 結果は対象プロジェクト配下に保存される単一の自己完結した戦略ブリーフドキュメントであり、FR-006 の必須セクションをすべて網羅する。
3. **Given** ユーザーがまだ重要な事項（例: ターゲットユーザー層）を決めていない、**When** スキルがその論点に到達する、**Then** 答えをでっち上げるのではなく、論点そのものと推奨デフォルトを明示する。

---

### ユーザーストーリー2 - 既存プロダクトにおける戦略整理 (優先度: P1)

コードベース・README、場合によっては過去の `specs/` 履歴を既に持つプロジェクトで作業している人が、新しい取り組み・拡張・方向転換について仕様策定の前に戦略を整理したいと依頼する——「既存プロダクトに新機能を足す前に戦略を整理したい」。スキルはまず既存のもの（README、`CLAUDE.md`、過去の戦略ブリーフ、過去の spec ディレクトリ）を読み込んで既知の事実を聞き直すことを避け、その上で新規・変更点のみを引き出し、既存の枠組みとの関係（拡張する・狭める・置き換える）を明示したブリーフを生成する。

**この優先度の理由**: 依頼で名指しされたもう一方の主要ケース（「既存のプロジェクト」）であり、単にストーリー1の入力が増えただけの縮小版ではない——発見（ディスカバリ）のステップと、既存の文脈に矛盾したりサイレントに上書きしたりしないという要件は、質的に異なる振る舞いである。

**独立したテスト**: `README.md` が整備され、少なくとも1つの過去の `specs/<N>-*` ディレクトリを持つプロジェクトで同種の戦略に関する質問を行い、スキルの質問がそれらのファイルに既に記載された事実を聞き直していないこと、生成されたブリーフが何を土台にしているかを明示的に引用していることを確認する。

**受け入れシナリオ**:

1. **Given** 既存の `README.md`・`CLAUDE.md`、および/または過去の戦略・spec 成果物を持つプロジェクト、**When** ユーザーが新規・変更に関する戦略整理を依頼する、**Then** スキルはまずその文脈を読み込み、既にそこに記録されている事実をユーザーに再度尋ねない。
2. **Given** 新しい戦略が既存の文書内容と矛盾する、または狭める、**When** スキルがブリーフを生成する、**Then** サイレントに統合するのではなく、その矛盾・縮小を明示的に述べる。
3. **Given** 既存プロジェクトにプロダクトの文脈を示す文書が一切ない（未文書化のレガシーコード）、**When** スキルが実行される、**Then** ストーリー1と同様のインタビューのみの引き出しにフォールバックし、履歴が欠落している旨をでっち上げるのではなくフラグとして示す。

---

### エッジケース

- **ユーザーが戦略整理を経ずに実装へ直行したい**: スキルは決してフローに割り込んではならない——明示的な戦略整理の依頼があったときのみ発火し、他の作業の前段としてブロッキングなゲートになってはならない。
- **引き出しセッションが全ての必須セクションに回答する前に終了する**（ユーザーが中断する、セッションが閉じられる、「一旦ここまで」と明示的に述べる等）: スキルは収集済みの内容を破棄せず、未完成であることを明示したドラフトブリーフとして保存しなければならない。
- **複数の、互いに矛盾する過去の戦略成果物が存在する**（例: 記録済みの方向転換）: スキルは最新のものを提示し、どちらが優先するかをユーザーに確認しなければならない。サイレントに統合してはならない。
- **依頼が、既に合意済みの1機能に関するスコープ/受け入れ基準の曖昧さである場合**: これは `clarifier` の管轄（1つの既にスコープ確定した機能の要件を確定させる）であり、本スキルの管轄（それらの機能が奉仕するプロダクトレベルの方向性を定める）ではない。`clarifier` にルーティングしなければならない。
- **依頼が Scrum/ファシリテーション色の強いものである場合**（「週次の振り返り」、スプリント計画など）: 本スキルではなく `scrum-master` にルーティングしなければならない。
- **依頼がプロダクト開発と無関係なオープンエンドな文書共同作成である場合**（一般的なメモ、ブログ記事など）: `minto-builder` にルーティングするか、本スキルの管轄外として扱う——本スキルの管轄は、あくまで開発作業に先立つ戦略整理に限定される。
- **依頼が今後の開発作業と関連しない一般的な事業計画書やピッチデックである場合**: 管轄外——`scrum-master` の仕様が一般的なプロジェクトマネジメントとの境界を引いたのと同様に、隣接するが対象外である旨をフラグする。

## 要求事項 *(必須)*

### 機能要求

**スキルの形状**

- **FR-001**: 本スキルは `product-strategy` という名称を持ち、既存のカスタムスキル群（`adr`、`clarifier`、`coder`、`minto-*`、`scrum-master`、`digital-agency-frontend`、`apple-notes`、`apple-reminders`、`git-workflow`、`cloud-platform-research`）と並んで `.claude/skills/product-strategy/SKILL.md` に配置しなければならない。
- **FR-002**: 本スキルの `description` フロントマターは、トリガー条件と明示的な非対象条件の両方を、本リポジトリの既存の慣例（`clarifier`、`scrum-master` のフロントマターを参照）に従って記述し、他のスキルと同様に自動ルーティングの評価対象となるようにしなければならない。
- **FR-003**: 本スキルの本文が適用するすべてのフレームワークは、名前・年代・出典を明示した引用可能な文献に基づかなければならない——出典のないフレームワークがあってはならない。これは、本リポジトリの「名前・年代付きの文献に基づく参考文献セクション」という慣例（`clarifier` の ISO 29148/INVEST/SMART の引用を参照）に一致する。基本ツールボックスとその出典は [参考文献](#参考文献) に一覧化し、FR-003a〜FR-003g がそれぞれをブリーフのどのセクションに紐づけるかを規定する。
- **FR-003a**: ビジョン/課題の整理には、Osterwalder & Pigneur のビジネスモデルキャンバス（2010）、より軽量な扱いを望む場合は Maurya のリーンキャンバス（2012）を引用しなければならない。さらに、ソフトウェア/テックプロダクト固有の戦略対ロードマップの区別を補うものとして、Cagan の *INSPIRED*（2017/2018）を引用しなければならない。
- **FR-003b**: ターゲットユーザーの整理には、Christensen らの Jobs-to-be-Done 理論（2016）と、ユーザー文脈の収集・検証プロセスとしての ISO 9241-210（2019）を引用しなければならない。さらに、JTBD が示す「なぜ」を、実際の引き出し手順である「どのように」へ橋渡しする方法として、Torres のオポチュニティ・ソリューション・ツリー（*Continuous Discovery Habits*、2021）を引用しなければならない。
- **FR-003c**: 提供価値の整理には、Osterwalder・Pigneur・Bernarda・Smith の価値提案キャンバス（2014）を引用しなければならない。
- **FR-003d**: 成功指標の整理には、Doerr の OKR（2018、Grove の iMBO（1983）に遡る）を成果志向の目標設定として引用しなければならない。単一の North Star 指標では多利害関係者のプロダクトを正しく表現できない場合の代替として Kaplan & Norton のバランスト・スコアカード（1992/1996）を引用しなければならない。「North Star」という語自体を用いる場合は、その出典として Sean Ellis による命名（2010年代初頭）と、Amplitude/John Cutler による体系化（"North Star Playbook"）を引用しなければならない。
- **FR-003e**: スコープ/優先順位の整理には、`clarifier` から流用する本リポジトリ既存の MoSCoW の引用（Clegg & Barker、1994）を用いなければならず、競合する優先順位付け方式を新たに持ち込んではならない。
- **FR-003f**: ビジョン/「なぜ」のセクションには、Porter による戦略の定義（1996、他と区別された独自の一連の活動としての戦略）を引用し、ブリーフにおける「戦略」がロードマップやバックログと混同されないようにしなければならない。
- **FR-003g**: MoSCoW によるイン/アウトの判断を補うものとして、スコープ内に含めた項目が「当たり前品質」なのか「魅力的品質（差別化要因）」なのかを識別する軽量な視点として、狩野モデル（Kano, Seraku, Takahashi, Tsuji、1984）を引用してもよい（MUST ではなく SHOULD）。

**スコープの境界**

- **FR-004**: 本スキルはプロダクト/事業戦略の内容（ビジョン、ターゲットユーザー、課題と提供価値、成功指標、スコープの優先順位、制約）のみを扱わなければならない。アーキテクチャ、技術スタック、内製/購入の意思決定を行ってはならない——それらは本スキルが担わない、別の・後段の関心事である（不可逆性の高い技術的判断については、`adr` が独立して適用される場合にそちらを参照）。
- **FR-005**: 本スキルの description は、`clarifier`（既にスコープ確定した1機能の要件を確定させる）、`scrum-master`（プロセス/ファシリテーション）、`minto-builder`（汎用的な文書共同作成）と自らを区別し、複合的・隣接した依頼が誤ってルーティングされないようにしなければならない。

**引き出しと出力内容**

- **FR-006**: 生成される戦略ブリーフには、ビジョン/課題の記述、ターゲットユーザー（Jobs-to-be-Done またはペルソナによる整理）、提供価値、成功指標（North Star 的な成果指標と、それを支える補助指標）、MoSCoW で表現したスコープと優先順位、制約を含めなければならない。未解決の重要な論点は、`clarifier` テンプレートの「デフォルト/代替案/影響」構造に従って、サイレントに決定するのではなく、デフォルトと代替案を明示した未解決の前提として記録しなければならない。
- **FR-007**: 本スキルは既存プロダクト、そのユーザー、その指標について事実を捏造してはならない。プロジェクト内に根拠が存在しない場合、推測するのではなく、質問するか論点として明示しなければならない。
- **FR-007a**: 引き出しセッションが FR-006 の必須セクションすべてに回答する前に終了した場合、スキルはセッションの入力内容を破棄するのではなく、未完成である旨のマーカー（例: `ステータス: ドラフト——未完成` と未回答セクションの一覧）を付した部分的なブリーフとして保存しなければならない。

**新規/既存プロジェクトの分岐**

- **FR-008**: 対象プロジェクトが既存のプロダクトの文脈（README、`CLAUDE.md`、過去の戦略ブリーフ、過去の `specs/` 履歴）を持つ場合、スキルはまずそれを読み込み、既にそこに記録されている事実をユーザーに再度尋ねてはならない。
- **FR-009**: 新しい戦略が既存の文書化された文脈と矛盾する、狭める、あるいは置き換える場合、スキルの出力はサイレントに統合するのではなく、その関係性を明示的に述べなければならない。
- **FR-009a**: 複数の、互いに矛盾する過去の戦略成果物が見つかった場合、スキルは最新のものを提示し、どちらを優先するかをユーザーに確認しなければならない。サイレントに統合してはならない（エッジケース）。
- **FR-010**: そのような文脈が存在しない場合（新規プロジェクト、または文書化されたプロダクトの枠組みを持たない既存プロジェクト）、スキルはインタビューのみの引き出しにフォールバックし、事前の文脈が欠落していることをでっち上げるのではなくフラグとして示さなければならない。

**出力成果物**

- **FR-011**: 本スキルは戦略ブリーフを、対象プロジェクト配下の単一の自己完結したドキュメントとして生成しなければならない（例: 対象プロジェクトが既に `specs/<N>-*` の慣例を用いている場合は `specs/<N>-<slug>/strategy.md`、それ以外はプロジェクトに適した既定の場所、例えば `docs/strategy/<slug>.md`）。スキル自身が作成したのではないファイルへ書き込む・変更してはならない——自らの成果物のみを生成し、他のツールのファイルやワークフローへの依存・統合を持たない。
- **FR-011a**: 書き込みの前に、スキルは対象の場所に既に戦略ブリーフが存在するかを確認しなければならない。存在する場合、サイレントに上書きしたりサイレントにバージョンを積み上げたりするのではなく、上書きするか新しいバージョンを作るかをユーザーに確認しなければならない。

**配布とドキュメント**

- **FR-012**: `install.sh` は、他のカスタムスキルと同じ仕組みを用いて、本スキルをユーザースコープの Claude Code スキル配置先に配置しなければならない（Codex CLI への配布対象は無い——Codex サポートは spec 029/031 により本リポジトリから既に除去されている）。
- **FR-013**: 本リポジトリのスキル一覧（`README.md`、`README.ja.md`）は、既存スキルが列挙されているのと同じ場所・同じ形式で、`product-strategy` を一行の目的説明とともに列挙しなければならない。
- **FR-014**: スキルの境界を列挙するルーティングルール文書があれば、それには `product-strategy` のエントリを含め、それがいつ適用されるか、`clarifier`・`scrum-master`・`minto-builder` とどう異なるかを述べなければならない。

**回帰テストの網羅**

- **FR-015**: ルーティング回帰スイートには、期待されるスキルが `product-strategy` であるケースを少なくとも1つ含めなければならない（新規プロジェクトのプロンプトを対象とする）。また、隣接する依頼（Scrum ファシリテーション、または単一機能のスコープ明確化）が引き続き既存のスキルにルーティングされ、この新しいスキルにはルーティングされないことを確認する否定的なケースを少なくとも1つ含めなければならない。
- **FR-016**: 本スキルの追加後も、既存のルーティング回帰ケースはすべて変更なく成功しなければならない。

**構造上の制約（`run-config-pyramid.sh` の既存契約に由来）**

- **FR-017**: 本文は `clarifier`・`scrum-master`・`minto-builder`・`coder` 等の兄弟スキル名をそのまま埋め込んではならない（`authored_skills` 群に加わる以上、他の全メンバーが満たしている構造契約——SKILL-05 相当——であり、本スキルだけを例外にしない）。
- **FR-018**: 本文は `.claude/skills/product-strategy/` という自分自身の配置パスをハードコードしてはならない（同上、SKILL-06 相当）。

### 主要エンティティ

- **戦略ブリーフ**: 単体の出力ドキュメント——ビジョン、ターゲットユーザー、課題/提供価値、成功指標、MoSCoW によるスコープの優先順位、制約、未解決の前提を含む。対象プロジェクトの所有物であり、本リポジトリの所有物ではない。
- **既存プロダクトの文脈**: 対象プロジェクトが既に文書化しているプロダクトに関するあらゆる情報——README、`CLAUDE.md`、過去の戦略ブリーフ、過去の `specs/` エントリ。読み込まれるが、サイレントに上書きされることはない。
- **ルーティング境界**: `product-strategy` に属するもの/属さないものの明示的な記述であり、`clarifier`・`scrum-master`・`minto-builder` と区別する。独立したデータエンティティとしてではなく、[data-model.md](./data-model.md) の「スキル」エンティティの検証ルール V2/V3 として実現される。

## 成功基準 *(必須)*

### 測定可能な成果

- **SC-001**: スキル名を出さずに開発着手前の戦略に関する質問をしたユーザーが、`product-strategy` のロードと、そのブリーフ構造に沿った回答を得る——新規プロジェクトのケースと既存プロジェクトのケースを対象に、表現の異なる少なくとも4つのプロンプトで検証する。うち少なくとも1つは日本語、少なくとも1つは英語のプロンプトとする。
- **SC-002**: 本変更以前から存在していたすべてのルーティング回帰ケースが、以前と同じスキルに解決される——回帰ゼロ。
- **SC-003**: 既存プロジェクトのシナリオにおいて、整備された `README.md`/`CLAUDE.md` を持つプロジェクトに対して生成されたブリーフは、それらのファイルに既に記載されている事実を一切聞き直していない——固定のサンプルプロジェクトに対して検証する。
- **SC-004**: 完成したブリーフの100%が FR-006 の6つの必須セクションすべてを含む。完成したブリーフ内の欠落した入力は、捏造された値ではなく、フラグの立った前提として表現される。中断時に保存された部分的なブリーフ（FR-007a）はこの集計の対象外とするが、未完成であることが判読可能な形で明示されていなければならない。
- **SC-005**: `install.sh` を1回実行した後、`product-strategy` がユーザースコープの Claude Code スキル配置先で発見可能であり、インストーラーを再実行しても同一の終了状態になる（重複なし、リンク切れなし）。
- **SC-006**: 読者は、英語版・日本語版いずれのドキュメントからも、スキル自体を開くことなく1分以内に `product-strategy` を見つけ、その目的を理解できる。

## 前提条件

- **本スキルは完全に単体で完結する。** Speckit や他の特定の下流ツールへの依存や、それらとの統合作業を一切行わない（ユーザーによる明示的なスコープ縮小に基づく——[明確化の決定](#明確化の決定) の2を参照）。そのようなツールが対象プロジェクトに存在するか否かにかかわらず、同一に動作する。
- **「既存プロジェクトか新規プロジェクトか」は、ユーザーの申告ではなく証拠によって解決する。** スキルは対象プロジェクトを検査して文書化されたプロダクトの文脈の有無を調べ、それに基づいて分岐する（FR-008〜FR-010）。ユーザーに最初にモードを選ばせることはしない。
- **本スキルは単発の引き出し+ドキュメント生成器である**——複数セッションにまたがる戦略トラッキングシステムではない。中断時に保存される部分的なブリーフ（FR-007a）は可読性のための保険であり、再開可能なセッションではない——スキルは以前の部分的なブリーフを読み込んで引き出しの続きから再開することはしない。後続の実行は最初からやり直すか、FR-011a に従って発見したファイルの上書き/バージョン管理についてユーザーに確認するかのいずれかである。それを超えて戦略ブリーフを継続的に見直したりバージョン管理したりすることは本機能のスコープ外である。
- **本スキルは一度に1つのプロダクト/取り組みを対象とする。** 複数プロダクトにまたがるポートフォリオレベルの戦略はスコープ外である。
- **配布対象は Claude Code のみである。** Codex CLI サポートは本リポジトリから既に除去されており（spec 029、031）、本機能は第二の配布対象を再導入しない。
- **ブリーフの既定の保存場所は、対象プロジェクト自身の慣例に従う**（`specs/<N>-*` があればそれ、なければ `docs/strategy/`）。本リポジトリが固定のパスを指定するわけではない。

## リスク / 未解決の論点

以下はブロッキングとして扱わなかった。それぞれに妥当なデフォルトが存在し、いずれも単独ではスキルの本質（そのスコープと、単体出力のみという性質——これらは決定済み）を変えないためである。実装への昇格前にレビューすべきである:

1. **トリガー境界の精度（FR-002、FR-005 に関連）。** `product-strategy`、`clarifier`、`scrum-master`、`minto-builder` はいずれも「作業に入る前に自分が本当に欲しいものを整理したい」という何らかの形を扱う。それらが衝突しないようにする正確な文言は、`scrum-master` の仕様が FR-007a の境界に払ったのと同じ注意を要する——実装時に4つの description を並べて起草することを推奨する。
2. **フレームワークツールボックスは引用によって既に固定されている（FR-003a〜FR-003g、参考文献）。未解決なのはそこではない。** 実装時の判断として残るのは、各引用フレームワークをどこまで規範的にユーザーへ提示するか（例えば常に文字通りのビジネスモデルキャンバスの格子を生成するか、散文的な等価物にするか）のみであり、ブリーフの根拠とする出典そのものではない。
3. **出力ファイル名/見出し規約の既定値**は機能的には記述されている（FR-011、FR-006）が、厳密なテンプレートファイルとしては固定されていない。スキル自身が使う `templates/strategy-brief-template.md` のようなものを実際に作るかどうかは実装に委ねる。
